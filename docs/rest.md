# sfbench REST API の画面の技術設計

区切り4で作る REST API の画面の設計を書く。
画面の見た目は [screens.md](screens.md)、サーバーの API は [design.md](design.md)、画面全体の作り（状態の持ち方、非同期の流れ、エラーの扱い）は [web.md](web.md) にあり、この文書はそれらに REST API の画面を足す部分を決める。

## 範囲

区切り4は、次の2つの PR に分ける。

| PR | 内容 |
| --- | --- |
| 4a（サーバー） | `POST /api/orgs/:user/rest`、要求の検査、実行履歴の保存と `GET /api/orgs/:user/rest/history`、`--rest` と `--body` の CLI、テスト |
| 4b（画面） | ヘッダーのタブ（SOQL と REST API）、作業画面に2つの画面を置く作り、REST API の画面（実行履歴、要求の欄、Send、本番の確認、レスポンス）、`--rest` の初期値と案内 |

次のものは区切り4に入れず、あとの PR にする。

- **REST API の AI**：[ai.md](ai.md) のとおり、先に `AiContext` を、どの画面でも使う部分と画面ごとの部分に分ける必要があり、それだけで状態の多い設計になる。データを変えうる送信の流れと同じ PR に入れると、レビューの対象が倍になる。
- **結果の表での編集と削除**：行の選択、セルの編集、sObject Collections の一部の失敗、本番の確認と、SOQL の画面の状態が大きく増える。REST API の画面と共有できるのは、本番の確認の判定と `/rest` の経路だけなので、別の PR にする。

Apex のタブは、区切り5まで出さない。

## 前提にする事実

いまのコードには、REST API の画面の設計を左右する性質が4つある。

1. **Salesforce のエラーを例外にしている。** `OrgClient.request` は 400 以上を `SalesforceError` として投げ、サーバーは Salesforce の 4xx をそのまま HTTP ステータスにして返す。REST API の画面でこの経路を使うと、Salesforce の 404 や 401 を、sfbench の `NOT_FOUND` やセッション切れと取り違える。
2. **画面で止めても、Salesforce への要求は止まらない。** サーバーの `client.request` は中止の signal を受け取らない。画面で待つのをやめても、サーバーは Salesforce の応答まで処理を続ける。
3. **GET でもデータを変えうる。** Tooling API の `executeAnonymous` や、`/services/apexrest/` に置いた利用者の Apex REST は、GET でもデータを変えられる。パスは利用者が自由に書くので、メソッドだけでは読み取りと言えない。
4. **ボディのある GET を、代わりの経路で送ってしまう。** `fetch` は、ボディのある GET を送る前に TypeError を投げる。`fetchOnce` はこれをネットワークエラーとみなすので、GET は `sf api request rest` で送り直される。
5. **401 が返ると、同じ要求を送り直す。** `sendWithFetch` は、401 が返るとトークンを取り直して同じ要求をもう一度送り、2回目も 401 なら `OrgAuthError` にする。利用者の Apex REST は、データを変えたあとで 401 を返せるので、そのまま `/rest` に使うと POST が二重に実行される。
6. **利用者のヘッダーと既定のヘッダーを、名前の大文字と小文字を区別して重ねている。** `content-type` と小文字で書くと、既定の `Content-Type` と別のキーになり、`fetch` は2つの値をつないで送る。

## 画面の切り替え

### モードの置き場所

いま開いている画面（`mode`：`soql` か `rest`）は、作業画面の外の `AppContext` に置く。
ヘッダー（作業画面の外）が書き、作業画面が読むからである。
sessionStorage（`sfbench.mode`）に保存し、タブを再読み込みしたら戻す。
組織を切り替えても、モードは変えない（パネルの開閉と同じ、表示の好みとして扱う）。
起動時に `--rest` があれば、最初のモードを `rest` にする。

### 作業画面の作り

組織の `key` で作り直す `OrgWorkspace` の中に、SOQL の画面と REST API の画面の両方を置いたままにし、選んでいない方は `hidden` で隠す。
エディタ領域を閉じるときにすでに使っている作りと同じである。
React の Activity は使わない。隠したときに effect の後始末が走り、`useTask` が要求を中止するからである（web.md「`useTask` の状態と遷移」）。
REST API の画面は、最初に開いたときに作り、以後は隠すだけにする。

`SoqlProvider`、`PanelsProvider`、`AiProvider` は SOQL の画面だけを、`RestProvider` は REST API の画面だけを包む。
2つの画面は、互いの状態を読まない。
選んでいないタブで要求が走っていることを示す印は出さない。出すには、作業画面の中の「送信中」を、外にあるヘッダーへ知らせる配線が要り、作業画面を作り直したときの後始末も要るからである。

| 状態 | タブを切り替えたとき |
| --- | --- |
| SOQL のエディタ（本文と取り消しの履歴）、結果、続きのページ、CSV の取得、AI の生成 | すべて残る。走っている要求も止めずに続き、届いた結果はそのまま反映する |
| REST API の要求の欄、レスポンス、送信中の要求 | すべて残る。データを変えうる送信を、画面の切り替えで止めないためである |
| ⌘↵ | フォーカスのあるエディタだけが受けるので、隠れた画面には届かない |

この作りは、「画面を条件で描き分けない」という決まりの上に成り立つ。
条件で描き分けると、タブを切り替えただけで送信中の要求が `stale` になり、結果が画面に出なくなる。
CLAUDE.md の「非同期の処理」にこの決まりを足し、タブを切り替えても送信の結果が出ることをテストで押さえる。

## 送信の流れ

### 作り

`RestProvider` は、送信用の `useTask`（ignore）を1つ持つ。
本体は、Send を押した時点の要求の写し（メソッド、パス、ヘッダー、ボディ）を受け取り、`api.rest` を呼んで結果を返すだけにする。

状態は reducer（`src/web/rest/restState.ts`）に持たせ、表の行をそのまま単体テストにする。

| 状態 | 中身 |
| --- | --- |
| `result` | `idle`、`response`（レスポンス）、`error`（送れなかった）、`unknown`（結果が分からない）のいずれか。どれも、送った要求の写しを一緒に持つ |
| `confirming` | 確認を待っている要求の写しと、確認の理由 |
| `launchNotice` | `--rest` で開いたときの案内を出すか |

写しは、Send を押した時点の下書きから作る。メソッドがボディを取らない（`methodTakesBody` が偽）なら、欄に残っているボディを写しに含めない。ボディを書いたあとで GET に変えたときに、ボディ付きの GET を送ってサーバーに断られないためである。

送信中かどうかは、`useTask` の `running` だけで判定し、reducer には持たない。

要求の欄の下書き（メソッド、パス、ヘッダーの行、ボディ）は `RestProvider` の状態に置く。
ボディは CodeMirror が持つ（SOQL のエディタと同じ）。
SOQL の `claimEditorText` と同じ規則で sessionStorage に保存し、同じ組織のまま再読み込みしたときだけ戻す。

### データを変えうる要求か

画面で、要求がデータを変えうるかは、`src/web/rest/changes.ts` の `restMayChangeData(method, path)` の1か所だけで決める。
GET 以外のメソッドと、パスが `/services/apexrest/` で始まるか Tooling API の `executeAnonymous` を含む GET を、データを変えうるとみなす。
この結果は、本番の確認、キャンセルを出すか、⌘↵ で送るか、送信の失敗を「結果が分からない」とみなすかに使う。
サーバーは、この判定によらず、`/rest` のすべての要求を送り直さない（「送り方」）。

### 確認するかどうか

実行の前に確認のダイアログを出すかは、`src/web/rest/confirm.ts` の純粋な関数 `needsConfirm(request, { isProduction, history })` だけで決める。
次のどれかに当たれば確認する。

- 本番の組織で、データを変えうる要求である。
- 実行履歴に、同じ要求で「応答待ち」か「不明」の記録がある。実行履歴はサーバーにあるので、再読み込み、組織の切り替え、別のブラウザのタブのあとでも確認が出る。

同じ要求とは、メソッド、パス、ボディ（写しに含めたもの）が文字どおり一致するものである。ヘッダーは比べない。
本番かどうかは、`OrgContext` の `isProduction`（一覧から消えた組織も本番として扱う）を使う。
確認は、押した時点の値で決める。

### 状態と遷移

| いまの状態 | 出来事 | 次の状態、見せるもの |
| --- | --- | --- |
| 待機 | Send（確認が要らない） | 送信中。下書きの写しを本体に渡す |
| 待機 | Send（確認が要る） | 確認中。本番なら「本番の組織 `<エイリアス>` で `<メソッド> <パス>` を実行します」、結果が分からない記録があれば「同じ要求の前の送信は、結果が分かっていません。Salesforce で確かめてから送ってください」を出す。キャンセルが先にフォーカスを取る |
| 確認中 | 実行 | 写しで送信を始める。確認を待つ間に下書きが変わっても、送るのは写しである |
| 確認中 | キャンセル、Esc | 待機。何も送らない |
| 確認中 | 実行の二度押し | 2回目は ignore で `stale` になる。描画を待たずに判定するので、二重に送らない |
| 送信中 | Send、⌘↵、連打 | 何もしない。ボタンは押せなくし、`useTask` も ignore で捨てる |
| 待機 | ⌘↵（データを変えうる要求） | 送らない。「データを変えうる要求は Send ボタンで送ります」と、ボタンの横に短く出す |
| 送信中（データを変えない要求） | キャンセル | 実際に止めたとき（`cancel` が真）だけ結果を空にする。「Salesforce の側の処理は止まらない」と注記する |
| 送信中（データを変えうる要求） | なし | キャンセルを出さない。「応答まで待ちます（最長 `<待つ時間>` 秒）」と出す |
| 送信中 | 応答（Salesforce が返したステータスによらない） | 待機。`result` をレスポンスにする。API 使用量を反映し、実行履歴を取り直す |
| 送信中 | `ORG_AUTH_ERROR` | 待機。結果の位置に再ログインのコマンドを出す。`/rest` がこのエラーを返すのは、送る前にトークンを取れなかったときと、Salesforce がセッション切れ（`INVALID_SESSION_ID`）と答えたときだけで、どちらも Salesforce は要求を処理していない |
| 送信中 | `BAD_REQUEST`（サーバーの検査で断った）、`SF_CLI_NOT_FOUND` | 待機。結果の位置か案内で出す。Salesforce には送っていないので、実行履歴にも残らない |
| 送信中 | `SALESFORCE_TIMEOUT`、`SALESFORCE_UNREACHABLE` | 待機。`result` を「結果が分からない」にし、「Salesforce の側で処理が終わっている場合があります。Salesforce か実行履歴で確かめてから送り直してください」と出す。データを変えない要求でも同じ文を出す（読むだけなので、送り直しても害はないが、出し分けない） |
| 送信中 | `SF_CLI_ERROR`、`INTERNAL_ERROR` | データを変えうる要求なら「結果が分からない」、そうでなければエラーとして出す（送ったあとで失敗した場合がある） |
| 送信中 | セッション切れ、sfbench のサーバーが止まった | 帯で案内する。データを変えうる要求なら、`result` を「結果が分からない」にもする |
| 送信中 | `ORG_NOT_FOUND` | `handleOrgError` に任せる |
| 送信中 | タブの切り替え | そのまま続く |
| 送信中 | 組織の切り替え、再読み込み、タブを閉じる | 画面の要求は `stale` になる。サーバーは送信を続け、結果を実行履歴に書く。戻ってくると、実行履歴に結果か「応答待ち」が出る |
| どれでも | 中止した要求や、組織を切り替えたあとに届いた応答 | 何もしない（`stale`） |
| 送信中 | 下書きの編集 | できる。結果の欄には、送った写しを出す |
| どれでも | 実行履歴の行を押す | 下書きを置き換える。送らない |
| 作業画面ができたとき（`--rest` の初期値あり） | | 下書きを埋め、案内を出す。送らない |
| 案内あり | 閉じるボタン、Send（確認が要るときは実行） | 案内を消す |

どの失敗を「結果が分からない」とみなすかは、`errors.ts` の `isOutcomeUnknown(error, changesData)` の1か所で決める。`changesData` は `restMayChangeData` の結果である。

### Salesforce が返した 4xx と 5xx

エラーではなく、レスポンスとして見せる。
サーバーは HTTP 200 の封筒で `{ status, headers, body }` を返し、画面はステータスを色分けして、本文をそのまま出す。
REST API の道具では、4xx の本文（`errorCode` と `message`）そのものが利用者の見たいものだからである。
例外にすると、サーバーの HTTP ステータスと Salesforce のステータスが混ざる（前提の1）。
4xx は Salesforce が受け取って断った結果であり、結果が分からない状態ではない。

401 は、本文の `errorCode` が `INVALID_SESSION_ID` のときだけトークンを取り直して送り直し、それでも同じなら `ORG_AUTH_ERROR` にする。
それ以外の 401（利用者の Apex REST が返したものなど）は、レスポンスとして返す（前提の5）。
この規則は `/rest` だけでなく、SOQL などほかの要求にも当てる。Salesforce がセッション切れを `INVALID_SESSION_ID` 以外で答える場面は見つかっていないからである。

## サーバーの `/rest`

### 要求

`POST /api/orgs/:user/rest`

```
{ method: 'GET' | 'POST' | 'PATCH' | 'PUT' | 'DELETE', path: string, headers?: Record<string, string>, body?: string }
```

- **メソッド**：HEAD は受け付けない。画面の仕様に要らず、`sf api request rest` で HEAD が動くかも確かめていないからである。
- **ボディ**：POST、PATCH、PUT のときだけ受け付け、GET と DELETE では 400 にする（前提の4）。どのメソッドがボディを取るかは、`shared/api.ts` の `methodTakesBody` で定義する。サーバーがこれで検査し、画面は同じ関数でボディの欄を押せなくする。ボディは文字列のまま送り、JSON として解析し直さない。上限は、ほかの要求と同じ 5 MB である。
- **パス**：16 KB まで。`assertSalesforcePath` で検査し、検査に使った `URL` の `pathname + search` を、`fetch` と `sf api request rest` のどちらの経路でも送る。検査したものと送るものを同じにするためである。同じオリジンの絶対 URL が貼り付けられたときも、パスとクエリ文字列だけが送られる。
- **ヘッダー**：名前と値は、Node 標準の `http.validateHeaderName` と `http.validateHeaderValue` で検査する（名前は HTTP の token の文字だけ、値に CR、LF、NUL を含まない）。数は50まで、合計 16 KB まで。名前は小文字にそろえてから扱う。`authorization`、`cookie`、`host`、`content-length`、`connection`、`transfer-encoding`、`te`、`trailer`、`upgrade`、`keep-alive`、`expect`、`proxy-` で始まる名前は 400 で拒む。既定の `accept: application/json` と、ボディがあるときの `content-type: application/json` に、利用者のヘッダーを小文字の名前で重ねるので、利用者の値が既定を上書きする（前提の6）。`authorization` は、利用者のヘッダーを重ねたあとで最後に付ける。検査が漏れても上書きされないようにするためである。

### 応答

成功（Salesforce が応答したとき）は 200 で次を返す。

```
{ id, status, headers: Record<string, string>, body: string, bodyOmitted?: 'binary' | 'tooLarge', size, elapsedMs, apiUsage }
```

- `body` は Salesforce が返した生の文字列で、整形は画面が行う。
- `content-type` が JSON、テキスト、XML のどれでもないときは、本文を返さず `bodyOmitted: 'binary'` にする（ファイルの本文など）。20 MB を超えるときは `bodyOmitted: 'tooLarge'` にする。上限は、読み終えてから比べるのではなく、読みながら数えて打ち切る。
- 応答のヘッダーは、`set-cookie` だけを除いて返す。Salesforce の標準の応答はトークンを含まない。利用者の Apex REST がセッション ID を返す場合は、利用者のコードの問題として受け入れる（画面はもともと、トークンと同じ権限で API を呼べる）。
- `id` は、実行履歴の記録の id である。

失敗は、ほかの API と同じ `errorResponse` の形で返す（`BAD_REQUEST`、`ORG_AUTH_ERROR`、`SALESFORCE_TIMEOUT`、`SALESFORCE_UNREACHABLE`、`SF_CLI_ERROR`、`ORG_NOT_FOUND`）。
`/rest` は `SALESFORCE_ERROR` を返さない。

### 送り方

`OrgClient` に、400 以上でも例外を投げない `requestRaw` を足し、`request` はその上に作り直す。
経路の切り替え、401 での取り直し、送り直さない判定は、両方で同じものを使う。

`/rest` から送る要求には、メソッドによらず `changesData: true` を付ける（前提の3）。
そのため、REST API の画面の GET も、ネットワークが途中で切れたときに `sf api request rest` で自動では送り直さず、`SALESFORCE_UNREACHABLE` を返す。
送り直してよいかの判定は、これまでどおり `salesforce.ts` の `mayChangeData` の1か所で行う。

`sf api request rest` の経路が 3xx のリダイレクトを追い、`Authorization` を付けたまま別のオリジンへ送らないかを、4a の実装の最初に確かめる。
追うなら、`/rest` の要求はこの経路を使わず、`fetch` が使えるまでエラーを返す（`fetch` の経路は `redirect: 'manual'` で追わない）。
トークンが漏れ、任意の URL を中継することになるからである。

画面の接続が切れても、Salesforce への要求は止めない。
止めると、「途中で止めた」という新しい、結果の分からない状態ができるからである。

ログには、1つの要求につき `rest <メソッド> <パス（クエリ文字列を除く）> <ステータスかコード> <所要時間>` を書く。
クエリ文字列（`q=` の SOQL を含みうる）、ボディ、ヘッダーの値は書かない。

## 実行履歴

### 置き場所と書き方

実行履歴は、`~/.sfbench/rest-history/<ユーザー名>.json` に置く。
ファイル名の作り方と権限（600 と 700）は、最近のクエリと同じである。
最近のクエリとは形も残す規則も違うので、ファイルを分ける。
書くのは、サーバーの `/rest` の処理だけである。

```
{ id, method, path, headers?, body?, bodyOmitted?, sentAt, bootId, outcome }
```

`outcome` は、`{ state: 'pending' }`、`{ state: 'done', status, elapsedMs }`、`{ state: 'unknown', reason }` のどれかである。

- 検査を通って Salesforce へ送る直前に、`pending` で書く。応答が届いたら、同じ id の記録を書き換える。
- 送らなかったと分かるもの（検査の失敗、トークンを取れなかった、`SF_CLI_NOT_FOUND`）は書かない。Salesforce がセッション切れと答えた `ORG_AUTH_ERROR` は、Salesforce が処理していないので、記録を消す。それ以外の失敗では記録を消さず、「不明」に書き換える。
- 読み込み、書き換え、書き出しは同期の処理で行う。Node の1つのスレッドの中では割り込まれないので、同じ組織への要求が重なっても壊れない（最近のクエリと同じ作法）。
- 書き込みに失敗しても、ログに警告を出して送信は続ける。そのときは記録が残らないので、応答の `id` は空にする。終わったときの書き換えで記録が見つからなければ、足さずに捨てる。
- 組織ごとに100件まで残す。同じ要求でもまとめない。POST を2回送った事実を消さないためである。

読むときに、記録ごとに形を確かめ、壊れた記録は捨てる。
`pending` の記録の `bootId` がいま動いているサーバーと違えば、「sfbench が止まったため不明」として返す。
サーバーが止まって残った `pending` を、いつまでも応答待ちとして見せないためである。

### 残すもの

| 中身 | 扱い |
| --- | --- |
| レスポンスの本文 | 残さない。レコードの中身そのものだからである |
| 要求のボディ | 32 KB までなら残し、超えたら `bodyOmitted` にする。利用者が書いたもので、最近のクエリに条件の値が残るのと同じ程度と見る |
| 利用者が付けたヘッダー | 残す。`Authorization` と `Cookie` は入口で拒むので、記録には入らない。独自の API キーのような値は平文で残る |
| パス | クエリ文字列も含めて残す |

### 画面

左の一覧の各行に、メソッド（色は `tokens.css` の変数）、パス、時刻、ステータスか「応答待ち」「不明」の印を出す。
行を押すと、下書きに読み込む（送らない）。
取り直すのは、作業画面ができたとき、送信が終わったとき、再読み込みのボタンを押したときである（`useTask` の replace）。
取り直しに失敗したときは何も出さず、一覧は前のまま残す（最近のクエリと同じ）。

## `--rest` の起動時の指定

```
sfbench --rest <パス> [--method <メソッド>] [--body '<json>' | --body-file <ファイル>]
```

- メソッドは `--method` で渡し、省けば GET にする。Node の `parseArgs` は1つのオプションに値を2つ取れないので、design.md の `--rest <method> <path>` の形をやめ、オプションを分ける。
- CLI の入口で、メソッド（5つのどれか、大文字にそろえる）、パス（`/services/` で始まる）、ボディ（POST、PATCH、PUT のときだけ、JSON として解析できること）を検査する。`--run` や `--query` と一緒に使ったら、エラーで終える。
- `--body-file` は、Windows のシェルで JSON を引用符で囲む手間を省き、AI のエージェントから使いやすくするために置く。ファイルを読むのは CLI の入口で、サーバーには中身を渡す。
- 組織が決まらない（`-o` がなく、sf CLI の既定の組織もない）ときは、エラーで終える。データを変えうる要求を、どの組織に入れるかを利用者に選ばせないためである。
- `LaunchOptions` に `rest?: { method, path, body? }` を足す。`/api/launch` の形は、項目を足すだけなので、「バージョンをまたいで変えない契約」を守る。
- 画面では、`orgState.ts` の `select` の遷移が、届いた `rest` を作業画面の初期値（`seed.rest`）に変える。`--org` の組織を選んだときだけ渡し、ほかの組織を選んだときは捨てて、「コマンドラインの REST API の要求は `<名前>` の組織用なので、入れていません」と案内する。`--org` の組織が一覧になかったときも同じである。
- 案内（「コマンドラインから入力しました。データを変更しうるので、送信していません。確かめてから Send を押してください」）は、どのメソッドでも出す。閉じるボタンか、最初の Send で消す。

## 判定の置き場所

| 判定 | 置き場所 |
| --- | --- |
| 送り直してよいか | `salesforce.ts` の `mayChangeData`。`/rest` は常に `changesData: true` を付ける |
| どのメソッドがボディを取るか | `shared/api.ts` の `methodTakesBody`。サーバーが検査し、画面は同じ定義で欄を押せなくする |
| パスが `/services/` で始まるか | `shared/api.ts` の `isServicesPath`（サーバーと CLI）。オリジンの比較はサーバーの `assertSalesforcePath` だけ |
| 通してよいヘッダー | サーバーの `src/server/rest.ts` だけ。画面は 400 のエラーを出すだけ |
| 画面で、要求がデータを変えうるか | `src/web/rest/changes.ts` の `restMayChangeData` だけ |
| 本番の組織か | `orgs/production.ts` と `OrgContext` の `isProduction` |
| 実行の前に確認するか | 画面の `src/web/rest/confirm.ts` の `needsConfirm` だけ（本番かと、実行履歴の記録から決める） |
| 送ったあとの失敗が「結果が分からない」か | 画面の表示は `errors.ts` の `isOutcomeUnknown`、記録はサーバーの store（`bootId` と `outcome`）。送り直しの確認は、記録の方だけを見る |
| トークンを取り直して送り直すか | `salesforce.ts`（401 で本文が `INVALID_SESSION_ID` のときだけ） |
| `--rest` を入れる組織 | `orgState.ts` の `select` の遷移 |
| 送信中か | REST API の送信の `useTask` の `running` だけ |
| 組織が切り替わったか | 作業画面の `key` だけ |

本番の確認はサーバーでは強制しない。
本番かどうかの判定（組織の要約による）が画面にあり、サーバーでも強制すると判定が二重になるからである。

## 検討した案

物差しは、正しさ（二重に送らないか、結果が分からないまま送り直させないか）、自前のコードの量、取り込む大きさ、保守の手間である。

### 送信の結果の追い方

| 案 | 中身 | 正しさ | コード | 大きさ | 保守 |
| --- | --- | --- | --- | --- | --- |
| 採った案 | サーバーが送る直前に「応答待ち」で実行履歴に書き、終わったら書き換える。データを変えうる送信ではキャンセルを出さない | 組織の切り替え、再読み込み、タブを閉じる、サーバーが止まる、のどれでも、実行履歴に結果か「応答待ち」「不明」が残る（書き込みに失敗したときと、サーバーが2つ動いたときを除く）。送り直しの確認も、この記録で判定する | 中（store に100から150行。`bootId`、読むときの読み替え、上限、切り詰め、id による書き換え） | 増えない | 最近のクエリと同じ作法 |
| 送信をサーバーのジョブにし、画面が結果を取りに行く | `POST /rest` は id をすぐ返し、画面は `GET /rest/:id?wait=1` で結果を待つ。サーバーは終わった結果を、期限と件数の上限付きでメモリに持つ | 採った案に加えて、再読み込みや別のタブからも、レスポンスの本文まで取り戻せる。「応答待ち」も自動で終わる | 多（待つ API、メモリの結果の管理、画面の待ち合わせ） | 増えない | サーバーにメモリの状態が増える。区切り4の範囲には要らない。採った案の記録の上に、あとから足せる |
| 機能を減らす：送信中は組織の切り替えを止める | 終わったときだけ実行履歴に書き、データを変えうる送信の間は、組織の切り替えを押せなくする。`beforeunload` で警告する | 再読み込みやタブを閉じたときに、警告を無視されると記録が残らない。別のタブからの送り直しは防げない | 少から中（実行中を作業画面の外へ知らせる配線） | 増えない | web.md で退けた「実行中は切り替えを止める」配線が戻る。流れを足すたびに配線が要る（採った案は、この配線を持たないよう、タブの印も出さない） |
| さらに減らす：実行履歴を作業画面のメモリだけに持つ | サーバーは書かない | 組織を切り替えると何を送ったか消え、送り直しを防げない | 少 | 増えない | 仕様の「実行履歴」が再読み込みで消える |
| 既存のライブラリ：TanStack Query の `useMutation` | 画面の送信をライブラリに任せる | サーバーの側で続く送信の結果が分からない問題は解けない。`signal` も受け取らない | 中 | 約13 KB | web.md「検討した案」で退けた理由がそのまま当てはまる |

### タブの切り替え

| 案 | 正しさ | コード | 弱点 |
| --- | --- | --- | --- |
| 採った案：両方の画面を残し、`hidden` で隠す | 走っている要求が切り替えで止まらない | 少 | 両方の画面がメモリに残る。隠れている間の CodeMirror と TanStack Virtual の大きさの測り直しは手で確かめる |
| 機能を減らす：選んでいない画面を外す | データを変えうる送信が、切り替えだけで `stale` になる（実行履歴には残る）。SOQL の結果と取り消しの履歴は消える | 最少 | タブを替えて一目見るだけで、作業が消える |

### ボディの欄とレスポンスの表示

| 案 | 判断 |
| --- | --- |
| 採った案：ボディは CodeMirror に `@codemirror/lang-json` を足して色分けする（取り消し、Tab の字下げ、整形は `JSON.parse` と `JSON.stringify`）。レスポンスは、読み取り専用の CodeMirror に同じ色分けで出し、コピーのボタンを付ける | `devDependencies` に足し、ビルド時に取り込むので、利用者の実行時の依存は増えない。取り込む大きさは数 KB で、JSON を読む画面なので色分けの効果が大きい |
| 取り込み済みのパッケージだけで作り、レスポンスは `<pre>` で出す | 依存を足さないが、大きな JSON が読みにくい |
| JSON を木の形で見せるライブラリ | 取り込む大きさに対して、得るものが小さい |
| textarea | 最少だが、SOQL のエディタと操作感がそろわず、Tab の扱いを自分で書くことになる |

レスポンスの本文が 2 MB を超えるときは、整形も色分けもせずに先頭の 200 KB だけを出し、全体はコピーで取り出せるようにする。

### 4xx の扱い

レスポンスとして見せる案を採った（「Salesforce が返した 4xx と 5xx」）。
例外にする案は、ステータスの取り違えが起きることと、REST API の道具として見たいものが見えなくなることから採らなかった。

この文書の案は、別のサブエージェントに問題と制約だけを渡して出させた案をもとにしている。
最初に考えていた「送信中は組織の切り替えを止める」案（上の「機能を減らす」）より、組織の切り替え、再読み込み、タブを閉じるのどれにも効くので、そちらを採った。
設計のレビューで、401 での送り直し、ヘッダー名の大文字と小文字、GET に変えたあとのボディ、`sf api request rest` のリダイレクトの4つの穴を見つけ、上のとおりに塞いだ。送り直しの確認を画面のメモリでなく実行履歴で判定すること、タブの印を出さないことも、このレビューで決めた。

## 既知の弱点

- **本番の確認はサーバーが強制しない。** 画面の判定が抜けると、そのまま送られる。
- **データを変えない要求のキャンセルは、待つのをやめるだけである。** Salesforce とサーバーの処理は続き、API の呼び出しも消費する。
- **GET でもデータを変えうる要求は、パスでしか見分けられない。** Salesforce に新しい API が増えても一覧は足されず、本番の確認に漏れる。送り直しの禁止は、すべての要求に効かせている。
- **REST API の画面の GET は、ネットワークが切れても `sf api request rest` で送り直さない。** 利用者が Send を押し直す。
- **`sf api request rest --include` の出力の解析は、JSON の本文を前提にしている。** テキスト、HTML、XML の本文を読み違えないか、記録した出力でテストする。
- **大きな応答は、20 MB までサーバーと画面のメモリに丸ごと載る。**
- **同じ名前のヘッダーを2つ送れない**（名前から値への対応で持つため）。
- **実行履歴のファイルには、要求のボディ（レコードの値を含みうる）が残る。** Windows では権限の指定が効かない。1件の送信につき2回、ファイルを書き直す。
- **同じサーバーが動いている間は、「応答待ち」は実行履歴を取り直すまで変わらない**（ジョブにして結果を取りに行く案を採らないため）。
- **サーバーが2つ動いたとき**（古いサーバーが止まらず、別のサーバーを起動したとき）、一方が他方の「応答待ち」を「不明」と見せ、同じファイルへの書き込みが一方で消えうる。まれである。
- **ログのパスに、レコードの値が入りうる**（`/services/apexrest/customer/<メールアドレス>` など）。クエリ文字列は除くが、パスは除けない。
- **ユーザー名からファイル名を作るときに衝突しうる**（`a+b@x` と `a_b@x`。最近のクエリと同じ、既存の弱点）。
- **2つの画面を描いたまま残すので、メモリを使う。**
- **開発中だけの事象として、** Fast Refresh で `--rest` の初期値がもう一度入る（SOQL と同じ。送信はしないので害はない）。
- **2つのブラウザのタブで同じ組織に送ると、** 結果はそれぞれのタブにしか出ない。実行履歴には両方が残る。
