# sfbench の AI にツールを呼ばせる仕組みの技術設計

AI に組織のメタデータをツールで読ませながら、SOQL、REST API のリクエスト、匿名 Apex を組ませる仕組みの設計を書く。
区切り7で REST API と Apex に作り、0.1.0 の公開の前に SOQL もこの仕組みにそろえる（「SOQL をそろえる」）。
設定、提供元ごとの呼び出しの基本、画面の状態の作りは [ai.md](ai.md) にある。

## 範囲

| PR | 内容 |
| --- | --- |
| 7a | `AiContext` を、どの画面でも使う部分（`useAiSession`、`AiInput`、`ProposalFrame`、`DiffText`）と SOQL の部分に分ける。ふるまいは変えない |
| 7b | ツールを呼ばせるサーバーの仕組み（`POST /api/orgs/:user/ai/agent`）と、REST API の画面の AI |
| 7c | Apex の画面の AI |
| 7d | SOQL の AI をこの仕組みにそろえ、2段の流れを消す（「SOQL をそろえる」） |

区切り7の時点では、SOQL の AI は2段の流れ（画面がオブジェクトを選ばせてから項目を渡す）のまま残した。
公開の前に、利用者と相談して7d でそろえる。

## 利用者と決めたこと

| # | 問い | 決めたこと |
| --- | --- | --- |
| 1 | AI に渡す情報 | AI にツールを呼ばせ、オブジェクトの検索と項目の一覧を、必要なときに必要な分だけ読ませる。REST API のエンドポイントやリクエストの形、Apex の文法は、AI の知識に任せる |
| 2 | 「AI で直す」を置くか | 置く。REST API は 4xx と 5xx のレスポンス、Apex はコンパイルエラーと実行時の例外に出す |
| 3 | 直すときに送るエラーの中身 | 押したときだけ、エラー文をそのまま送る。送る情報に「エラー文」の札を出す |
| 4 | 前の実行結果を AI に渡すか | 「前の結果」の札で、押したときだけ送る（既定はオフ）。REST API は直前のレスポンスのステータスと本文、Apex は直前の結果と `USER_DEBUG` の行。どちらも先頭の 16,000 文字まで |
| 5 | SOQL の AI もツールの仕組みにそろえるか | そろえる。2段の流れと同じ頼みごとの組で測り、劣らないことを確かめてからマージする。公開後に AI の作りを変えないよう、0.1.0 の前に行う |

## 前提にする事実

検証用の Developer Edition 組織（オブジェクト1,555個）のメタデータで、試作のスクリプトを Claude Haiku 5.5 と Claude Sonnet 5.5 に動かして確かめた。

1. **REST API のエンドポイントと Apex は、AI の知識で書ける。** `/limits`、`/sobjects/Opportunity`、`/query`、`/composite/tree`、Apex の SOQL、DML、`Schema` の describe を、ツールなしの知識で正しく書いた。
2. **組織ごとのものは、ツールで読ませれば正しく使う。** 「Lプロジェクト」は、オブジェクトを名前で探して `Project__c` にたどり着いた。ラベルが重なるもの（標準の Quote とカスタムの Quote__c がどちらも「見積」）では、一方で書き、説明でもう一方に触れた。
3. **今日の日付を渡さないと、日付の要望を書けない。** 「今月末」が `<UNKNOWN>` になった。今日の日付とタイムゾーンを指示に入れると直った。
4. **指示がないと、複雑な要求の形を崩すことがある。** 「取引先と取引先責任者をまとめて作成」で、Haiku はパスを崩し、子のレコードを落とした。「1回の呼び出しで済むいちばん簡単なエンドポイントを選ぶ」「パスが実在するか確かめる」と指示すると直った。
5. **ツールを必ず呼ばせる指定（`tool_choice: any`）を受け付けないモデルがある**（Claude Sonnet 5.5）。`auto` で、試した要望ではすべてツール（答えを出す `submit` を含む）を呼んだ。
6. **1回の依頼で、AI の呼び出しは2〜4回、3〜12秒、送った量は2〜20 KB だった。**
7. **オブジェクトの一覧をそのまま渡すと大きすぎる**（1,555個）。名前かラベルに語を含むものを探すツールにすると、1回の結果は数 KB に収まった。
8. **OpenAI の推論するモデルは、Chat Completions ではツールを使えない。** 最初 Chat Completions で書いたところ、gpt-6-luna で「推論の指定があるとツールを使えない。Responses API を使う」と断られた。Responses API に書き換えると、試した5件（REST API の生成と修正、Apex の生成と修正）がすべて通った。AI の呼び出しは1回の依頼で1〜3回、4〜17秒だった。

## サーバー

### `POST /api/orgs/:user/ai/agent`

```
{ task: 'generateSoql' | 'fixSoql' | 'generateRest' | 'fixRest' | 'generateApex' | 'fixApex', input: { ... }, apiVersion?: string }
→ 200 { output: { ... } }
```

組織の経路の下に置く。
ツールの結果は、サーバーがその組織から読むからである。

- サーバーは、指示、ツール、答えの形をタスクごとに組み、AI とツールのやり取りを繰り返す（`src/server/ai/agent.ts`）。
- AI がツールを呼んだら、サーバーが実行して結果を返す。答えを出すツール（`submit`）を呼んだら、その引数を出力として検査し、返す。
- ツールを呼ばずに文で答えたら、「submit で答えてください」と1回だけ促す。2回目も呼ばなければ `AI_BAD_OUTPUT` にする。空の返事は会話に残さない（空の返事のあとに促すと、提供元が 400 で断るため）。
- 1回の依頼で、ツールの呼び出しは8回まで（「大きなオブジェクト」）、ツールの結果は合わせて 100 KB までにする（項目の多いオブジェクトの describe は、それだけで数百 KB になりうる）。大きなオブジェクトの読み方は「ツール」にある。上限に達したら、そのことをツールの結果として伝え、答えを出させる。それでも答えなければ `AI_BAD_OUTPUT` にする。この促しは、submit を呼ばせる促しとは別に1回ある。誤って何度も読む場合と、料金に備えるためである。
- 待つ時間は、いまの AI と同じく、全体で300秒にする。画面が要求を切ったら、AI への要求を止め、次のツールの読み込みもしない（読み込み中の1回は終わるまで待つ）。
- ログには、タスク、AI の呼び出しの回数、ツールの呼び出しの回数、所要時間だけを書く。要望、ツールの結果、AI の出力は書かない。

### ツール

| ツール | 引数 | 結果 |
| --- | --- | --- |
| `findObjects` | `keywords: string[]` | API 名かラベルに語を含むオブジェクト（大文字と小文字を区別しない）を、1行に1つ「API 名 ラベル」で、50個まで |
| `describeObject` | `name: string` | オブジェクトの子リレーションと項目。収まる大きさに合わせて、3つの形のどれかで返す（下の「大きなオブジェクト」） |
| `findFields` | `object: string`、`keywords: string[]` | そのオブジェクトの項目と子リレーションのうち、名前かラベルに語を含むものを、省かずに返す |
| `submit` | タスクごとの答えの形 | なし（これで終わる） |

- 項目は、JSON ではなく1項目1行の短い形で返す。更新も作成もできない項目には `readonly` の印を付ける。選択リストは有効な値を50個まで載せ、残りがあれば「(+N more)」と書き添える。子リレーションは項目より前に置く。

```
Object Opportunity (商談)
Child relationships:
OpportunityLineItems -> OpportunityLineItem
Fields:
Name string 商談名
StageName picklist フェーズ [Prospecting, Closed Won, Closed Lost]
AccountId reference(Account) relationship Account 取引先 ID
CreatedDate datetime readonly 作成日
```

#### 大きなオブジェクト

ツールの結果は、一覧の途中で黙って切らない。
切ると、切られた項目や子リレーションが AI から見えず、AI はそれがあることも知らないまま、推測で書くか、目的を満たさないクエリを組むからである。
代わりに、詳しい情報が収まらない分は `findFields` で探させる。

1回のツールの結果は、40 KB と、全体の予算（1回の依頼で 100 KB）の残りの小さいほうまでにする。
項目の多いオブジェクトを最初に読んでも、親や子のオブジェクトを読む分が残るようにするためである。

`describeObject` は、この上限に収まる形を、次の順に選ぶ。

1. **すべて**：子リレーションと、すべての項目を上の1行の形で。
2. **型まで**：子リレーションと、すべての項目の名前、型、参照先、関係名。ラベルと選択リストの値は省き、「ラベルと選択リストの値は省いた。`findFields` で探せば省かずに返す」と書き添える。
3. **名前だけ**：子リレーションの名前と、すべての項目の名前を、カンマで区切って並べる。「型、ラベル、選択リストの値は省いた。`findFields` で探す」と書き添える。1項目20バイトほどなので、900項目でも 20 KB 前後に収まる。

名前だけでも収まらないのは、全体の予算の残りが少ないときである。
そのときは一覧を返さず、「ツールの結果の上限が近いので、この一覧は返せない。手持ちで答える」と伝える。

1つの依頼の中で、すでに返したオブジェクトをもう一度 `describeObject` で読もうとしたら、どの形で返していても、送り直さずに「上にある。省いた部分は `findFields` で探す」と答える。
同じ文を送り直しても、新しく分かることはなく、予算だけが減るからである。
読めなかったオブジェクトと、上限が近くて一覧を返せなかったオブジェクトは、返したものに数えない。

`findFields` は、語に合う項目と子リレーションを、いつも1行の形で省かずに返す。

- 照らすのは、項目の API 名とラベル、子リレーションの関係名と子オブジェクトの名前である。大文字と小文字を区別せず、名前空間を省く設定のときは、省いた名前と付いた名前のどちらでも照らす。
- 名前が語と一致するものを先に、名前かラベルに語を含むものを後に並べる。項目の名前を正しく渡されたときに、その項目が先頭に来るようにするためである。
- 50行か、1回のツールの結果の上限に達したら止め、残りの数を書いて、語を絞るよう案内する。
- オブジェクトがないとき、語が空のときは、そのことを返す。上限が近くて1行も返せないときは、`describeObject` と同じく、手持ちで答えるよう伝える。

ツールの呼び出しは、1回の依頼で8回までにする。
大きなオブジェクトを使うクエリでは、オブジェクトを探す、読む、項目を探す、親のオブジェクトを読む、その項目を探す、と5回ほど呼ぶことがあり、区切り7の6回では足りなくなりうるからである。
料金は、回数ではなく、ツールの結果の予算（100 KB）で抑える。

検討した案は次のとおりである。

| 案 | 中身 | 大きなオブジェクトで残ること | 採否 |
| --- | --- | --- | --- |
| 上限で行を切る（7d の最初の作り） | 収まらない分を切り、切ったことを書き添える | 切られた項目と子リレーションに、AI がたどり着けない。どの上限で切ったかで続きを読んでよいかが変わり、AI への説明が食い違った（コードレビューの指摘） | 採らない |
| 上限を設定で変えられるようにする | 大きな組織の利用者が上限を上げる | 上げれば起きにくくなるが、上げた上限を超えるオブジェクトでは、切る案と同じことが残る。上げるほど、毎回の往復で送る量と料金が増える。利用者が上げる必要に気づくのは、誤った提案を見たときである | 採らない |
| 上限を超えるときに利用者に確かめる | 生成の途中で確認のダイアログを出し、続けるか選ばせる | サーバーで続いている AI とのやり取りを止めて、画面の答えを待つ仕組みが要る（今は1回の要求で答えまで返す）。利用者には、何 KB を送るかで選ぶ手がかりがない | 採らない |
| `describeObject` はいつも名前だけを返し、詳しい情報はいつも探させる | 形が1つで、返した形を覚えなくてよい | 小さなオブジェクトでも、毎回探す往復が要る。測った頼みごとの組の大半（項目が100以下）で、時間と回数が増える | 採らない |
| 項目の名前を渡して、その項目を省かずに読む（`fields` 引数） | 名前を確実に引ける | 名前を知らない項目には使えない。`findFields` で名前が一致するものを先に並べれば、同じことができる | `findFields` に含める |
| 採った案：収まる形で返し、収まらない詳しい情報は探させる | 上のとおり | すべての項目と子リレーションの名前は、上限が近い場合を除いて必ず見える。詳しい情報は探せば届く。ただし AI が案内に従って探すことが前提で、従わずに推測で書く余地は残る。大きなオブジェクトでは往復が1〜2回増える。選択リストの値は1項目50個までで、それを超える値（国や州の一覧など）には届かない | 採る |

- describe は、サーバーのキャッシュを使う（`OrgRegistry.describeGlobal`、`describeObject`）。画面の API バージョンがあれば（SOQL と Apex の画面で選んだもの）、そのバージョンで読む。REST API の画面にはバージョンの選択がないので、組織の最新で読む。オブジェクトの describe のキーには `object:` を付け、オブジェクトの一覧のキー（`global`）と取り違えないようにする。
- 名前は、REST API と Apex では、名前空間を省く設定に従わず、いつも名前空間の付いた名前で渡す。REST API と Apex では、名前空間を省けないからである。SOQL では省くことがある（「SOQL のときのツール」）。
- ツールの結果に入るのはメタデータ（オブジェクトと項目の名前、型、ラベル、選択リストの値）だけで、レコードの値は入らない。

### 答えの形

| タスク | 渡すもの | 答え |
| --- | --- | --- |
| `generateRest` | 要望、いまの要求（メソッド、パス、ボディ。送る札が押されているとき） | `{ method, path, body, explanation }` |
| `fixRest` | 送った要求、レスポンスのステータスと本文 | 同じ |
| `generateApex` | 要望、いまのコード（送る札が押されているとき） | `{ code, explanation }` |
| `fixApex` | 実行したコード、コンパイルエラーか例外の文と行 | 同じ |

- 指示には、組織の最新の API バージョン、今日の日付と利用者のタイムゾーン（ブラウザの `Intl` から）、画面の表示言語を入れる。
- REST API の指示には、前提の4で効いた2つの指示を入れる。値が要望にないときは例の値を入れ、説明でそれと分かるように書かせる。
- `method` は REST API の画面のメソッドの一覧に限る。`path` は `/services/` で始まるものに限る（REST API の画面と同じ検査）。外れたら `AI_BAD_OUTPUT` にする。

### 提供元ごとの呼び出し

ツールの形と、やり取りの続け方は、提供元ごとのファイルに閉じ込める。

- Anthropic：`tools`（どれも `strict: true`）、`tool_choice: { type: 'auto' }`。応答の `tool_use` を実行し、`tool_result` を返す。
- OpenAI：Responses API（`/v1/responses`）の `tools`（`function`、`strict: true`）、`tool_choice: 'auto'`。応答の `function_call` を実行し、`function_call_output` で返す。Chat Completions を使わないのは、推論するモデル（gpt-6-luna など）が Chat Completions ではツールを受け付けないからである（利用者の「接続を確かめる」で分かった）。OpenAI 側に会話を残さないよう `store: false` にし、前の返事（暗号化された推論を含む）をこちらから送り返して続ける。

### 接続を確かめる

設定画面の「接続を確かめる」は、ツールを1回呼ぶ小さな依頼で確かめる（組織は読まず、ツールは何も見つけない）。
ツールの呼び出しに対応しないモデル（手元の小さなモデルなど）を、画面で初めて知ることがないようにするためである。
区切り7では SOQL 用のツールなしの依頼も送っていたが、7d で SOQL もツールを使うようになったので、1回にした。

## 画面

- REST API の画面は要求の欄の上に、Apex の画面はコードの欄の上に、AI の入力欄（`AiInput`）を置く。
- 送る情報の札は次のとおりである。
  - 「組織のメタデータ（必要なときに AI が読む）」は、いつも送るので押せない札にする。
  - 「いまの要求」（REST API）と「いまのコード」（Apex）は、押して切り替える札にする。SOQL の「エディタの内容」と同じく、外した状態は作業画面がある間続く。
  - 直すときは「エラー文」の札を出す（利用者と決めたこと 3）。
- 直前の実行の結果があれば、「前の結果」の札を出す（利用者と決めたこと 4）。前の結果を使って次の処理を組みたい（作ったレコードの Id で続けて更新するなど）ことがあるからである。前の結果にはレコードの値がそのまま入るので、既定はオフにし、押したときだけ送る。札にマウスを載せると、レコードの値が入りうることを出す。
  - REST API：直前のレスポンスのステータスと本文。
  - Apex：直前の結果（成功、コンパイルエラーの文、例外の文）と、デバッグログの `USER_DEBUG` の行だけ。ログ全体は長く、`System.debug` で出した値のほうが次の処理の手がかりになるためである。
  - どちらも先頭の 16,000 文字までにする（`src/web/ai/cut.ts`）。
  - 札だけでは気づかれにくいので、結果の欄の見出しにも「この結果を使って AI に頼む」を置く。利用者が前の結果を使いたいと思うとき、見ているのは結果の欄だからである。押すと札をオンにし、たたんだ欄を開き、AI の入力欄にカーソルを移して見える位置までスクロールし、AI の欄を一瞬強調する（動きを減らす設定では強調の枠だけ）。入力欄の案内文も「この結果を使ってやりたいことを書く」に変える。押したあとのボタンは「✓ この結果を AI に渡します」になり、もう一度押すと送らない。
  - 前の結果を送って生成したら、札はオフに戻す。新しく実行して結果が変わったときもオフに戻す。レコードの値を、選んだ1回の依頼のほかに送らないためと、選んだのとは別の結果を送らないためである。
- 生成中は「考えています…」と Cancel を出す。ツールを何回呼ぶかは前もって分からず、サーバーは途中の段階を返さないので、段階は分けない。
- 提案カードが出ている間は、上の段を高くする（REST API の画面の上の段は高さが決まっていて、カードがボディの欄を押しつぶすため）。
- 提案カード（`ProposalFrame`）は、「破棄」と「置き換え」だけにする。データを変えうる操作なので、AI の出力を読んでから実行してもらう（ai.md「範囲」）。
  - REST API：メソッドとパスを出し、ボディはいまのボディとの差分（`DiffText`）で出す。置き換えると、メソッド、パス、ボディを書き換える（ヘッダーは変えない）。
  - Apex：いまのコードとの差分を出す。置き換えると、コードを取り消せる1回の変更として書き換える。
- 「AI で直す」は、REST API ではレスポンスが 4xx か 5xx のときに、Apex ではコンパイルエラーか例外のときに、結果の欄に出す。REST API のレスポンスの本文は、先頭の 16,000 文字までを送る（エラーページの HTML などで、サーバーが受け付ける量を超えないため）。送るのは、そのとき送った要求か実行したコードで、いまの欄の内容ではない（SOQL の「AI で直す」と同じ）。

## SOQL をそろえる

7d で、SOQL の AI を2段の流れからこの仕組みに移す。
AI の作りを1つにし、ツールの読み方、上限、提供元ごとの呼び出しを1か所で直せるようにするためである。

### 測った2段の流れ

移す前に、2段の流れを頼みごとの組で測った。
組は、sfbench-demo（英語のサンプルデータと、カスタムオブジェクト `Invoice__c`（ラベル Invoice）を入れたスクラッチ組織）の18件と、名前空間 `cuhacker` のスクラッチ組織の4件である。
18件の内訳は、生成15件（単純な条件、日付リテラルと親の項目、集計、サブクエリ、選択リストの値、カスタムオブジェクト、日本語の要望、エディタに書きかけのクエリがある場合、Tooling API）と、AI で直す3件である。

| モデル | そのまま実行できた | 意図どおりのオブジェクト | 生成1件の時間 | 生成1件の入力トークン |
| --- | --- | --- | --- | --- |
| Claude Haiku 5.5 | 22件中22件 | 22件中19件 | 2.5〜12.8秒（多くは3〜5秒） | 約1万7千〜2万 |
| gpt-6-luna | 22件中21件 | 22件中19件 | 3.4〜15.1秒 | 約7千〜1万 |

意図どおりでなかった3件は、どちらのモデルも、カスタムの `Invoice__c` を指す要望で標準の `Invoice`（請求書）を選んだものである。
`chooseObjects` に渡す一覧では、両方が「Invoice」の1行ずつで並び、どちらが組織で使われているかを見分ける手がかりがない。
入力トークンの大半は、1,400個ほどのオブジェクトの一覧である。

### 検討した案

| 案 | 中身 | 正しさ | コードの量と保守 | 採否 |
| --- | --- | --- | --- | --- |
| 2段の流れのまま残す | いまのまま | 上の表のとおり。同じラベルの取り違えは、一覧の行に印を足せば減らせる | AI の作りが2つ残る。提供元ごとに、ツールなしの呼び出し（Anthropic の構造化出力、OpenAI の Chat Completions）とツールの呼び出しの両方を保守する | 採らない。利用者の目的（作りを1つにする）を満たさない |
| 2段の流れをサーバーに移し、各段を `submit` だけの会話で呼ぶ | 読むツールは渡さず、オブジェクトの一覧と項目をこれまでどおり渡す。答えだけを `submit` で受ける | 2段の流れと同じ（流れは変わらず、呼び方だけが変わる）。上の表の数字がそのまま当てはまる | ツールなしの呼び出しは消える。ただし、オブジェクトの一覧と項目を組んで予算に収める処理（`objectInfo.ts` に当たるもの）と、`chooseObjects` の指示と検査がサーバーに残り、指示の組は SOQL だけ別になる。入力トークンも減らない | 採った案が測って劣ったときの代わりにする |
| 生成だけ移し、AI で直すは2段のまま | 直すときは FROM のオブジェクトの項目だけで足りることが多い | 移した生成と同じ | ツールなしの呼び出しと、画面での項目の組み立て（`objectInfo.ts`）が残る | 採らない。作りが2つ残る |
| 採った案：生成も直すも、ツールの仕組みに移す | 下のとおり | 測って確かめる（「測り方」） | ツールなしの呼び出し、`chooseObjects`、画面の項目の組み立て、`/api/ai/generate` が消え、コードは減る | 採る |

別のサブエージェントに問題と制約だけを渡して出させた案も、同じ「既存の仕組みに乗せ、2段の流れを消す」案だった。
その案から、カスタムオブジェクトの印（同じラベルの取り違えに効く）と、SOQL で引けないオブジェクトを検索から除くことを取り入れた。
設計のレビューで、移すと失うものも挙げられた。
途中の段階（オブジェクトの選択、項目の読み込み、生成）の表示と、ツールを呼べないモデルで SOQL の AI が使えなくなることである（「既知の弱点」）。
公開前なので、2段の流れで使っていた利用者はいない。

### タスク

`POST /api/orgs/:user/ai/agent` に、`generateSoql` と `fixSoql` を足す。

| タスク | 渡すもの | 答え |
| --- | --- | --- |
| `generateSoql` | 要望、エディタの内容（送る札が押されているとき）、左の一覧で開いているオブジェクトの名前（手がかり）、Tooling API か | `{ soql, explanation }` |
| `fixSoql` | 実行したクエリ、エラー文、FROM のオブジェクトの名前（画面が `fromObjectOf` で読んだもの）、Tooling API か | 同じ |

- `apiVersion` は、ほかのタスクと同じく要求の上の段に置く。SOQL の画面で選んだバージョン（直すときは、失敗した実行のバージョン）である。
- 指示には、今日の日付とタイムゾーン、Tooling API で実行すること（そのとき）、2段の流れの指示にあった SOQL の規則（その場で実行できる形にする、文字列は一重引用符、日付リテラルを使う、親は関係名、子はサブクエリ）を入れる。
- 開いているオブジェクトは、名前だけを手がかりとして渡し、項目は渡さない。要望が別のオブジェクトについてなら、そちらで組むよう指示する（ai.md「Generate の流れ」で、項目を渡すと開いているオブジェクトに引きずられた）。
- 直すときは、FROM のオブジェクトを、AI が `describeObject` で読むのと同じ形と上限で最初の依頼に入れ、ツールの結果の予算に数える。2段の流れと同じ情報から始め、AI の往復を1回減らすためである。入れたものは `describeObject` で返したものとして扱い（「大きなオブジェクト」）、指示では「`describeObject` が返したものと同じ。省いた部分があれば `findFields` で探す」と伝える。FROM の解析は画面にあるものを使い、サーバーは受け取った名前をオブジェクトの一覧に照らすだけにする。一覧にない名前（存在しないオブジェクトがエラーの原因のとき）は、項目を入れずに始める。
- 同じラベルのオブジェクトが複数見つかったときは、項目や要望の手がかりからどちらを指すかを考えて選び、説明でもう一方に触れるよう指示する。標準とカスタムのどちらを優先するかは決めない。どちらを使う組織もあるからである。
- エディタの内容と直すクエリは5万文字までにする。AI とのやり取りの往復ごとに送り直されるからである。判定はサーバーだけで行い、超えていたら AI を呼ばずに `AI_INPUT_TOO_LONG`（400）を返し、`details` にどちらが長いか（`editor` か `soql`）を入れる。画面は、エディタの内容なら「エディタの内容が長すぎて AI に送れない。札を外す」、クエリなら「クエリが長すぎて AI に送れない」という画面の言語の文に変える。判定を1か所にするのは、上限を変えるときに画面とサーバーがずれないためである（CLAUDE.md「判定の置き場所」）。本文全体の上限（200 KB の `PAYLOAD_TOO_LARGE`）とは別のコードにし、REST API と Apex の画面に SOQL の案内が出ないようにする。エラー文は、REST API と Apex と同じく、画面が先頭の 16,000 文字までにして送る。
- 答えの検査では、`soql` が空でなく、`SELECT` で始まることを確かめる。外れたら `AI_BAD_OUTPUT` にする。SOQL の画面は SOSL（`FIND`）を実行しないので、通さない。

### SOQL のときのツール

`findObjects` と `describeObject` を、タスクが SOQL のときは次のように変える。

- **Tooling API**：Tooling API のときは、`/tooling/sobjects/` を読む。1つの依頼の中では、オブジェクトの一覧も describe も同じ API（Tooling API かどうか）と同じバージョンで読む。読み先は依頼の初めに1つ決め、ツールの呼び出しごとに変えない。
- **describe の取得とキャッシュ**：describe のエンドポイント（画面の左の一覧が使うもの）と AI のツールが、`OrgRegistry` の同じメソッド（`describeGlobal`、`describeObject`）で取得とキャッシュを行う。これまではキーを組む式が2か所にあり、AI の側だけ Tooling API の区別がなかった。
- **名前の照らし合わせ**：`describeObject` に渡された名前は、オブジェクトの一覧と、大文字と小文字、名前空間の有無を区別せずに照らし、一覧の綴りで読む。一覧にない名前には「ない」と返す。REST API と Apex でも同じにする（綴りの違うキーで同じ describe を2回読まないため）。比べ方は `src/shared/namespace.ts`（画面と共通）の関数を使う。
- **名前空間**：クエリの実行に名前空間の指定（`Sforce-Call-Options: defaultNamespace`）を付けるときだけ、ツールの結果の名前（オブジェクト、項目、参照先、関係名、子オブジェクト）から組織の名前空間を外す。付けるかどうかは、サーバーの1つのメソッドが決め、クエリの実行と AI のツールの両方がそれを使う。設定の「名前空間を省く」がオフのとき、組織に名前空間がないとき、組織の名前空間を読めなかったときは、外さない。外した名前で書いたクエリが、指定なしで実行されて失敗しないようにするためである。設定は画面から送らず、サーバーが保存している値を読む。REST API と Apex は、これまでどおり名前空間の付いた名前で渡す。
- **検索の結果**：SOQL のときは、SOQL で引けないオブジェクト（`queryable` が偽）を除き、めったに引かない共有、履歴、フィード、変更イベントのオブジェクトを後ろに回す。2段の流れの `objectList` はこれらを除いていたが、AI に名前を推測させない指示と合わせると、`LoginHistory` のように引くことのあるオブジェクトにたどり着けなくなるからである。カスタムオブジェクトには `custom` の印を付ける。この印は REST API と Apex でも付ける。
- **開いているオブジェクト**：画面から受け取った名前を、その依頼の読み先（Tooling API かどうか）の一覧に照らし、あれば一覧の綴りで指示に入れる。なければ入れない（Tooling API に切り替える前に開いていたオブジェクトなど）。

### 画面

- 生成中の段階は、REST API と Apex と同じく「考えています…」の1つにする。オブジェクトの選択、項目の読み込み、生成の3段階は、サーバーが途中を返さないので出せなくなる。
- 送る情報の札は、「組織のメタデータ（必要なときに AI が読む）」（押せない札）と「エディタの内容」（押して切り替える札）にする。開いているオブジェクトを手がかりにすることは、これまでどおり固定の札の title で示す。
- 提案、「置き換えて実行」、最近のクエリへの要望の記録は変えない。提案は、送ったときの Tooling API と API バージョンを持ち、置き換えるとそれに切り替える。
- 画面の状態と遷移は、`useAiSession` の表（ai.md「画面の状態と遷移」）のまま変わらない。変わるのは、本体が呼ぶ API と段階の名前だけである。

### 消すもの

- サーバー：`tasks.ts`（`chooseObjects`、`generateSoql`、`fixSoql` の指示と検査）、`generate.ts`（待つ時間の定数は `agent.ts` に移す）、`POST /api/ai/generate`、`anthropic.ts` と `openai.ts` のツールなしの呼び出し（OpenAI の Chat Completions を含む）。
- 共通の型：`shared/api.ts` の `AiTask`、`AiTaskRequest`、`AiOutput`、`ChooseObjectsOutput`。
- 画面：`src/web/ai/objectInfo.ts`（一覧と項目の組み立てと予算）、`api.aiGenerate`、`AiContext` の2段の本体、`aiState.ts` の SOQL の段階、段階の文言、`aiTooLong` と `aiNoObjects` の文言。
- テスト：`src/server/ai/ai.test.ts` のうち2段の流れのもの、`src/web/AiFlow.test.tsx` のうち2段の流れを前提にしたもの（新しい流れのテストに書き直す）。
- 文書：ai.md の「タスク」「送る量」「Generate の流れ」「AI で直す」のうち2段の流れの説明と、「進め方」の 3a の行。この文書と ai.md の両方に同じ流れを書かないよう、ai.md からはこの文書を指す。
- 設定画面の「接続を確かめる」は、ツールを呼ぶ小さな依頼の1回だけにする。SOQL もツールを使うので、ツールなしの依頼で確かめる意味がなくなる。

### 失敗したとき

REST API と Apex と同じである（「サーバー」の上限、促し、待つ時間、中止）。
SOQL に固有なのは次のことだけである。

- Tooling API のときに、AI が Tooling API にないオブジェクトを読もうとしたら、ツールの結果で「ない」と返し、AI に探し直させる。
- 答えが SOQL の形でなければ（`SELECT` で始まらない）、`AI_BAD_OUTPUT` にし、入力欄の下に出す。
- 組織の名前空間を読めなかったときは、名前空間を外さずに続ける（「名前空間」）。AI は名前空間の付いた名前で書き、そのクエリは指定なしでも実行できる。
- 生成してから実行するまでの間に「名前空間を省く」を切り替えると、提案のクエリが実行で失敗することがある。名前空間を外した提案のあとで設定をオフにしたときである。まれなので、失敗したら「AI で直す」で直してもらう（「既知の弱点」）。

### 測り方

2段の流れと同じ頼みごとの組を、同じ組織、同じモデル（Claude Haiku 5.5 と gpt-6-luna）で流し、次を比べる。
組には、同じラベルで標準のほうが正解になる件を足す（sfbench-demo にカスタムの `Order__c`（ラベル Order）を足し、標準の注文を指す要望と、カスタムを指す要望を1件ずつ入れる）。
名前空間のある組織の件は、別に集計する。

- そのまま実行できた件数と、意図どおりのオブジェクトを使った件数。どちらも2段の流れ以上であること。
- 生成1件の時間。中央値が2段の流れの2倍を超えないこと。
- 入力トークンの合計、ツールの呼び出しの回数、上限に達した件数。

AI の答えは揺れるので、Claude Haiku 5.5 では、2段の流れと新しい流れをそれぞれ3回流し、件数は3回の合計で比べる。
gpt-6-luna は料金が高いので、それぞれ1回とする。
同数のときは「劣らない」とみなす。

下回ったら、指示とツールの結果の形を直して測り直す。
直しても下回るなら、数字を添えて利用者と相談する。

### 測った結果

測り方のとおりに流した結果は次のとおりである（2026-10-18、組は sfbench-demo の20件と名前空間のある組織の4件）。
「意図どおりのオブジェクト」は、各件に決めた正解のオブジェクト（`Invoice__c` を指す要望なら `Invoice__c`）がクエリに入っているかで数えた。

| モデルと流れ | そのまま実行できた | 意図どおりのオブジェクト | 生成の時間（中央値） | AI で直す時間（中央値） | 1件の入力トークン |
| --- | --- | --- | --- | --- | --- |
| Claude Haiku 5.5、2段（3回） | 60件中60件 | 60件中45件 | 3.1秒 | 1.3秒 | 約1万6千 |
| Claude Haiku 5.5、ツール（3回） | 60件中60件 | 60件中60件 | 4.6秒 | 2.7秒 | 約6千7百 |
| gpt-6-luna、2段（1回） | 20件中19件 | 20件中15件 | 4.3秒 | 2.2秒 | 約6千6百 |
| gpt-6-luna、ツール（1回） | 20件中20件 | 20件中18件 | 5.5秒 | 6.5秒 | 約3千9百 |
| 名前空間のある組織、Claude Haiku 5.5、2段（3回） | 12件中12件 | 12件中12件 | 4.0秒 | 1.4秒 | 約1万4千 |
| 名前空間のある組織、Claude Haiku 5.5、ツール（3回） | 12件中11件 | 12件中12件 | 6.0秒 | 2.4秒 | 約5千7百 |
| 名前空間のある組織、gpt-6-luna、2段（1回） | 4件中3件 | 4件中4件 | 5.7秒 | 1.6秒 | 約7千6百 |
| 名前空間のある組織、gpt-6-luna、ツール（1回） | 4件中3件 | 4件中4件 | 7.2秒 | 5.6秒 | 約3千2百 |

- 意図どおりのオブジェクトは、どちらのモデルでも増えた。2段の流れが外したのは、カスタムの `Invoice__c` を指す要望で標準の `Invoice` を、カスタムの `Order__c` を指す要望で標準の `Shipment` を選んだものである。ツールの仕組みでは、Claude Haiku 5.5 は全件で正しいオブジェクトを使い、gpt-6-luna は `Invoice` を2件で選んだ。標準のほうが正解の件（標準の `Order`）は、どちらの流れでも正しかった。
- 実行できなかった件は、2段の流れの gpt-6-luna の1件が Salesforce の一時的な 503 である。名前空間のある組織の1件（ツールの Claude Haiku 5.5 の3回のうち1回、両方の流れの gpt-6-luna）は、自動採番の `Name` で `GROUP BY` したクエリで、Salesforce が「グループ化できない項目」として断った。項目の一覧にグループ化できるかの印はなく、2段の流れでも同じ誤りが出た。「AI で直す」で直せる。
- 生成の時間の中央値は、どの組み合わせでも2段の流れの2倍に収まった。AI で直す時間は、gpt-6-luna で約3倍になった。項目を最初から渡しても、gpt-6-luna はツールを2〜3回呼んでから答えたためである（Claude Haiku 5.5 は0〜1回）。
- 入力トークンは、オブジェクトの一覧を送らなくなった分、半分以下になった。

測り方の基準（実行できた件数と意図どおりのオブジェクトがどちらも以上）に対し、名前空間のある組織の Claude Haiku 5.5 だけが実行できた件数で1件下回った。
下回った1件は2段の流れでも起きる誤りで、作りの違いによるものではないと判断し、移すことにした。

## 既知の弱点

- **ツールを呼べないモデルでは、SOQL の AI も使えない。** 2段の流れのときは、SOQL だけは使えた。「接続を確かめる」で前もって分かる。
- **AI で生成してから実行するまでの間に「名前空間を省く」をオフにすると、提案のクエリが失敗することがある。** 「AI で直す」で直せる。
- **開いているオブジェクトが読み先の一覧にないとき（Tooling API に切り替えた直後など）、札の説明は手がかりとして伝えると出すが、実際には渡さない。** 手がかりが渡らないだけで、AI はオブジェクトを探して組む。

- **ラベルが重なるオブジェクトでは、AI が意図と違う方を選ぶことがある。** 説明で触れさせるが、気づくのは利用者である。
- **ツールの呼び出しが不安定なモデルでは使えない。** 「接続を確かめる」で前もって分かるようにする。
- **AI の知識が古いと、新しいエンドポイントや Apex の新しい書き方を知らない。**
- **エラー文を送ると、そこに入ったレコードの値も AI の提供元に送られる。** 押したときだけ送り、札で示す（利用者と決めたこと 3）。
- **REST API の提案カードの差分は、ボディを書き換えたあとに古いままのことがある。** ボディの欄の変更では画面を描き直さないので、カードはほかの理由で描き直されたときに「変わった」と気づく。置き換えはボディ全体を書き換えるので、置き換えで消える内容を読み違えることはあっても、送る内容は提案のとおりである。
