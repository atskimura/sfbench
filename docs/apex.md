# sfbench 匿名 Apex の画面の技術設計

区切り5で作る匿名 Apex の画面の設計を書く。
画面の見た目は [screens.md](screens.md)、サーバーの API は [design.md](design.md)、画面全体の作りは [web.md](web.md) にある。
データを変えうる操作の流れは、REST API の画面（[rest.md](rest.md)）に倣い、同じところは「rest.md と同じ」と書く。

## 範囲

区切り5は、次の PR に分ける。

| PR | 内容 |
| --- | --- |
| 5a（サーバー） | `sf apex run` の呼び出しと出力の解析、`POST /api/orgs/:user/apex`、`GET /api/orgs/:user/apex/history`、実行履歴の保存、`--apex` と `--apex-file`、テスト |
| 5b（画面） | ヘッダーの Apex のタブ、作業画面に3つめの画面を置く作り、Apex の画面（エディタ、実行、確認、結果、デバッグログ、実行履歴）、`--apex` の初期値と案内 |

次のものは区切り5に入れず、あとの PR にする。

- **Apex の AI**：REST API と同じく、先に `AiContext` を、どの画面でも使う部分と画面ごとの部分に分ける必要がある（利用者と決めた順番で、表での編集のあとに作る）。
- **選んだ部分だけの実行**（Developer Console の Execute Highlighted）と、Apex の補完。

Apex の実行は、いつもデータを変えうる操作として扱う。

## 前提にする事実

sf CLI 2.153.5 で、組織のデータを変えない Apex（`System.debug` と、0で割る例外）を実行して確かめた。

1. **`sf apex run -f <ファイル> --json` は、結果とデバッグログを JSON で返す。**
   - 成功：`{ status: 0, result: { success: true, compiled: true, line: -1, column: -1, logs: '<デバッグログ全文>', ... } }`
   - コンパイルエラー：`{ status: 1, name: 'executeCompileFailure', data: { compiled: 'False', compileProblem: '...', line: '1', column: '9', logs: '' } }`（値は文字列）
   - 実行時の例外：`{ status: 1, name: 'executeRuntimeFailure', data: { compiled: 'True', exceptionMessage: 'System.MathException: Divide by 0', exceptionStackTrace: 'AnonymousBlock: line 1, column 1', logs: '...' } }`
   - 1回に数秒かかる（sf CLI の起動の分）。
2. **`sf apex run` の中身は、SOAP の Apex API の executeAnonymous である**（`@salesforce/apex-node`）。DebuggingHeader を付けてログを受け取るので、組織に TraceFlag を作らなくてよい。セッション切れの応答（500 で `INVALID_SESSION_ID`）を受けたときだけ、認証を取り直して1回送り直す（実行されていないので二重にならない）。下で使う HTTP の部品（jsforce）は、POST を送り直さない（送り直すのは GET、PUT、HEAD、OPTIONS、DELETE だけ）。ほかの失敗はすべて `unexpectedExecuteCommandError` で包んで返す。
3. **Tooling API の REST の executeAnonymous は、デバッグログを返さない。** design.md の「Tooling API の executeAnonymous で実行」は、この文書で書き直す。
4. **`-d`（デバッグレベル）は新しい sf CLI にしかない。** 2.149.9 にはなく、渡すと起動前のエラーになる。省いたときの既定はどの版も `DEBUGONLY` である。
5. **通信の失敗は、送る前か送ったあとかを見分けられない汎用のエラーになる**（`unexpectedExecuteCommandError`）。
6. **失敗したときの JSON の `message` には、実行時の例外の文やコンパイルエラーの文がそのまま入る。** 例外の文には、レコードの値が入りうる。
7. **組織は環境変数 `SF_TARGET_ORG` で渡せる。** sf CLI の既定の組織を設定していない環境で、`SF_TARGET_ORG=kimura-demo` を付けて実行し、ログの実行ユーザーが kimura-demo の管理者になることを確かめた。
8. **DEBUGONLY のデバッグログ**は、先頭の設定の行と `Execute Anonymous:` の行のあとに、実行の開始、`USER_DEBUG`（`System.debug` の出力。複数行の値は次の行に続く）、上限の使用量（SOQL の回数など）、実行の終わりが並ぶ。
9. **sf CLI 自身のログ（`~/.sf/sf-<日付>.log`）には、実行時の例外の文が残る。** sfbench の側では止められない。
10. **匿名 Apex の長さの上限は、約32,000文字である。** 31,000文字は実行でき、33,000文字は Salesforce が「Script too large」のコンパイルエラーで断った。

## 実行の経路

`sf apex run` だけを使う。

サーバーの中は `runApex(username, code) → ApexRunResult` という関数で切り、経路を差し替えられるようにしておく。

- コードは `~/.sfbench/tmp/apex-<乱数>.apex` に権限 600 で書き、`sf apex run -f apex-<乱数>.apex --json` を実行する。引数は固定の文字列と英数字のファイル名だけで、終わったら消す。サーバーが落ちて残ったものは、起動時の `tmp/` の掃除で消える。組織は環境変数 `SF_TARGET_ORG` で渡す（前提の7）。
- 待つ時間は、設定の「Salesforce の応答を待つ時間」に、sf CLI の起動の分の余裕（15秒）を足したものにする。`runSf` の既定（60秒）には頼らない。時間切れで sf を止めても、Salesforce の側の実行は続く。時間切れ（`SfTimeoutError`）は、REST の sf CLI の経路と同じく `SALESFORCE_TIMEOUT` に写し替える。

出力の解析は `src/server/sf/apexRun.ts` の1か所だけで行い、記録した出力（2.149.9 と 2.153.5）でテストする。
分ける順番は次のとおりで、この順番を変えない。

1. `status: 0` なら成功。
2. `name` が `executeCompileFailure` か `executeRuntimeFailure` なら、`data` を読んで結果にする（文字列の値は、ここで型をそろえる）。Apex の中で OAuth のコールアウトを試して失敗すると、例外の文に `invalid_grant` が入る。3より先に判定しないと、これを組織の認証切れと取り違え、実行履歴の記録を消し、再ログインのあとに確認なしで二重に実行させてしまう。
3. それ以外の名前（実行の前に起きる失敗）にだけ、`isAuthErrorMessage` を当てて `OrgAuthError` にする。
4. 残りは、実行したか分からない失敗（`ApexRunError`）とする。実行していないと分かる名前を細かく分けることはせず、すべて「不明」に倒す。

`ApexRunError` は、sf CLI の失敗の名前と、画面に出す文を持つ。
サーバーのログには名前だけを書き、文は書かない（前提の6のとおり、文に例外の文が入りうるため）。
`errorResponse` は、この例外では `SfCliError` のように文をログに書かず、`SF_CLI_ERROR` として画面にだけ文を返す。
知らない形の出力を「不明」に倒したことは、ログに名前で残し、sf CLI の版が変わったことに気づけるようにする。
- `-d` は渡さない（デバッグレベルを選ばせるかは、利用者に決めてもらう）。

## 応答の形

`POST /api/orgs/:user/apex` は `{ code: string }` を受け取る。
成功、コンパイルエラー、実行時の例外は、どれも Apex が受け付けた結果なので、200 で次を返す（REST の 4xx をレスポンスとして返すのと同じ考え方）。

```
{
  id: string | undefined,            // 実行履歴の記録の id
  result: 'success' | 'compileError' | 'runtimeError',
  compileProblem?: string, line?: number, column?: number,
  exceptionMessage?: string, exceptionStackTrace?: string,
  logs: string, logsOmitted?: 'tooLarge',
  elapsedMs: number,
}
```

`line` と `column` は、sf CLI の `data.line` と `data.column`（匿名ブロックの中の位置）を使う。呼んだクラスの中で例外が起きても、匿名ブロックの中で呼んだ行を指す。
実行していない失敗と、実行したか分からない失敗は、ほかの API と同じエラーの形で返す（「実行の流れ」の表）。

## 画面の構成

配置は、SOQL と REST API の画面にそろえる。

- **上の段の左：エディタ**。CodeMirror で Apex を色分けする。実行ボタンとコピーを置く。整形は置かない（Apex の整形には、パーサーか外部の道具が要るため）。
  エディタの本文は、SOQL のエディタと同じ規則で sessionStorage（`sfbench.apexDraft`）に保存し、同じ組織のまま再読み込みしたときだけ戻す。`--apex` の初期値があれば、それを優先する（`claimEditorText` と同じ）。
- **上の段の右：実行履歴**。SOQL の最近のクエリ、REST API の実行履歴と同じ位置と幅にし、たためるようにする。各行に、コードの最初の空でない行、時刻、結果の印（成功、コンパイルエラー、例外、応答待ち、不明）を出す。押すとエディタに読み込む（取り消せる1回の変更として入れる。実行はしない）。
- **境目のボタンで、上の段をたたむ。** たたんでいる間は、実行ボタンとコードの1行目の1行を出す。開閉は `sfbench.apexPanels` に覚える。
- **下の段：結果を横幅いっぱいに出す。**
  - 見出しの行に、結果の印、所要時間、実行した時刻を出す。
  - コンパイルエラーは、`compileProblem` と「1行目 9列」のボタンを出す。押すとエディタのその位置へ移る。実行時の例外は、例外の文とスタックトレースを出し、行へ移れるようにする。実行したあとでエディタのコードが変わっていれば、「実行したあとでコードが変わっています」と添える。
  - 例外で終わっても、すでに行ったコールアウトなど、外部への影響は戻らないと注記する。
  - デバッグログは、読み取り専用の CodeMirror に出す。既定は全文で、`System.debug` を入れていなくても、実行の開始と終わりや上限の使用量が見え、実行したことが分かる。
  - ログの上には、検索の欄と「USER_DEBUG だけ」の切り替え、コピー、ダウンロード（ブラウザの中で `.log` を作る。サーバーを通さない）を置く。「USER_DEBUG だけ」の切り替えは、ブラウザに覚える。
  - 検索は、ログ全体を見せたまま、一致した箇所をすべて色付けし、↑↓（または Enter）で前と次の一致へ移り、「3/12」のように何件目かを出す。前後の行を見たまま探せるようにするためである。一致した件だけに絞る機能は置かない（使ってみて要るなら、同じ欄に足す）。色付けと移動は CodeMirror の装飾で自前に書き、検索の部品は取り込まない。
  - 実行中は、結果の位置に「実行しています。取り消せません（最長 N 秒）」と出し、キャンセルは置かない（上の段をたたんでいても見える）。
- **案内**：`--apex` で開いたときと、別の組織用で入れなかったときの案内を、上部に出す（rest.md と同じ）。

「USER_DEBUG だけ」の絞り込みは、行ではなく **ログの1件ごと**に行う。
時刻（`^\d{2}:\d{2}:\d{2}\.\d+ \(\d+\)\|`）で始まる行から、次の同じ形の行までを1件とする。
最初の時刻の行より前（設定の行と `Execute Anonymous:` の行）は、まとめて先頭の1件とし、「USER_DEBUG だけ」のときは出さない。
`System.debug` で出した複数行の値が、途中で切れないようにするためである。
この処理は `src/web/apex/log.ts` の純粋な関数にし、記録したログでテストする。

## 実行の流れ

作りは rest.md「送信の流れ」と同じである。

- `ApexProvider` は、実行用の `useTask`（ignore）と、実行履歴用の `useTask`（replace）を持つ。
- 本体は、実行を押した時点のコードの写しを受け取り、`api.apex` の結果を返すだけにする。
- `result`、`confirming`、`launchNotice` は reducer（`src/web/apex/apexState.ts`）に持たせ、表の行をそのまま単体テストにする。
- 実行中かどうかは、`useTask` の `running` だけで判定する。
- `result` は、`idle`、`response`（成功、コンパイルエラー、実行時の例外のどれか）、`error`（実行していない）、`unknown`（結果が分からない）のどれかで、実行した写しを一緒に持つ。
- `ApexProvider` は `RestProvider` に倣って別に書く。確認の理由を組み立てる部分と、reducer の形は共有する。失敗した結果を「`result` と、手元に入れる不明の記録」に変える部分も、REST と共通の純粋な関数にし、両方が同じテストを通るようにする。2つを1つの汎用のフックにまとめると、区切り4で固めた REST の流れを作り直すことになるので、区切り5ではしない。

| いまの状態 | 出来事 | 次の状態、見せるもの |
| --- | --- | --- |
| 待機 | 実行（確認が要らない） | 実行中。写しを本体に渡す |
| 待機 | 実行（確認が要る） | 確認中。理由を出す（下の「確認するかどうか」）。キャンセルが先にフォーカスを取る |
| 確認中 | 実行 | 写しで実行する |
| 確認中 | キャンセル、Esc | 待機。何もしない |
| 確認中、実行中 | 二度押し、連打、⌘↵ | 何もしない |
| 待機 | ⌘↵ | 実行しない。「Apex は実行ボタンで実行します」と短く出す |
| 実行中 | 成功、コンパイルエラー、実行時の例外 | 待機。`result` を `response` にし、実行履歴を取り直す |
| 実行中 | `ORG_AUTH_ERROR`、`SF_CLI_NOT_FOUND`、`BAD_REQUEST` | 待機。`error` にする。実行していないので「不明」にしない |
| 実行中 | `SALESFORCE_TIMEOUT`（sf を止めた）、`SF_CLI_ERROR`（分けられない sf の失敗）、`INTERNAL_ERROR`、sfbench に接続できない | 待機。`unknown` にし、手元の実行履歴の先頭に「不明」の記録を入れる（rest.md と同じ） |
| 実行中 | sfbench がセッションを入口で断った（401） | 帯で案内する。「不明」にはしない |
| 実行中 | `ORG_NOT_FOUND` | `handleOrgError` に任せる |
| 実行中 | タブの切り替え | 止めずに続ける |
| 実行中 | 組織の切り替え、再読み込み、タブを閉じる | 画面の要求は `stale` になる。サーバーは sf を止めずに続け、実行履歴に書く |
| どれでも | 遅れて届いた応答 | 何もしない（`stale`） |
| 実行中 | エディタの編集 | できる。結果の欄には、実行した写しで出す |
| 作業画面ができたとき（`--apex` あり） | | エディタを埋め、案内を出す。実行はしない |
| 確認中 | 組織の切り替え | 作業画面ごと作り直され、何も実行しない |
| どれでも | 実行履歴の行を押す | エディタに読み込む（取り消せる1回の変更）。実行しない |
| 案内あり | 閉じる、最初の実行 | 案内を消す |

### 確認するかどうか

`src/web/apex/confirm.ts` の純粋な関数だけで決める。
理由を組み立てる部分は、REST API と共有する関数（`confirmReasons`）にし、同じ実行かどうかの判定だけを画面ごとに持つ。

- 本番の組織である（Apex はいつもデータを変えうる）。
- 実行履歴に、同じコードの「応答待ち」か「不明」の記録がある。
- 実行履歴をまだ一度も読み込めていない。
- 実行履歴に、いま動いているサーバーで「応答待ち」の記録がある（コードが違っても）。結果が分からなかったあとに、コードを少し直してから実行し直すのはふつうの流れなので、同じコードかどうかだけでは、二重の実行を止められないからである（利用者に決めてもらう）。

同じコードとは、改行を LF にそろえたうえで、文字どおり一致するものである。
コードは実行履歴に全文を残す（下の「残すもの」）ので、REST API の `bodyOmitted` のような例外は要らない。

## 実行履歴

置き場所は `~/.sfbench/apex-history/<ユーザー名>.json` である。
書き方（実行の直前に「応答待ち」で書き、終わったら書き換える。`bootId` で、止まったサーバーの「応答待ち」を「不明」に読み替える）は rest.md「実行履歴」と同じで、REST と Apex で共通の関数にする。

```
{ id, code, sentAt, bootId,
  outcome: { state: 'pending' }
         | { state: 'done', result: 'success' | 'compileError' | 'runtimeError', line?, column?, compileProblem?, exceptionType?, elapsedMs }
         | { state: 'unknown', reason } }
```

- sf CLI を起動する直前に「応答待ち」で書く。書けなければ、実行しない（エラーとして返す）。Apex はいつもデータを変えうるので、記録のない実行を作らない（REST は書けなくても送るが、Apex ではしない）。
- 実行していないと分かるもの（検査の失敗、`SF_CLI_NOT_FOUND`、`OrgAuthError`）は記録を消す。それ以外の失敗は「不明」にする。
- 同じコードでもまとめない（利用者の選択による）。

### 残すもの

| 中身 | 扱い |
| --- | --- |
| コード | 全文を残す。サーバーが受け付ける長さは32,000文字まで（前提の10。Salesforce の上限に合わせる。超えたら 400 で断り、実行しない） |
| `compileProblem` | 残す。コードから生まれる文である |
| 例外 | 型（`System.DmlException` など、`:` より前）だけを残す。例外の文には、レコードの値が入りうる。`:` より前が型の形（`^[A-Za-z_][\w.]*$`）でなければ、何も残さない |
| デバッグログ | 残さない。ディスクにも sessionStorage にも書かず、`ApexProvider` の状態にだけ持つ。組織の切り替えと再読み込みで消える。`USER_DEBUG` にはレコードの中身がそのまま出るからである |

画面へ返すデバッグログは 20 MB まで（Salesforce のデバッグログの上限と同じ）とし、超えたら返さずに `logsOmitted: 'tooLarge'` にする。

ログ（`server.log`）には、`apex <結果かエラーの名前> <所要時間>` だけを書く。
コード、`compileProblem`、例外の文、デバッグログ、sf CLI のエラー文の全文は書かない。

## `--apex` の起動時の指定

```
sfbench --apex "<code>" | --apex-file <ファイル>  [-o <組織>]
```

- `--apex-file` は、`--body-file` と同じ理由で置く。Apex は文字列に `'` を使うのでシェルの引用符がそろえにくく、Windows ではコマンドラインの長さにも上限がある。2つは同時に指定できない。BOM は取り除く。
- CLI の入口で、空でないこと、長さの上限、`--query`、`--run`、`--rest` と一緒に使っていないこと、組織が決まることを検査する。
- `LaunchOptions` に `apex?: { code: string }` を足す。
- `orgState.ts` の `select` が、`--org` の組織を選んだときだけ作業画面の初期値（`seed.apex`）にする。ほかの組織を選んだときは入れずに案内する（rest.md と同じ）。
- 最初の画面を Apex にする。

## 判定の置き場所

| 判定 | 置き場所 |
| --- | --- |
| sf CLI の出力から、結果（成功、コンパイルエラー、例外）、実行していない失敗、不明を分ける | `src/server/sf/apexRun.ts` だけ（上の順番で） |
| 失敗したときの実行履歴の行方（消すか、不明にするか） | `server.ts` の `apexOutcomeOf` |
| 確認するか | `src/web/apex/confirm.ts`（共通の `confirmReasons` と、同じコードかどうか） |
| 本番か | `OrgContext` の `isProduction` |
| 画面の「結果が分からない」 | `errors.ts` の `isOutcomeUnknown(e, true)` |
| コードの長さの上限 | `shared/api.ts` の定数（サーバーと CLI が検査する） |
| `--apex` を入れる組織 | `orgState.ts` の `select` |
| ログの1件の区切りと「USER_DEBUG だけ」、検索の一致 | `src/web/apex/log.ts` |
| 実行中か | 実行の `useTask` の `running` |
| 組織が切り替わったか | 作業画面の `key` |

## 検討した案

### 実行の経路

| 物差し | 採った案：`sf apex run` だけ | SOAP の API を直接呼ぶ | 両方（SOAP を主、sf を代わり） | Tooling の REST で実行し、TraceFlag を作って ApexLog を取りに行く |
| --- | --- | --- | --- | --- |
| 正しさ | sf CLI がセッション切れのときだけ送り直す（実行されていないので安全）。分け方は sf CLI の名前に頼る | セッション切れ（500 と faultcode）を自分で判定する | 経路を送る前に決め、送ったあとは切り替えなければ、既存の `mayChangeData` の規則で足りる | 組織に TraceFlag と DebugLevel を作る（本番では設定データの変更になる）。ログができるのを待つ |
| 速さ | 1回に数秒 | 1秒未満と Apex の実行時間 | ふだんは速い | 呼び出しが増える |
| 自前のコード | 少（100行ほど） | 中（XML の組み立ては20行ほど。応答から数個の要素を正規表現で取り出すのが手間で、合わせて80〜120行） | 両方 | 中 |
| sf CLI の出力への依存 | ある（`data` の形、`name`、値が文字列であること） | ない（SOAP の Apex API の形に依存する。長く安定している） | 両方 | ない |
| トークンを扱えない環境（`SFBENCH_TRANSPORT=cli`） | 動く | 動かない（代わりの `api request rest` は XML を送れない） | sf に切り替わる | 動く |

採った理由は、トークンを扱えない環境でも動くこと、区切り5の範囲を小さくすることである。
正しさに大きな差はない。SOAP を直接呼ぶ案も、トークンの扱いは REST と同じ程度に守れる。
1回に数秒かかるのは弱点なので、`runApex` で切っておき、あとから SOAP を直接呼ぶ経路を「両方」の形で足せるようにする。
最初に考えていたのは「両方」だったが、別のサブエージェントの案で sf CLI の中身が同じ SOAP の呼び出しだと分かり、まず `sf apex run` だけにした。

実行をサーバーのジョブにし、結果を期限付きでメモリに持つ案もある。
Apex は1回に数秒以上かかり、実行中に再読み込みや組織の切り替えが起きやすい。デバッグログをディスクに残さないので、いまの設計では、再読み込みすると結果もログも戻らない。
メモリに持てば、ディスクに書かずに取り戻せる。区切り5には入れず、実行履歴の記録の上に、あとから足せる案として残す。

### Apex の色分け

| 案 | 判断 |
| --- | --- |
| 採った案：`@codemirror/language` の `StreamLanguage` で自前に書く（導入済み） | キーワードを大文字と小文字を区別せずに扱い、`'` の文字列、`[SELECT ...]` の SOQL、`@` の注釈、コメントを塗れる。80行ほどとテスト。取り込む大きさは増えない |
| `@codemirror/legacy-modes` の `clike` に Apex のキーワードを渡す | ほぼ同じ結果。大文字と小文字の区別と SOQL は自分で足す。数 KB 増える |
| `@codemirror/lang-java` | `'abc'` を文字のリテラルの誤りとし、`[SELECT]` も誤って解析する。Apex との差は埋められない |
| Monaco と Apex の言語サーバー | 最も正しいが、MB 単位で、依存の方針に合わない |
| 機能を減らす：色分けしない | 操作感が SOQL と REST API にそろわない |

### 機能を減らす案

- **実行履歴を作業画面のメモリだけに持つ**：再読み込みや組織の切り替えのあとで、結果が分からないまま実行し直させてしまう。採らない。
- **デバッグレベルを選ばせない**（`DEBUGONLY` に固定）：古い sf CLI でも動き、ログが小さく、作りが単純になる。利用者に決めてもらう。
- **ログの絞り込みを置かない**：`USER_DEBUG` を探す手間が大きく、この画面の価値が落ちる。「USER_DEBUG だけ」と文字の絞り込みの2つに絞り、カテゴリごとの切り替えや木の形の表示は作らない。

この文書の案は、別のサブエージェントに問題と制約だけを渡して出させた案をもとにしている。

## 既知の弱点

- **1回の実行に数秒かかる**（sf CLI の起動の分）。
- **sf CLI の出力の形に依存する。** 版が変わったら `apexRun.ts` を直す。2.149.9 と 2.153.5 の両方の出力を記録してテストする。
- **分けられない sf CLI の失敗は、すべて「不明」にする。** 実際には実行していない失敗でも、次の実行で確認が出る（安全な側に倒す）。
- **時間切れで止めるのは sf CLI だけである。** Salesforce の側の実行は続き、「不明」として残る。
- **`sf apex run` は `Sforce-Limit-Info` を返さないので、** ヘッダーの API 使用量は、Apex の実行では更新されない。
- **コードは、一時ファイルとして短い間ディスクに載り、実行履歴にも全文が残る。** Windows では権限の指定が効かない。
- **デバッグログは、再読み込みや組織の切り替えで消える**（漏らさないために決めた）。
- **本番の確認は画面にしかない。**
- **「最長 N 秒」は、sf CLI の待ち行列（同時に4つまで）にいた時間を数えない。** ほかの sf CLI の処理と重なると、表示より長く待つことがある。
- **sf CLI 自身のログに、実行時の例外の文が残る**（前提の9）。
- **行と列へ移る機能は、実行したあとでコードを編集すると、ずれる。**
- **sf CLI のプロセスは同時に4つまでなので、** ほかの sf CLI の処理と重なると待ち行列に入る。その間も実行履歴は「応答待ち」になる。
- **REST API から引き継ぐ弱点**：サーバーが2つ動いたとき、2つのブラウザのタブで実行したとき、ユーザー名からファイル名を作るときの衝突。
