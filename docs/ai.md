# sfbench AI で組む機能の技術設計

区切り3（AI で組む機能）の設計を書く。
決まっている方針は [design.md](design.md) の「AI で組む機能」に、画面の仕様は [screens.md](screens.md) の「AI の入力欄」「AI の提案カード」「設定」にあり、この文書はそれらをどう実装するかを決める。

## 範囲

区切り3で作るのは、SOQL を AI に組ませる機能である。

- 要望の文から SOQL を組む（Generate）
- 実行エラーになった SOQL を直す（Fix with AI）
- 提案カード（差分、説明、Discard、Replace、Replace & Run）
- 設定画面の AI の欄と、接続の確認（Test connection）
- 最近のクエリに、AI に頼んだ文を残す

REST API のリクエストと匿名 Apex を組ませる機能は、それぞれの画面と一緒に区切り4と5で作る。
この文書の仕組み（設定、提供元ごとの呼び出し、出力の形の検査、提案カード）は、そのときもそのまま使う。
ただし REST API と Apex では、提案カードに「反映して実行」を置かない。
データを変えうる操作なので、AI の出力を利用者が読んでから実行するようにするためである。

## 設定

### 保存する形

`~/.sfbench/settings.json` の `ai` に保存する。

```json
{
  "ai": {
    "provider": "anthropic",
    "model": "<モデル ID>",
    "apiKey": "<キー>",
    "keyProvider": "anthropic"
  }
}
```

- **provider**：`off`、`anthropic`、`openai` のどれかである。`anthropic` は Anthropic の Messages API、`openai` は OpenAI の Chat Completions API を指す。
- **ai がないとき**：未設定である。画面は AI の入力欄の位置に設定への案内を出す。
- **provider が off のとき**：利用者が Off を選んだ。画面は AI に関する表示をすべて隠す。Off にしても `model` と `apiKey` は残し、元の提供元に戻したときに入れ直さずに済むようにする。
- **model**：モデル ID である。sfbench には埋め込まず、利用者が入れる。
- **apiKey**：API キーである。
- **keyProvider**：キーを入れたときの提供元である。キーを消すかどうかの判定に使う（後述）。

対応する提供元は Anthropic と OpenAI の2つに限る（利用者の決定）。
OpenAI 互換の API（Gemini、OpenRouter、手元で動かす Ollama など）にも広げられるが、Base URL の扱い、暗号化されない宛先へのキーの送信、各社の実装の違いへの対処が要り、保守する人のいない道具には重い。
手元で動かす小さなモデルは、SOQL を正しく組めないことが多い。macOS に組み込まれたモデル（`fm` コマンド）で試したところ、3つの要望のどれにも正しい SOQL を返さなかった。

`settings.json` は、作るときと書き換えるときにファイルの権限を 0600 にする（Windows では何もしない）。
API キーが入るので、同じマシンのほかの利用者に読ませないためである。
サーバーのログには、AI への要求のヘッダーと本文を書かない。

### API

`GET /api/settings` は、`ai` から `apiKey` と `keyProvider` を除き、代わりに `hasApiKey`（真偽値）を返す。

`PUT /api/settings` の `ai` は次のように扱う。

- `ai` を省けば、保存済みの `ai` をそのまま残す。設定画面は、AI の欄を変えたときだけ `ai` を送る。名前空間や待つ時間を変えて保存しただけで、未設定が Off に変わらないようにするためである。
- `apiKey` を省けば、保存済みのキーを残す。`apiKey: null` で消す。
- 提供元が `keyProvider` と変わったら、`apiKey` を省いていても保存済みのキーを消す。Anthropic のキーを OpenAI に送るような、利用者の意図しない宛先への送信を防ぐためである（design.md）。Off を経由しても、提供元が同じならキーは残る。
- `provider` が `anthropic` か `openai` なのに `model` が空なら 400 を返す。

## サーバー

### ファイルの分け方

```
src/server/ai/
  anthropic.ts        Anthropic Messages API の呼び出し
  openai.ts           OpenAI Chat Completions API の呼び出し
  tasks.ts            タスクごとの指示文、出力の形（JSON Schema）、受け取った出力の検査
  generate.ts         設定を読み、提供元を選んで呼び、出力を検査して返す
```

提供元ごとの呼び出しは1ファイルにまとめる（design.md「原則の例外」）。
API の仕様が変わって壊れても、直す場所がそのファイルに限られるようにするためである。

### 提供元ごとの呼び出し

どちらも Node の `fetch` で呼び、リダイレクトはたどらない（`redirect: 'error'`）。
リダイレクトの先に、キーを付けた要求が届かないようにするためである。
起動オプションの `--use-env-proxy` で、環境変数のプロキシを通る。

| 項目 | Anthropic | OpenAI |
| --- | --- | --- |
| 宛先 | `POST https://api.anthropic.com/v1/messages` | `POST https://api.openai.com/v1/chat/completions` |
| 認証 | `x-api-key`、`anthropic-version: 2023-06-01` | `Authorization: Bearer <キー>` |
| 出力の形の縛り | `output_config.format`（`{"type": "json_schema", "schema": ...}`） | `response_format`（`{"type": "json_schema", "json_schema": {"name", "schema", "strict": true}}`） |
| 出力の上限 | `max_tokens: 4096`（必須の項目） | 送らない |
| 温度など | 送らない | 送らない |
| 出力の場所 | `content` の `text` | `choices[0].message.content` |
| 拒否 | `stop_reason: "refusal"` | `message.refusal` |
| 上限で切れた | `stop_reason: "max_tokens"` | `finish_reason: "length"` |
| エラーの文 | `error.message` | `error.message` |

- Anthropic で、ツールの呼び出しを強制する方法（`tool_choice`）は使わない。新しいモデルでは 400 になるからである。
- OpenAI で出力の上限と温度を送らないのは、推論モデルが `max_tokens` と `temperature` を拒むからである。モデルの既定に任せる。
- `response_format` の縛りが効く前提にせず、受け取った出力は必ず sfbench の側で検査する。モデルによっては縛りに対応しないことがあるからである。
- 画面に出すエラーの文は、先頭の 2 KB までにする。途中のプロキシなどが、HTML のエラーページを返すことがあるからである。
- 失敗しても、自動では送り直さない（混雑を表す 429 や 529 も同じ）。利用者がもう一度 Generate を押す。

### 出力の形

出力の形は、OpenAI の strict モードの規則に合わせて書く。
この規則で書けば、Anthropic の制限にも収まる。

- いちばん外側はオブジェクトにし、すべてのオブジェクトに `additionalProperties: false` を付ける。
- すべての項目を `required` に入れる。省略できる項目は `["string", "null"]` にする。
- `minLength`、`maximum` などの値の範囲の指定は使わない（Anthropic が 400 を返す）。

受け取った文字列は、`JSON.parse` してから、形を手で検査する（`tasks.ts`）。
縛りが効かないモデルで、JSON の前後に文が付いて返る場合に備え、解析に失敗したら最初の `{` から最後の `}` までを取り出してもう一度解析する。
それでも形に合わなければ、「AI の応答が期待した形ではありません」として、受け取った文を詳細に付けて返す。

### タスク

AI に頼む仕事を、タスクとして3つ定める。
指示文（システムプロンプト）は英語で書く。
どのタスクにも、画面の表示言語（`en` か `ja`）と、Tooling API を使うかを渡す。
説明の文は、画面の表示言語で書くよう指示する。指示文の最後だけでなく、要望の後ろにも添える。「要望と同じ言語で」と指示すると、指示文やメタデータが英語のため、日本語の要望にも英語で返ることがあった（Claude Haiku 5.5）。

| タスク | 渡すもの | 返す形 |
| --- | --- | --- |
| `chooseObjects` | 要望、組織のオブジェクトの一覧（API 名とラベル）、開いているオブジェクト（ある場合） | `{"objects": string[]}`（多くて3つ） |
| `generateSoql` | 要望、オブジェクトの項目（後述）、エディタの内容（ある場合） | `{"soql": string, "explanation": string}` |
| `fixSoql` | エディタの SOQL、エラー文、オブジェクトの項目（ある場合） | `{"soql": string, "explanation": string}` |

- `chooseObjects` に渡すオブジェクトの一覧は、クエリできるものから、`Share`、`History`、`Feed`、`ChangeEvent` で終わるものを除く。Tooling API を使うときは、Tooling API の一覧を渡す。
- `chooseObjects` が返した名前は、渡した一覧に照らし（大文字と小文字、名前空間を区別せずに）、一覧にないものを捨てる。1つも残らなければ、「要望に合うオブジェクトを選べませんでした。オブジェクトの名前（「商談」など）を要望に入れて、もう一度試してください」と出す。

オブジェクトの項目は、JSON ではなく、1項目1行の短い形で渡す。

```
Object Opportunity (商談)
Fields:
Id id
Name string 商談名
StageName picklist フェーズ [Prospecting, Closed Won, Closed Lost]
AccountId reference(Account) relationship Account 取引先 ID
Child relationships:
OpportunityLineItems -> OpportunityLineItem
```

- 選択リストは、有効な値を多くて50個まで載せる。
- 名前は、名前空間を省く設定がオンなら、組織の名前空間を省いた形で渡す。AI が書く SOQL と、エディタで書く SOQL を同じ書き方にそろえ、差分に余計な違いが出ないようにするためである。
- 渡す情報は、画面が describe の結果から組み立てる。サーバーは、受け取った文を指示文と合わせて AI に渡す。

### 送る量

画面は、組み立てた情報が、要望やエディタの内容と合わせて予算（100 KB）に収まるまで削ってから送る。
削る順は、選択リストの値、ラベル、子リレーションである。
それでも収まらなければ、項目を API 名だけにし、さらに収まらなければ末尾の行を切る。

サーバーは、受け取った情報が 200 KB を超えたら、AI を呼ばずに 413 を返す。
画面の予算を超えることは通常ないので、これは最後の安全網である。

100 KB はおよそ3万トークンで、上位のモデルでも1回の料金は数十円に収まる。

### プロンプトインジェクション

組織のメタデータ（ラベル、選択リストの値）とエディタの内容には、AI への指示に見える文が入りうる。
次の3つで、影響を小さくする。

- 指示文で、区切った中の情報はデータであって指示ではない、と AI に伝える。
- AI の説明文は、プレーンテキストとして表示する。Markdown や HTML として描画しない。画像やリンクの URL を使って、情報を外に送られないようにするためである。
- AI の出力は提案カードに出すだけで、利用者が押すまでエディタも組織も変えない（design.md）。SOQL は読み取りだけなので、Replace & Run を許す。

### API

| エンドポイント | 内容 |
| --- | --- |
| `POST /api/ai/generate` | `{ "task", "input" }` を受け、検査済みの出力を `{ "output" }` で返す |
| `POST /api/ai/test` | `PUT /api/settings` と同じ形の `ai` を受け、保存せずに `generateSoql` を小さな入力で1回呼ぶ。成功すれば、所要時間を返す |

接続の確認は、設定画面で入力中の内容で行う。
キーの欄が空なら、保存済みのキーを使う。ただし、提供元が `keyProvider` と同じときに限る（`PUT` と同じ判定）。
料金のかからない `/models` の一覧ではなく、実際の生成を1回行う。
キーと URL だけでなく、選んだモデルが出力の形の縛りを受け付けるかまで確かめられるからである。
料金は数トークン分かかる。推論するモデルでは、推論の分も加わる。設定画面にその旨を書く。

エラーは次のコードで返す。`ApiErrorCode` に足す。

| コード | 状態 | 場面 |
| --- | --- | --- |
| `AI_NOT_CONFIGURED` | 400 | AI が未設定か Off |
| `AI_ERROR` | 502 | AI の API がエラーを返した、または出力を拒否した。`message` に API の文を入れる |
| `AI_BAD_OUTPUT` | 502 | 応答が期待した形でない（上限で切れた場合を含む）。`details` に受け取った文を入れる |
| `AI_TIMEOUT` | 504 | 待つ時間を超えた |
| `PAYLOAD_TOO_LARGE` | 413 | 渡す情報が大きすぎる |

AI の応答を待つ時間は300秒にする。
Salesforce の応答を待つ時間（設定、既定120秒）とは分ける。
手元で動かすモデルは、生成に数分かかることがあるからである。
画面が要求を切ったら（Cancel やタブを閉じたとき）、サーバーは応答の `close` を拾って AI への要求も中止する。
待つ時間と中止は、`AbortSignal.any` で1つのシグナルにまとめる。

## 画面

### AI の入力欄

エディタの上に置く（screens.md）。

- 1行の入力欄と Generate ボタンを置く。入力欄で Enter を押すと Generate と同じである。日本語入力の変換を確定する Enter では送らない（`isComposing` を見る）。
- 生成中は Generate を押せなくし、Enter を連打しても二重に送らない。
- 入力欄の下に、AI に送る情報を並べる。
  - **「エディタの内容」**：エディタが空でないとき、押して切り替える札（`aria-pressed` のボタン）で出す。押されている（塗りつぶしとチェックの印）ときに送り、もう一度押すと送らない（枠だけ）。送らない状態は、作業画面がある間（組織を切り替えるまで）続き、項目を足しても Replace しても戻らない。条件に書いた値を送りたくなくて外した利用者に、知らないうちに送らないためである。すぐ下のエディタのツールバーにある Query All や Tooling API のチェックボックスと見分けられるよう、チェックボックスにしない。
  - **「オブジェクトの一覧」「選ばれたオブジェクトの項目」**：いつも送るので、押せない札（枠なしの塗り）で出す（次の「Generate の流れ」）。開いているオブジェクトの名前も手がかりとして送るので、「オブジェクトの一覧」の札にマウスを載せると「開いている Account を、どのオブジェクトを使うかの手がかりとして伝えます」と出す。
  - 行の見出しは「送る情報:」なので、札には送るものの名前だけを書き、AI がどうするかの説明は書かない。
- AI の欄は背景色を変えて、エディタのツールバーと区切る。
- 右端に、使う AI（提供元とモデル）を出す。

### Generate の流れ

1. `chooseObjects` で、AI に組織のオブジェクトの一覧から、要望に合うオブジェクトを選ばせる。左の一覧で開いているオブジェクトがあれば、手がかりとして一緒に渡す（`openObject`）。AI には「要望がそのオブジェクトについてなら選び、別のオブジェクトについてならそちらを選ぶ」と指示する。
2. 選んだオブジェクトの describe を取得する。describe は区切り2のキャッシュを使う。
3. `generateSoql` を呼ぶ。
4. 提案カードを出す。

生成の間は、いまの段階（「オブジェクトを選んでいます」「項目を読み込んでいます」「SOQL を組んでいます」）と Cancel ボタンを出す。
AI を2回呼ぶのは、組織のオブジェクトすべての項目を渡すと大きすぎるからである。
オブジェクトの一覧（API 名とラベル）だけなら、千数百個でも数十 KB に収まる。

開いているオブジェクトの項目を最初から渡さないのは、AI が渡された項目に引きずられ、要望が別のオブジェクト（Account を開いたまま商談について頼むなど）でも、開いているオブジェクトで無理に組むからである。
利用者と比べた案は次のとおりである。

| 案 | 中身 | 採らなかった理由 |
| --- | --- | --- |
| 開いているオブジェクトの項目を送る札を置き、外したら AI に選ばせる（区切り3b の作り） | 札で切り替える | 札を外すと「AI が選び直す」に変わることが画面から読めない。押し忘れると、開いているオブジェクトで無理に組む |
| 「開いているオブジェクト」と「AI に選ばせる」の2択を置く | 既定は開いているオブジェクトで、AI は1回 | 押し忘れると、開いているオブジェクトで無理に組む |
| 開いているオブジェクトの項目で組ませ、返った SOQL の FROM が別のオブジェクトなら、その項目で組み直す | 判定は画面の FROM の解析。合っていれば AI は1回 | AI が開いているオブジェクトに無理に合わせて組んだときに、見分けられない |
| 採った案：いつも AI に選ばせ、開いているオブジェクトは手がかりにする | 上のとおり | AI が毎回2回になり、時間（約3秒が約6秒）と料金（オブジェクトの一覧の分）が増える |

### Fix with AI

実行エラーの表示（結果の位置）に「Fix with AI」ボタンを置く。
出すのは、Salesforce がエラーを返したとき（`SALESFORCE_ERROR`）だけで、AI が未設定か Off のときは出さない。
認証切れや通信のエラーは、AI に直させても意味がないからである。
押すと、失敗した実行の SOQL と Tooling API の指定（エディタのいまの内容ではない）、エラー文、FROM のオブジェクトの項目を渡して `fixSoql` を呼び、提案カードを出す。
FROM のオブジェクトが組織にない（エラーの原因がそれである）ときは、項目を渡さずに呼ぶ。

### 提案カード

AI の入力欄とエディタの間に出す（screens.md）。

- **差分**：エディタに中身があれば、エディタの内容と提案の差分を出す。語（空白と記号で区切る）の単位で、消えた語を取り消し線と赤、増えた語を緑で示す。大文字と小文字だけの違い（`select` と `SELECT`）は差分にしない。差分は最長共通部分列で求める関数を `src/web/ai/diff.ts` に自分で書く（ライブラリは足さない）。両方の語の数の積が100万を超えたら、計算せずに提案だけを出す。共通する語が提案の半分に満たないときも、差分は消える語と増える語が入り混じって読めないので、提案だけを出す。差分の中の語は、それぞれの文の空白をそのまま保つ。エディタが空なら提案だけを出す。
- **説明**：AI の `explanation` を、プレーンテキストとして出す。
- **ボタン**：Discard、Replace、Replace & Run を置く（日本語の画面では「破棄」「置き換え」「置き換えて実行」）。Replace はエディタを提案で置き換える（取り消せる1回の変更として）。Replace & Run は置き換えてすぐ実行する。押すまでエディタは書き換えない。

### 最近のクエリへの記録

Replace か Replace & Run で置き換えたとき、そのときの要望とエディタの内容を覚えておく。
実行したときにエディタの内容が置き換えたときと同じ（空白の並びを1つにまとめて比べる）なら、`POST /query` に要望を `prompt` として付け、サーバーは最近のクエリに一緒に残す。
Format で整形しただけなら、空白の違いなので一致する。
語を書き換えたあとの実行には付けない。
要望が指すクエリと、実際に実行したクエリがずれないようにするためである。

- Fix with AI で置き換えたときは、直す前のクエリが AI で組んだもの（要望を覚えているもの）なら、その要望を引き継ぐ。手で書いたクエリを直したときは、引き継ぐ要望がないので何も残さない。
- 同じクエリをあとで実行し直したときは、新しい記録に `prompt` がなければ、古い記録の `prompt` を引き継ぐ（`addHistory`）。
- 最近のクエリから読み込んで実行したときも、同じ規則で要望が残る。

### 画面の状態と遷移

AI の流れは、docs/web.md「非同期の流れ」の作りに従う（docs/web.md「流れごとの指定」の AI の行は、この節を指す）。
AI の状態は作業画面（組織の `key` で作り直す木）の中に置くので、組織を切り替えると、生成中の要求は中止され、提案もエラーも要望の印も消える。
流れの側で組織を比べない。
部品の木は、`SoqlProvider` の中に `PanelsProvider`、その中に `AiProvider` を置く。
`AiProvider` は、Replace でエディタと実行を呼び、Fix でエディタ領域を開くからである。

状態は次の場所に持つ。

| 状態 | 持つ場所 | 書く出来事 |
| --- | --- | --- |
| 生成中かどうか、段階 | `AiContext` の `useTask<AiStep>` の `running` と `progress`。Generate と Fix がこの1つを共有する | `useTask` だけ |
| 提案（SOQL、説明、Tooling API の指定、要望）とエラー（文と `details`） | `AiContext` の reducer（`src/web/ai/aiState.ts`） | 成功、失敗、Cancel、Discard、Replace |
| 要望の印（置き換えた SOQL、Tooling API の指定、要望） | `SoqlContext` の状態 | Replace、Replace & Run、最近のクエリの読み込み |
| 失敗した実行（SOQL、Tooling API の指定、付けた要望） | `SoqlContext` の結果（`SALESFORCE_ERROR` のときだけ） | クエリの実行 |
| エディタの落ち着いた本文（入力が止まって300 ms 後） | `SoqlContext` | エディタ |
| 提案が届いた時点のエディタの本文 | `AiContext` の reducer（提案と一緒に） | 成功 |
| 入力中の要望、エディタの内容の札の状態 | `AiContext` | 利用者の入力 |

AI の状態を `SoqlContext` に入れないのは、段階が変わるたびにエディタや左の一覧まで描き直さないためである。
逆向きには分かれておらず、`AiContext` はエディタの解析のたびに描き直される。

本体（`useTask` に渡す関数）は、押した時点の値（要望、開いているオブジェクト、エディタの本文、Tooling API の指定、名前空間）を引数で受け取り、本体の中でエディタを読まない。
段階は `progress` で知らせる。
describe のキャッシュは中止できないので、本体の中で待つ。
成功したら `{ soql, explanation, tooling, prompt }` を返す。
開いているオブジェクトが、いまの API（Tooling API かどうか）の一覧にないときは、手がかりとして渡さない。
Generate の要望は入力した文で、Fix の要望は失敗した実行に付けた要望（なければなし）である。

提案カードの差分は、提案が届いた時点のエディタの本文（呼んだ側が成功を受けたときに読む）と比べて作る。
届いたあとに利用者がエディタを書き換えたら（落ち着いた本文が届いた時点の本文と違えば）、差分をやめて提案だけを出し、「エディタが変わったため、差分を出していません」と添える。
差分をいまのエディタと比べ直すと、手で直すたびに提案カードの中身が動き、提案そのものが書き換わったように見えるからである。
古い本文との差分を出し続けると、Replace が消す語を誤って見せる。

| いまの状態 | 出来事 | 次の状態 |
| --- | --- | --- |
| 待機 | Generate（ボタンか、変換中でない Enter。要望が空でない） | 生成中。「オブジェクトを選んでいます」から始める |
| 待機、結果が `SALESFORCE_ERROR` | Fix with AI | 生成中（「項目を読み込んでいます」）。送るのは失敗した実行の SOQL と Tooling API の指定で、エディタの本文ではない。エディタ領域が閉じていれば開く（提案カードを見せるため） |
| 生成中 | Generate、Enter の連打、Fix | 何もしない（ignore。描画を待たずに判定するので、AI への要求は1回だけ出る）。ボタンは押せなくする |
| 生成中 | 段階が進む | 段階の表示を変える |
| 生成中 | 成功 | 待機。提案を新しいものにし、エラーを消す。入力欄の要望と札の状態は残す |
| 生成中 | 失敗 | 待機。提案を消し、下の「失敗したとき」のとおりに見せる。入力欄の要望と札の状態は残す |
| 生成中 | Cancel | 実際に止めたとき（`cancel` が真）だけ、提案とエラーを消す。完了と同時に押しても、届いた提案は消えない |
| どれでも | 中止した要求や、組織を切り替えたあとに届いた応答 | 何もしない（`stale`） |
| 生成中 | 表示 | 提案カードとエラーを出さない（生成中かは `running` だけで決める）。提案を始める前に消さないのは、ignore で捨てられた二度目の押下で、表示中の提案を消さないためである |
| 提案あり | Discard | 提案を消す |
| 提案あり | Replace | エディタを提案で置き換え（取り消せる1回の変更）、Tooling API の指定を提案のものにし（Tooling API なら Query All を外す）、要望の印を作り直し、提案を消す |
| 提案あり | Replace & Run | Replace と同じことをして、提案の SOQL、Tooling API の指定、要望を、実行へ直接渡す（印の状態が描画に届くのを待たない）。実行中なら、走っている実行を置き換える（replace）。押した操作で実行することがはっきりしているからである |
| どれでも | Run、⌘↵ | 要望の印に照らして、`POST /query` に付ける要望を決める（次の規則1） |
| どれでも | 実行が `SALESFORCE_ERROR` で失敗 | 結果に、実行した SOQL、Tooling API の指定、付けた要望を残す。Fix はこれを受け継ぐ |
| どれでも | 最近のクエリを読み込む | 要望の印を、その記録の要望で作り直す（なければ印を消す） |
| 生成中 | エディタの編集、Tooling API の切り替え | 生成は、押した時点の値のまま続く |
| 生成中 | 組織の切り替え | 作業画面ごと消え、要求は中止される |

Query All は提案に持たせない。
Replace & Run はトグルのいまの値で実行し、Fix の提案も失敗した実行の Query All を引き継がない。
要望が指すのは SOQL であり、Query All は削除済みのレコードを含めるかの指定だからである。

#### 失敗したとき

入力欄の下のエラーに出すものと、ほかに任せるものを次のように分ける。
どの失敗でも、入力中の要望と札の状態は残し、提案は消す。

| 失敗 | 見せ方 |
| --- | --- |
| AI の API のエラー（`AI_*`、`PAYLOAD_TOO_LARGE`） | 入力欄の下に `message` を出し、`details` があれば開いて見られるようにする |
| 画面だけで起きる失敗（要望とエディタの本文が予算を使い切る、AI が選んだオブジェクトが組織の一覧にない） | 入力欄の下に案内の文を出す |
| describe の失敗のうち、組織に関わるもの（`ORG_AUTH_ERROR`、`NOT_FOUND`）と、セッション切れ、sf CLI がないこと | `handleOrgError` に任せ（再ログインのコマンドの通知、組織の一覧の読み直しなど）、入力欄の下には出さない |
| そのほかの describe の失敗 | 入力欄の下に `message` を出す |

`AI_NOT_CONFIGURED`（別のタブで設定を変えたなど）も、AI の API のエラーとして文を出す。
設定は読み直さない。

#### 要望の印

要望の印の規則は、`src/web/ai/promptMark.ts` の純粋な関数だけで判定する。

1. **実行に付けるか**（`promptForRun`）：印があり、実行する SOQL が印の SOQL と同じで、Tooling API の指定も同じなら、印の要望を付ける。比べるときは、両方を整形（`formatSoql`）してから空白をまとめる。Format は空白だけでなく、キーワードの大文字と小文字、記号の前後の空白、サブクエリの括弧の位置も変えるからである。解析できない SOQL は、空白をまとめるだけで比べる。
2. **印を作るか**（`markFor`）：Replace と Replace & Run は提案の要望で、最近のクエリの読み込みはその記録の要望で、印を作る。要望がなければ印を消す。ほかの操作では印を変えない。
3. 空白のまとめ方（`squashSoql`）は `src/shared/api.ts` に置き、画面とサーバーの `addHistory` が同じ関数を使う。サーバーは SOQL を解析しないので、整形はしない。

最近のクエリに残る要望の出どころは3つある。
画面の印（置き換えた文のまま実行したとき）、失敗した実行の結果（Fix が受け継ぐ）、サーバーの `addHistory`（同じクエリの古い記録から引き継ぐ）である。
3つは矛盾しない。
印を消すのは、画面が別のクエリに古い要望を付けないためである。
サーバーの引き継ぎは、同じクエリにだけ要望を付けるので、手で書いたクエリを Fix で直した結果が、要望付きの過去の記録と同じクエリになれば、その要望が付く。
同じクエリなので、これを正とする。

画面の印は Query All を比べず、サーバーの `addHistory` は比べる。
画面は「置き換えた文のままか」を、サーバーは「同じ記録か」を判定しており、目的が違うからである（Query All を切り替えて実行すると、要望の付いた別の記録になる）。

最近のクエリの読み込みで印を作るのは、要望付きの記録を読み込んで実行し、失敗したときに、Fix が要望を引き継げるようにするためである。
読み込んだ記録を `history` から引き直す形にもできるが、印を作る経路が Replace と同じ1つにそろうので、印にする。

#### 既知の弱点

- 印は1つだけなので、提案 A で置き換えたあと提案 B で置き換え、⌘Z で A に戻して実行しても、画面は要望を付けない（A を前に実行していれば、サーバーが引き継ぐ）。
- describe は中止できないので、「項目を読み込んでいます」の間に Cancel しても、describe は裏で続く（結果はキャッシュに入るだけである）。
- 生成中に設定で AI を Off にしても、生成は止めず、表示を隠すだけである（提案カードも、AI が使えない間は出さない）。あとで On に戻すと、その間に届いた提案が出る。
- サーバーの `addHistory` は整形しないので、Format の前と後の同じクエリは、最近のクエリで別の記録になり、要望の引き継ぎもしない（画面が印で要望を付ければ、後の記録には残る）。
- `squashSoql` は文字列リテラルの中の空白もまとめるので、`Name = 'a  b'` と `Name = 'a b'` は最近のクエリで1つにまとまる。
- 提案が届く直前の300 ms に打った文字があると、落ち着いた本文が届いた時点の本文に追いつくまで、差分の代わりに「エディタが変わった」と出ることがある。

#### 検討した案

物差しは、二重送信、遅れて届いた応答、組織の切り替え、要望のずれを作りで防げるか（正しさ）、自前のコードの量、取り込む大きさ、保守の手間である。

| 案 | 中身 | 正しさ | コード | 大きさ | 保守 |
| --- | --- | --- | --- | --- | --- |
| 採った案 | 上のとおり | 作りで決まる。提案とエラーを書くのは1つの `useTask` の結果を受けた reducer だけ。組織は `key` で分かれる | 中（`AiContext`、reducer、純粋な関数2つ、`SoqlContext` の印と失敗した実行と実行の口） | 増えない | 既存の `useTask` と reducer の作法（組織の一覧、続きのページ）のまま |
| 前の作り | 流れごとの `AbortController` の ref、組織の印を付けた状態、本体に状態を書く関数を渡す | 個別の守りで、レビューのたびに穴が出た | 中 | 増えない | 守りの書き方が流れごとに違う |
| 提案とエラーを `useState` で持ち、呼んだ側ごとに書く | reducer を作らない | 採った案と同じ | 少し減る | 増えない | 書く場所が Generate、Fix、Cancel、Discard、Replace に散り、表の行をそのままテストにできない |
| Generate と Fix で `useTask` を分ける | 流れごとに1つ | 両方が提案を書くので、Fix の完了が生成中の Generate の提案を上書きしうる（防ぐには、先に片方を止める取り決めが要る） | 少 | 増えない | 取り決めが崩れやすい |
| 既存のライブラリ：TanStack Query | `useMutation`、または要求ごとのキーで `refetch` する `useQuery` | `useMutation` は `signal` を受け取らない。`useQuery` なら受け取れるが、生成を読み込みとして扱うことになる | 中 | 約13 KB | 仕組みが2つになる（docs/web.md「検討した案」と同じ理由） |
| 既存のライブラリ：React 19 の `useActionState` | 生成を action として扱う | action を順に全部実行し（無視も置き換えもしない）、`AbortSignal` を渡さないので、ignore と Cancel を自前で書く | 中 | 増えない | 保留中の判定が transition に結び付く |
| 既存のライブラリ：XState などの状態機械 | 上の表を機械として書く | 表とコードが一致する | 中 | 十数 KB | 同じ利点は reducer で得られる。中止は結局 `useTask` に頼る |
| 印を CodeMirror の状態に持つ | `StateField` と `invertedEffects` で、印を取り消しの履歴に乗せる | ⌘Z の弱点が消える | 中 | 増えない | エディタの外から印を読む口が要り、仕組みが重い |
| 印を「SOQL から要望への Map」にする | 作業画面の中で置き換えたものをすべて覚える | ⌘Z の弱点が消える | 少 | 増えない | 書き換えて元に戻した文にも古い要望が付く。覚える数に上限が要る |
| 機能を減らす：要望は Replace & Run のときだけ付ける | 印をなくす | Fix の引き継ぎは結果で残せる | 約15行減る | 増えない | Replace のあとの Run や Format のあとの Run で記録されなくなり、仕様が変わる |
| 判定をサーバーへ移す | Replace のときに置き換えた SOQL と要望をサーバーへ送る | 照合は1か所になる | 中（新しい API） | 増えない | タブごとの状態をサーバーに持つことになり、作業画面の作り直しで消えない |

差分は、jsdiff の `diffWordsWithSpace` や `@codemirror/merge` でも作れるが、自前の `diff.ts` は約60行で、依存を足すほどではない。
採った案は、別のサブエージェントに問題と制約だけを渡して出させた案をもとにし、設計のレビューで reducer を足した。

### 設定画面の AI の欄

screens.md のとおり、Off、Anthropic、OpenAI から選び、モデルと API キーを入れる。

- API キーの欄は、保存済みなら空のまま「保存済み」と表示する。入力すれば置き換え、「キーを消す」で消す。
- 提供元を変えると、保存済みのキーが消えることを、欄の下に書く。
- AI に送る情報として、オブジェクトと項目の名前、型、選択リストの値、エディタの内容（条件に書いた値を含む）、エラー文を挙げる。クエリの結果とレコードは送らない、と書く。
- Test connection は、入力中の内容で試す（前述）。

## テスト

- `anthropic.ts` と `openai.ts` は、`fetch` を差し替え、記録した応答（成功、エラー、拒否、上限で切れた出力、形に合わない出力、HTML のエラーページ）で確かめる。送る本文に、上限や温度の項目が表のとおり入ること（入らないこと）も確かめる。
- `tasks.ts` の検査は、形に合う出力、合わない出力、前後に文の付いた JSON で確かめる。`chooseObjects` の名前の照らし合わせも確かめる。
- 設定の API は、キーを返さないこと、`ai` を省くと保存済みが残ること、提供元を変えるとキーが消え、Off を経由しても提供元が同じなら残ることを確かめる。
- 画面は API を差し替えて、Generate の流れ（開いているオブジェクトあり、なし、別のオブジェクトが選ばれる）、Cancel、提案カードの各ボタン、Fix with AI、最近のクエリへの記録、予算に収める削り方を確かめる。
- 実際の AI の API を呼ぶ確認は手で行う（Anthropic と OpenAI）。
