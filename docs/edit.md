# sfbench 結果の表での編集と削除の技術設計

SOQL の結果の表で、レコードの値を書き換えて保存し、行を選んで削除する機能の設計を書く。
画面の見た目は [screens.md](screens.md)、結果の表の作りは [web.md](web.md)「結果の表」、サーバーの API は [design.md](design.md) にある。
データを変えうる操作の確認と失敗の分け方は、REST API の画面（[rest.md](rest.md)）と共通の関数を使う。

## 範囲

次の PR に分ける。

| PR | 内容 |
| --- | --- |
| 6a（サーバー） | `POST /api/orgs/:user/records/update`、`POST /api/orgs/:user/records/delete`、テスト |
| 6b（画面） | 結果の見出しの「編集」、セルの編集、行の選択、保存と削除、確認、保存していない変更を捨てる前の確認 |

次のものは作らない。

- 新しいレコードの作成。
- 親の項目（`Account.Name`）とサブクエリのレコードの編集。
- 複数の行に同じ値を一度に入れる操作。

## 前提にする事実

kimura-demo（API 66.0）に、存在しない ID への更新を送って確かめた（データは変えていない）。

1. **sObject Collections の更新（`PATCH /composite/sobjects`）は、送った順に1件ずつ成否を返す。** `{ success, errors: [{ statusCode, message, fields }] }` の配列で、失敗した行には `id` が付かない。1回に200件まで送れる。
2. **項目の値の形の誤りは、その行だけの失敗になる。** 数値の項目に `"abc"` を送ると、その行が `JSON_PARSER_ERROR` になり、ほかの行は続けて処理される。
3. **数値は文字列で送ってよい。** `"12"` も `"12345678901234567.25"` も受け付けた。画面は数値を文字列のまま送り、`Number` を通さないので、桁が丸まらない。
4. **クエリの結果のキーは、クエリの書き方によらず API 名になる**（`select id, numberofemployees` でも `Id`、`NumberOfEmployees`）。
5. **削除（`DELETE /composite/sobjects?ids=...&allOrNone=...`）も、1回に200件まで、1件ずつ成否を返す。**
6. **`allOrNone` を真にすると、1件でも失敗したらその呼び出しのすべてを取り消す。** 1回の呼び出しの中でだけ効くので、200件を超えると全体の取り消しは保証できない。

## 画面

### 編集を始める

- 結果の見出しに「編集」の切り替えを置く。既定はオフで、オフのあいだは表はいままでどおり読むだけである。
- 次の結果では「編集」を押せなくし、理由を `title` に出す。
  - Tooling API の結果、集計の結果（`attributes.type` が `AggregateResult`）
  - `Id` の列がない結果（Id を SELECT していない）
- 編集できる列は、FROM のオブジェクト自身の項目（列の `path` が1段）のうち、そのオブジェクトの describe で `updateable` が真のものである。describe は、クエリを実行したときの API バージョンで読む。編集できない列は、編集中も見た目を変えない。

### セルを書き換える

- 編集中に、編集できる列のセルをダブルクリックするか、選んで Enter を押すと、そのセルが入力欄になる。Enter で確定し、Esc で取り消す。
- 入力欄は項目の型で変える。

| 型 | 入力欄 | 送る値 |
| --- | --- | --- |
| `boolean` | チェックボックス（押すとすぐ変わる） | `true` か `false` |
| `picklist` | 有効な値の選択と「（なし）」 | 文字列か `null` |
| `int`、`double`、`currency`、`percent` | 文字の入力欄 | 文字列（前提の3）。空なら `null` |
| `date`、`datetime`、`time` | 文字の入力欄（いまの値の形で書く。例 `2026-10-18`、`2026-10-18T09:00:00.000+0000`） | 文字列。空なら `null` |
| それ以外（`string`、`textarea`、`email`、`url`、`phone`、`reference`、`multipicklist` など） | 文字の入力欄（`textarea` は複数行） | 文字列。空なら `null` |

- 変えたセルは色を変え、見出しに「N件の変更を保存」「変更を取り消す」を出す。N は変えた行の数である。もとの値に戻したセルは、変更から外す。
- 値の検査は Salesforce に任せる（形の誤りはその行の失敗として返る。前提の2）。画面は型ごとの入力欄を出すだけにする。

### 行を選んで削除する

- 編集中は、表の左端に行の選択列を出す。見出しのチェックボックスで、いま表示している行（絞り込みの結果）をすべて選ぶ。
- 選んだ行があれば、見出しに「N件を削除」を出す。

### 保存と削除

- 「1件でも失敗したら全部取り消す」のチェックボックスを、保存と削除のボタンの横に置く。既定はオフで、ブラウザに覚える（利用者と決めたこと 1）。オンのときは、200件を超える保存や削除を押せなくする（前提の6）。
- 保存は、変えた行を200件ずつ順に送る。削除も同じである。送っている間は「保存しています（200/600件）」と出し、表の編集はできなくする。
- 本番の組織では、保存の前に「本番の組織 X の Account の N件を更新します」と確認する。削除は、本番かどうかによらず「Account の N件を削除します」と確認する（利用者と決めたこと 3）。
- 終わったら、表の中で反映する（利用者と決めたこと 2）。
  - 保存できた行は、送った値をレコードに入れ、変更から外す。数式の項目や最終更新日は、クエリを実行し直すまで古いままである。
  - 削除できた行は、表から消す。見出しの件数も減らす。
  - 失敗した行は、変更を残し、行の頭にエラーの印を出す。印を押すと Salesforce のエラー文を出す。`allOrNone` で取り消された行には「ほかの行の失敗で取り消しました」と出す。
- 途中の呼び出しが失敗したら、そこで止める。
  - 送ったか分からない失敗（`SALESFORCE_TIMEOUT`、`SALESFORCE_UNREACHABLE`、sfbench に接続できない）なら、その200件は変更を残したまま「結果が分かりません。クエリを実行し直して確かめてください」と出す。送り直す前の確認や実行履歴は作らない（利用者と決めたこと 4）。
  - 送っていない失敗（認証切れなど）なら、エラーを出し、まだ送っていない行の変更を残す。
  - すでに終わった200件ずつの結果は、表に反映する。

### 保存していない変更を捨てる前の確認

保存していない変更があるときに、次の操作をすると「保存していない変更がN件あります。捨てますか」と確認する（利用者と決めたこと 5）。

- クエリの実行（実行ボタン、⌘↵、AI の提案の「置き換えて実行」）
- 組織の切り替え
- 「編集」をオフにする
- タブを閉じる、再読み込みする（ブラウザの `beforeunload` の確認）

行を選んだだけ（削除していない）では確認しない。

## サーバー

### `POST /api/orgs/:user/records/update`

```
{ object: string, records: [{ id: string, fields: { [name]: string | boolean | null } }], allOrNone: boolean, apiVersion?: string }
→ 200 { results: [{ id, success: boolean, errors: [{ statusCode, message, fields }] }] }
```

- 1回に200件までにする。分けて送るのは画面である。画面が分けると、進み具合を出せ、途中で止めたときにどこまで送ったかが分かるからである。
- 検査：`object` と項目名は英数字と `_` だけ、`id` は15か18文字の英数字、値は文字列、真偽値、`null` だけ。外れたら 400 で、何も送らない。
- `results` は送った順に並べ、Salesforce が返さない `id` は送った `id` で埋める。
- Salesforce が呼び出し全体を断ったとき（400 など）は、ほかの API と同じ `SALESFORCE_ERROR` にする。
- ログには `records update <オブジェクト> <件数> <失敗の件数> <所要時間>` だけを書く。値とエラー文は書かない（エラー文には値が入りうる）。

### `POST /api/orgs/:user/records/delete`

```
{ ids: string[], allOrNone: boolean, apiVersion?: string }
→ 200 { results: [{ id, success, errors }] }
```

- 1回に200件まで。検査とログは更新と同じである。

### 経路

どちらも OrgClient の `request` で送る。GET でないので、データを変えうる要求として扱われ、接続が切れても送り直さない（design.md「代わりの経路への切り替え」）。
API バージョンは、クエリの実行と同じく、組織が対応するかを確かめてから使う。

## 判定の置き場所

| 判定 | 置き場所 |
| --- | --- |
| 編集できる結果か、編集できる列か | `src/web/results/editable.ts` |
| 入力した文字から送る値への変換 | `src/web/results/editable.ts` |
| 変更、選択、行のエラー、送った結果の反映 | `src/web/results/edits.ts` の reducer |
| 200件ずつに分ける | `src/web/results/edits.ts` |
| 確認するか | `confirmReasons`（execution.ts）。保存は本番だけ、削除はいつも |
| 失敗の分け方 | `runFailed`（execution.ts） |
| 保存していない変更があるか | 結果の表が `SoqlContext` に知らせ、実行と組織の切り替えがそこで確かめる |

## 検討した案

| 案 | 判断 |
| --- | --- |
| 採った案：保存のあと表の中で反映する | 読み込んだページとスクロールの位置が残る。数式の項目などは古いままになる |
| 保存のあとクエリを実行し直す | 値は正しくなるが、続きのページとスクロールの位置を失う。利用者と決めて採らない |
| 実行履歴を残し、結果の分からない保存の送り直しを確認する | 同じ値の更新は送り直しても値が変わらず、削除の送り直しは失敗するだけなので、作る手間に見合わない。トリガーやフローが二度動くことは既知の弱点にする |
| サーバーが200件ずつに分ける | 画面が進み具合を出せず、途中の失敗でどこまで送ったかを返す形が複雑になる |
| Composite API で1回にまとめる | `allOrNone` を200件を超えて効かせられるが、1回の上限（25の要求）があり、作りが大きくなる |

## 既知の弱点

- **保存のあと、数式の項目、最終更新日、トリガーが変えた値は、クエリを実行し直すまで古いままである。**
- **結果が分からなかった保存を送り直すと、トリガーやフローが二度動く。** 値は同じになる。
- **「1件でも失敗したら全部取り消す」は200件までしか効かない。** それを超えると押せなくする。
- **日付と日時は文字で入力する。** 形が違えば、その行の失敗として Salesforce のエラー文が出る。

## 利用者と決めたこと

| # | 問い | 決めたこと |
| --- | --- | --- |
| 1 | 一部の行だけ失敗したとき | 通る行は保存する。「1件でも失敗したら全部取り消す」を選べるようにし、既定はオフ |
| 2 | 保存と削除のあとの表 | 表の中で反映する。クエリは実行し直さない |
| 3 | 確認のダイアログ | 削除はいつも件数を示して確認する。保存は本番の組織でだけ確認する |
| 4 | 結果が分からなかったとき | 「結果が分かりません」と出して変更を残す。実行履歴は作らない |
| 5 | 保存していない変更があるときの実行や切り替え | 捨ててよいか確認する |
