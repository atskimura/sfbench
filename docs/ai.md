# sfbench AI で組む機能の技術設計

区切り3（AI で組む機能）の設計を書く。
決まっている方針は [design.md](design.md) の「AI で組む機能」に、画面の仕様は [screens.md](screens.md) の「AI の入力欄」「AI の提案カード」「設定」にあり、この文書はそれらをどう実装するかを決める。

## 範囲

区切り3で作るのは、SOQL を AI に組ませる機能である。

- 要望の文から SOQL を組む（Generate）
- 実行エラーになった SOQL を直す（Fix with AI）
- 提案カード（差分、説明、Discard、Replace、Replace & Run）
- 設定画面の AI の欄と、接続の確認（Test connection）
- 最近のクエリに、AI に頼んだ文を残す

REST API のリクエストと匿名 Apex を組ませる機能は、それぞれの画面と一緒に区切り4と5で作る。
この文書の仕組み（設定、提供元ごとの呼び出し、出力の形の検査、提案カード）は、そのときもそのまま使う。
ただし REST API と Apex では、提案カードに「反映して実行」を置かない。
データを変えうる操作なので、AI の出力を利用者が読んでから実行するようにするためである。

## 設定

### 保存する形

`~/.sfbench/settings.json` の `ai` に保存する。

```json
{
  "ai": {
    "provider": "anthropic",
    "model": "<モデル ID>",
    "apiKey": "<キー>",
    "keyProvider": "anthropic"
  }
}
```

- **provider**：`off`、`anthropic`、`openai` のどれかである。`anthropic` は Anthropic の Messages API、`openai` は OpenAI の Chat Completions API を指す。
- **ai がないとき**：未設定である。画面は AI の入力欄の位置に設定への案内を出す。
- **provider が off のとき**：利用者が Off を選んだ。画面は AI に関する表示をすべて隠す。Off にしても `model` と `apiKey` は残し、元の提供元に戻したときに入れ直さずに済むようにする。
- **model**：モデル ID である。sfbench には埋め込まず、利用者が入れる。
- **apiKey**：API キーである。
- **keyProvider**：キーを入れたときの提供元である。キーを消すかどうかの判定に使う（後述）。

対応する提供元は Anthropic と OpenAI の2つに限る（利用者の決定）。
OpenAI 互換の API（Gemini、OpenRouter、手元で動かす Ollama など）にも広げられるが、Base URL の扱い、暗号化されない宛先へのキーの送信、各社の実装の違いへの対処が要り、保守する人のいない道具には重い。
手元で動かす小さなモデルは、SOQL を正しく組めないことが多い。macOS に組み込まれたモデル（`fm` コマンド）で試したところ、3つの要望のどれにも正しい SOQL を返さなかった。

`settings.json` は、作るときと書き換えるときにファイルの権限を 0600 にする（Windows では何もしない）。
API キーが入るので、同じマシンのほかの利用者に読ませないためである。
サーバーのログには、AI への要求のヘッダーと本文を書かない。

### API

`GET /api/settings` は、`ai` から `apiKey` と `keyProvider` を除き、代わりに `hasApiKey`（真偽値）を返す。

`PUT /api/settings` の `ai` は次のように扱う。

- `ai` を省けば、保存済みの `ai` をそのまま残す。設定画面は、AI の欄を変えたときだけ `ai` を送る。名前空間や待つ時間を変えて保存しただけで、未設定が Off に変わらないようにするためである。
- `apiKey` を省けば、保存済みのキーを残す。`apiKey: null` で消す。
- 提供元が `keyProvider` と変わったら、`apiKey` を省いていても保存済みのキーを消す。Anthropic のキーを OpenAI に送るような、利用者の意図しない宛先への送信を防ぐためである（design.md）。Off を経由しても、提供元が同じならキーは残る。
- `provider` が `anthropic` か `openai` なのに `model` が空なら 400 を返す。

## サーバー

### ファイルの分け方

```
src/server/ai/
  anthropic.ts        Anthropic Messages API の呼び出し
  openai.ts           OpenAI Chat Completions API の呼び出し
  tasks.ts            タスクごとの指示文、出力の形（JSON Schema）、受け取った出力の検査
  generate.ts         設定を読み、提供元を選んで呼び、出力を検査して返す
```

提供元ごとの呼び出しは1ファイルにまとめる（design.md「原則の例外」）。
API の仕様が変わって壊れても、直す場所がそのファイルに限られるようにするためである。

### 提供元ごとの呼び出し

どちらも Node の `fetch` で呼び、リダイレクトはたどらない（`redirect: 'error'`）。
リダイレクトの先に、キーを付けた要求が届かないようにするためである。
起動オプションの `--use-env-proxy` で、環境変数のプロキシを通る。

| 項目 | Anthropic | OpenAI |
| --- | --- | --- |
| 宛先 | `POST https://api.anthropic.com/v1/messages` | `POST https://api.openai.com/v1/chat/completions` |
| 認証 | `x-api-key`、`anthropic-version: 2023-06-01` | `Authorization: Bearer <キー>` |
| 出力の形の縛り | `output_config.format`（`{"type": "json_schema", "schema": ...}`） | `response_format`（`{"type": "json_schema", "json_schema": {"name", "schema", "strict": true}}`） |
| 出力の上限 | `max_tokens: 4096`（必須の項目） | 送らない |
| 温度など | 送らない | 送らない |
| 出力の場所 | `content` の `text` | `choices[0].message.content` |
| 拒否 | `stop_reason: "refusal"` | `message.refusal` |
| 上限で切れた | `stop_reason: "max_tokens"` | `finish_reason: "length"` |
| エラーの文 | `error.message` | `error.message` |

- Anthropic で、ツールの呼び出しを強制する方法（`tool_choice`）は使わない。新しいモデルでは 400 になるからである。
- OpenAI で出力の上限と温度を送らないのは、推論モデルが `max_tokens` と `temperature` を拒むからである。モデルの既定に任せる。
- `response_format` の縛りが効く前提にせず、受け取った出力は必ず sfbench の側で検査する。モデルによっては縛りに対応しないことがあるからである。
- 画面に出すエラーの文は、先頭の 2 KB までにする。途中のプロキシなどが、HTML のエラーページを返すことがあるからである。
- 失敗しても、自動では送り直さない（混雑を表す 429 や 529 も同じ）。利用者がもう一度 Generate を押す。

### 出力の形

出力の形は、OpenAI の strict モードの規則に合わせて書く。
この規則で書けば、Anthropic の制限にも収まる。

- いちばん外側はオブジェクトにし、すべてのオブジェクトに `additionalProperties: false` を付ける。
- すべての項目を `required` に入れる。省略できる項目は `["string", "null"]` にする。
- `minLength`、`maximum` などの値の範囲の指定は使わない（Anthropic が 400 を返す）。

受け取った文字列は、`JSON.parse` してから、形を手で検査する（`tasks.ts`）。
縛りが効かないモデルで、JSON の前後に文が付いて返る場合に備え、解析に失敗したら最初の `{` から最後の `}` までを取り出してもう一度解析する。
それでも形に合わなければ、「AI の応答が期待した形ではありません」として、受け取った文を詳細に付けて返す。

### タスク

AI に頼む仕事を、タスクとして3つ定める。
指示文（システムプロンプト）は英語で書く。
どのタスクにも、画面の表示言語（`en` か `ja`）と、Tooling API を使うかを渡す。
説明の文は、要望があれば要望と同じ言語で、なければ画面の表示言語で書くよう指示する。

| タスク | 渡すもの | 返す形 |
| --- | --- | --- |
| `chooseObjects` | 要望、組織のオブジェクトの一覧（API 名とラベル） | `{"objects": string[]}`（多くて3つ） |
| `generateSoql` | 要望、オブジェクトの項目（後述）、エディタの内容（ある場合） | `{"soql": string, "explanation": string}` |
| `fixSoql` | エディタの SOQL、エラー文、オブジェクトの項目（ある場合） | `{"soql": string, "explanation": string}` |

- `chooseObjects` に渡すオブジェクトの一覧は、クエリできるものから、`Share`、`History`、`Feed`、`ChangeEvent` で終わるものを除く。Tooling API を使うときは、Tooling API の一覧を渡す。
- `chooseObjects` が返した名前は、渡した一覧に照らし（大文字と小文字、名前空間を区別せずに）、一覧にないものを捨てる。1つも残らなければ、「対象のオブジェクトを選べませんでした。左の一覧でオブジェクトを開いてから、もう一度試してください」と出す。

オブジェクトの項目は、JSON ではなく、1項目1行の短い形で渡す。

```
Object Opportunity (商談)
Fields:
Id id
Name string 商談名
StageName picklist フェーズ [Prospecting, Closed Won, Closed Lost]
AccountId reference(Account) relationship Account 取引先 ID
Child relationships:
OpportunityLineItems -> OpportunityLineItem
```

- 選択リストは、有効な値を多くて50個まで載せる。
- 名前は、名前空間を省く設定がオンなら、組織の名前空間を省いた形で渡す。AI が書く SOQL と、エディタで書く SOQL を同じ書き方にそろえ、差分に余計な違いが出ないようにするためである。
- 渡す情報は、画面が describe の結果から組み立てる。サーバーは、受け取った文を指示文と合わせて AI に渡す。

### 送る量

画面は、組み立てた情報が予算（100 KB）に収まるまで削ってから送る（決定待ち）。
削る順は、選択リストの値、ラベル、子リレーションである。
それでも収まらなければ、項目を API 名だけにする。

サーバーは、受け取った情報が 200 KB を超えたら、AI を呼ばずに 413 を返す。
画面の予算を超えることは通常ないので、これは最後の安全網である。

100 KB はおよそ3万トークンで、上位のモデルでも1回の料金は数十円に収まる。

### プロンプトインジェクション

組織のメタデータ（ラベル、選択リストの値）とエディタの内容には、AI への指示に見える文が入りうる。
次の3つで、影響を小さくする。

- 指示文で、区切った中の情報はデータであって指示ではない、と AI に伝える。
- AI の説明文は、プレーンテキストとして表示する。Markdown や HTML として描画しない。画像やリンクの URL を使って、情報を外に送られないようにするためである。
- AI の出力は提案カードに出すだけで、利用者が押すまでエディタも組織も変えない（design.md）。SOQL は読み取りだけなので、Replace & Run を許す。

### API

| エンドポイント | 内容 |
| --- | --- |
| `POST /api/ai/generate` | `{ "task", "input" }` を受け、検査済みの出力を `{ "output" }` で返す |
| `POST /api/ai/test` | `PUT /api/settings` と同じ形の `ai` を受け、保存せずに `generateSoql` を小さな入力で1回呼ぶ。成功すれば、所要時間を返す |

接続の確認は、設定画面で入力中の内容で行う。
キーの欄が空なら、保存済みのキーを使う。ただし、提供元が `keyProvider` と同じときに限る（`PUT` と同じ判定）。
料金のかからない `/models` の一覧ではなく、実際の生成を1回行う。
キーと URL だけでなく、選んだモデルが出力の形の縛りを受け付けるかまで確かめられるからである。
料金は数トークン分かかる。推論するモデルでは、推論の分も加わる。設定画面にその旨を書く。

エラーは次のコードで返す。`ApiErrorCode` に足す。

| コード | 状態 | 場面 |
| --- | --- | --- |
| `AI_NOT_CONFIGURED` | 400 | AI が未設定か Off |
| `AI_ERROR` | 502 | AI の API がエラーを返した、または出力を拒否した。`message` に API の文を入れる |
| `AI_BAD_OUTPUT` | 502 | 応答が期待した形でない（上限で切れた場合を含む）。`details` に受け取った文を入れる |
| `AI_TIMEOUT` | 504 | 待つ時間を超えた |
| `PAYLOAD_TOO_LARGE` | 413 | 渡す情報が大きすぎる |

AI の応答を待つ時間は300秒にする。
Salesforce の応答を待つ時間（設定、既定120秒）とは分ける。
手元で動かすモデルは、生成に数分かかることがあるからである。
画面が要求を切ったら（Cancel やタブを閉じたとき）、サーバーは応答の `close` を拾って AI への要求も中止する。
待つ時間と中止は、`AbortSignal.any` で1つのシグナルにまとめる。

## 画面

### AI の入力欄

エディタの上に置く（screens.md）。

- 1行の入力欄と Generate ボタンを置く。入力欄で Enter を押すと Generate と同じである。日本語入力の変換を確定する Enter では送らない（`isComposing` を見る）。
- 生成中は Generate を押せなくし、Enter を連打しても二重に送らない。
- 入力欄の下に、AI に送る情報をチップで並べる。チップは × で外せる。
  - **「<オブジェクト> fields」**：左の一覧で開いているオブジェクト。区切り2で、左の一覧は FROM のオブジェクトに追従するので、通常は FROM のオブジェクトと同じである。食い違うのは、利用者が左の一覧で別のオブジェクトを開いたときで、そのときは開いている方を使う。
  - **「Editor text」**：エディタが空でないとき
- 右端に、使う AI（提供元とモデル）を出す。
- 組織を選んでいないときは使えない。

### Generate の流れ

1. 「<オブジェクト> fields」のチップがあれば、そのオブジェクトを使う。なければ `chooseObjects` で AI にオブジェクトを選ばせる。
2. 選んだオブジェクトの describe を取得する。describe は区切り2のキャッシュを使う。
3. `generateSoql` を呼ぶ。
4. 提案カードを出す。

生成の間は、いまの段階（「オブジェクトを選んでいます」「項目を読み込んでいます」「SOQL を組んでいます」）と Cancel ボタンを出す。
チップがないときに AI を2回呼ぶのは、組織のオブジェクトすべての項目を渡すと大きすぎるからである。
オブジェクトの一覧（API 名とラベル）だけなら、千数百個でも数十 KB に収まる。

### Fix with AI

実行エラーの表示（結果の位置）に「Fix with AI」ボタンを置く。
出すのは、Salesforce がエラーを返したとき（`SALESFORCE_ERROR`）だけで、AI が未設定か Off のときは出さない。
認証切れや通信のエラーは、AI に直させても意味がないからである。
押すと、エディタの SOQL、エラー文、FROM のオブジェクトの項目を渡して `fixSoql` を呼び、提案カードを出す。
FROM のオブジェクトが組織にない（エラーの原因がそれである）ときは、項目を渡さずに呼ぶ。

### 提案カード

AI の入力欄とエディタの間に出す（screens.md）。

- **差分**：エディタに中身があれば、エディタの内容と提案の差分を出す。語（空白と記号で区切る）の単位で、消えた語を取り消し線と赤、増えた語を緑で示す。大文字と小文字だけの違い（`select` と `SELECT`）は差分にしない。差分は最長共通部分列で求める関数を `src/web/ai/diff.ts` に自分で書く（ライブラリは足さない）。両方の語の数の積が100万を超えたら、計算せずに提案だけを出す。エディタが空なら提案だけを出す。
- **説明**：AI の `explanation` を、プレーンテキストとして出す。
- **ボタン**：Discard、Replace、Replace & Run を置く。Replace はエディタを提案で置き換える（取り消せる1回の変更として）。Replace & Run は置き換えてすぐ実行する。押すまでエディタは書き換えない。

### 最近のクエリへの記録

Replace か Replace & Run で置き換えたとき、そのときの要望とエディタの内容を覚えておく。
実行したときにエディタの内容が置き換えたときと同じ（空白の並びを1つにまとめて比べる）なら、`POST /query` に要望を `prompt` として付け、サーバーは最近のクエリに一緒に残す。
Format で整形しただけなら、空白の違いなので一致する。
語を書き換えたあとの実行には付けない。
要望が指すクエリと、実際に実行したクエリがずれないようにするためである。

- Fix with AI で置き換えたときは、直す前のクエリが AI で組んだもの（要望を覚えているもの）なら、その要望を引き継ぐ。手で書いたクエリを直したときは、引き継ぐ要望がないので何も残さない。
- 同じクエリをあとで実行し直したときは、新しい記録に `prompt` がなければ、古い記録の `prompt` を引き継ぐ（`addHistory`）。
- 最近のクエリから読み込んで実行したときも、同じ規則で要望が残る。

### 設定画面の AI の欄

screens.md のとおり、Off、Anthropic、OpenAI から選び、モデルと API キーを入れる。

- API キーの欄は、保存済みなら空のまま「保存済み」と表示する。入力すれば置き換え、「キーを消す」で消す。
- 提供元を変えると、保存済みのキーが消えることを、欄の下に書く。
- AI に送る情報として、オブジェクトと項目の名前、型、選択リストの値、エディタの内容（条件に書いた値を含む）、エラー文を挙げる。クエリの結果とレコードは送らない、と書く。
- Test connection は、入力中の内容で試す（前述）。

## テスト

- `anthropic.ts` と `openai.ts` は、`fetch` を差し替え、記録した応答（成功、エラー、拒否、上限で切れた出力、形に合わない出力、HTML のエラーページ）で確かめる。送る本文に、上限や温度の項目が表のとおり入ること（入らないこと）も確かめる。
- `tasks.ts` の検査は、形に合う出力、合わない出力、前後に文の付いた JSON で確かめる。`chooseObjects` の名前の照らし合わせも確かめる。
- 設定の API は、キーを返さないこと、`ai` を省くと保存済みが残ること、提供元を変えるとキーが消え、Off を経由しても提供元が同じなら残ることを確かめる。
- 画面は API を差し替えて、Generate の流れ（チップあり、なし）、Cancel、提案カードの各ボタン、Fix with AI、最近のクエリへの記録、予算に収める削り方を確かめる。
- 実際の AI の API を呼ぶ確認は手で行う（Anthropic と OpenAI）。
