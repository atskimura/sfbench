# sfbench 画面の技術設計

区切り2（SOQL の画面）で作る画面側の設計を書く。
画面の見た目と振る舞いは [screens.md](screens.md)、サーバーの API は [design.md](design.md) にあり、この文書はそれらをどう実装するかを決める。

## 範囲

この文書は、SOQL の画面（区切り2）と、AI で SOQL を組む機能の画面（区切り3、詳しくは [ai.md](ai.md)）を扱う。
SOQL の画面は、組織の切り替え、組織を開くボタン、設定画面、接続できないときの案内を含む。
REST API の画面（区切り4）の設計は [rest.md](rest.md) に、Apex の画面（区切り5）の設計は [apex.md](apex.md) にある。
結果の表での編集と削除（区切り6）の設計は [edit.md](edit.md) にある。

## ライブラリ

画面のライブラリはすべて `devDependencies` に入れ、ビルド時に取り込む。
利用者の実行時の依存にはならない。

| 用途 | ライブラリ | 理由 |
| --- | --- | --- |
| 画面 | React 19 | 決定済み |
| SOQL の解析と組み立て、整形 | `soql-parser-js` 5 | lwc-soql-builder でも使っていた。最後のリリースは 2024年1月の 5.0.2 だが、ビルド時に取り込むので利用者の環境で壊れることはない。`WITH USER_MODE`、`TYPEOF`、`FIELDS(ALL)`、日付リテラル、`GROUP BY ROLLUP` は解析と組み立ての往復で崩れない。Apex のバインド変数（`:foo`）は解析できない |
| エディタ | CodeMirror 6（`@codemirror/view`、`state`、`commands`、`autocomplete`、`language`、`lang-sql`） | 補完の仕組みを持つ。React 用のラッパーは使わず、`useEffect` で直接組み込む。色分けは `lang-sql` の `SQLDialect.define` で SOQL のキーワードを定義する |
| 結果の表の仮想スクロール | `@tanstack/react-virtual` | 数万行の結果でも描画を軽く保つ。表そのものは自分で描く（TanStack Table は列が動的に決まる表には大きすぎる） |
| テスト | Vitest、jsdom、Testing Library | 画面のテストを Node 上で動かす |

`soql-parser-js` が解析できない SOQL（新しい構文、バインド変数など）でも、エディタと実行は使える。
解析できない間は、項目の一覧との同期、整形、補完の文脈の判定のうち解析に頼る部分だけが止まる。

取り込んだライブラリのライセンス表示は、ビルド時に `dist/web/licenses.txt` にまとめて出力し、npm の公開物に含める。
`vite.config.ts` のプラグインが、束ねたコードに中身が残ったパッケージ（スタイルシートやフォントとして取り込んだものを含む）を集め、それぞれのライセンスのファイル（`LICENSE`、`LICENSE-MIT`、`COPYING`、Apache-2.0 が引き継ぎを求める `NOTICE` など）の全文を書き出す。
ライセンスのファイルがないパッケージがあれば、ビルドを失敗させる。
MIT など多くのライセンスは、著作権表示と本文を含めることを求めるからである。
画面では、設定画面の下部の「ライセンス」から開く。
開発中（`npm run dev`）は、Vite が最後に `npm run build` で作った版を返す。

## ディレクトリ

```
src/web/
  main.tsx, App.tsx      起動と全体の配置
  apiClient.ts           サーバーの API を呼ぶ関数（fetch、セッショントークン、エラーの型）。
                         src/web/api/ には置かない（開発時に /api/ で始まる URL で配信され、
                         Vite がローカルサーバーへ転送してしまう）
  errors.ts              API のエラーの分け方と、画面に出す文言（「エラーの扱い」）
  ai/                    AI の要望の印、提案の reducer、差分、送る量（純粋な関数）
  rest/                  REST API の画面の reducer、確認、データを変えうるかの判定（純粋な関数）
  apex/                  Apex の画面の reducer、確認、ログの区切り、色分け（純粋な関数）
  state/                 アプリの状態（React の Context と useReducer）
  soql/                  SOQL の解析、組み立て、字句の区切り、補完の候補（React に依存しない純粋な関数）
  results/               結果の表の列の決め方、セルの値、CSV（純粋な関数）
  orgs/                  本番の判定などの組織に関する純粋な関数
  components/            画面の部品。部品ごとに *.tsx と *.module.css
  i18n/                  英語と日本語の文言
  styles/tokens.css      デザイントークン
```

`soql/`、`results/`、`orgs/` は React に依存しない純粋な関数にし、単体テストの中心にする。
旧版で不具合が出やすかったのはこの部分（SOQL と項目の選択の同期、結果の列の展開）だからである。

## 状態の持ち方

状態管理のライブラリは使わず、React の Context と `useReducer` で持つ。
状態の数が少なく、外部の依存を増やす理由がないからである。
変わる頻度が違う状態は Context を分け、エディタの入力で結果の表が再描画されないようにする。

| 状態 | 持つ場所 |
| --- | --- |
| セッショントークン | sessionStorage（`apiClient.ts` が管理） |
| 起動時の指定（組織、クエリ、実行するか） | 起動時に一度だけ使い、保存しない。再読み込みで `--run` を再実行しないためである |
| 組織の一覧、各組織の状態の印（未確認、正常、認証エラー） | `OrgContext` |
| 選んでいる組織、その詳しい種別と名前空間、API 使用量 | `OrgContext`。選んでいる組織のユーザー名は sessionStorage にも保存し、再読み込みで戻す |
| オブジェクトの一覧、describe の結果 | 組織ごとのメモリ上のキャッシュ（サーバーにもキャッシュがあるので、タブの再読み込みで消えてよい） |
| エディタの本文 | CodeMirror が持ち、React の状態にしない。変更のたびに sessionStorage に保存する |
| エディタの解析結果（FROM のオブジェクト、選んでいる項目）、Tooling API と Query All の指定、API バージョン | `SoqlContext`。API バージョンは sessionStorage にも保存し、同じ組織の再読み込みで戻す（「API バージョン」） |
| 結果（生のレコード、列、続きのページの URL、子レコードの表） | `ResultContext` |
| 最近のクエリ | サーバーから取得し、クエリの実行後に取り直す |
| 設定 | サーバーから取得し、設定画面で保存する |
| いま開いている画面（SOQL、REST API、Apex） | `AppContext`。sessionStorage にも保存し、タブの再読み込みで戻す |
| REST API の画面の状態 | `RestContext`（[rest.md](rest.md)） |
| Apex の画面の状態 | `ApexContext`（[apex.md](apex.md)） |
| パネルの開閉 | localStorage |

API 使用量は、組織の API の応答に含まれる `apiUsage` で毎回更新する。

組織を選んだら（起動時、切り替え時、再読み込み時のいずれも）、summary、オブジェクトの一覧、最近のクエリを並行して取得する。
summary は、詳しい種別、本番の帯、名前空間、API 使用量の最初の値の取得元である。
summary が届くまで、本番の判定は組織の一覧の情報（`kind` と `edition`）で行い、名前空間はないものとして扱う。
summary の取得に失敗した場合（Organization を読めないユーザーなど）も同じ扱いを続け、通知は出さない。

組織を切り替えたら、作業画面の状態をすべて初期化する（エディタの本文、Tooling API と Query All の指定、API バージョン、結果、AI の要望と提案を含む）。
残すのはパネルの開閉だけである。
組織ごとの画面と組織に関係ない画面を作り分けずに済み、非同期の流れが単純になるからである（「非同期の流れ」）。
同じ SOQL を別の組織で実行するには、切り替える前にエディタの内容をコピーする。
最近のクエリは組織ごとに保存されているので、元の組織に戻れば元の履歴が表示される。
クエリの実行中や AI の生成中に切り替えると、実行や生成は止まって消える。
組織を選ぶまでは、作業画面を表示しない。

## 起動から作業画面まで

起動用のコードの交換は、React の描画の前に `main.tsx` で1回だけ行う。
`useEffect` で行うと、React の開発時の二重実行で2回送られ、2回目が「使用済み」になるからである。

1. URL が `/launch/<code>` なら、`POST /api/session` でセッショントークンと起動時の指定を受け取る。トークンだけを sessionStorage に保存し、URL を `/` に置き換える。
2. URL が `/` で sessionStorage にトークンがあれば、それを使う（タブの再読み込み）。
3. トークンがなければ、「`npx sfbench` を実行して開いてください」と表示する。
4. 組織の一覧を取得する（数秒かかることがあるので、読み込み中の表示を出す）。
5. 選ぶ組織を決める。起動時の指定があればそれを、なければ sessionStorage に保存した組織を、組織の一覧と照らして選ぶ。起動時の指定が一覧になければ案内を出し、組織の一覧を開く。どちらもなければ、組織の一覧を開いた状態で始める。
6. 起動時の指定にクエリがあれば、最初に表示する作業画面のエディタに入れ、`run` があり組織が見つかっていれば実行する（「非同期の流れ」の「起動時のクエリ」）。

## エラーの扱い

`apiClient.ts` は、サーバーの応答の `error.code` を持つエラーを投げる。
どこに出すかは `errors.ts` の `errorKind` だけが決め、Context や流れは、その結果に従って振る舞う（コードを自分で比べない）。
サーバーが自分の状態について返す文（タイムアウトなど）は、`errorMessage` が画面の文言に置き換える。
HTTP ステータスを見るのは、`UNAUTHORIZED` の 401（セッションが無効）と 410（起動用の URL が使えない）を分けるときだけである。
サーバーは Salesforce が返した 4xx のステータスをそのまま返すので、ステータスだけで判定すると、Salesforce の 401 を sfbench のセッション切れと取り違えるからである。

| 応答 | 画面の扱い |
| --- | --- |
| 401 `UNAUTHORIZED`（セッションが無効） | 作業画面を残したまま、上部の帯で「sfbench に接続できません。`npx sfbench` を実行して開き直してください」と案内する。エディタの内容は sessionStorage に残っている |
| 410 `UNAUTHORIZED`（起動用の URL が期限切れか使用済み） | 作業画面の代わりに「この URL は使えません」と表示する |
| `ORG_AUTH_ERROR` | その組織の状態の印を認証エラーにする。再ログインのコマンド（`reloginCommand`）をコピーボタン付きで、クエリの実行中なら結果の位置に、それ以外なら通知に出す。組織の一覧にも同じコマンドを出す |
| 503 `SF_CLI_NOT_FOUND` | 作業画面の代わりに、sf CLI のインストールを案内する |
| `SALESFORCE_ERROR`（Salesforce がエラーを返した） | 実行のエラーなら結果の位置に、それ以外（describe、続きのページ）なら通知に出す。`details`（Salesforce が返した JSON）を開いて見られるようにする。「AI で直す」は、実行のエラーのうち、Salesforce が 400 で断ったものにだけ出す。Salesforce は書き方の誤り（`MALFORMED_QUERY`、`INVALID_FIELD` など）を 400 で返す。403（API の上限、権限）や 5xx（Salesforce の側の失敗）は、クエリを直しても通らないからである |
| 504 `SALESFORCE_TIMEOUT`（Salesforce が時間内に答えなかった） | `SALESFORCE_ERROR` と同じ場所に、「Salesforce の側で処理が終わっている場合がある」と案内する。「AI で直す」は出さない（クエリの書き方の問題ではないため） |
| 502 `SALESFORCE_UNREACHABLE`（データを変えうる要求の送信の途中で接続が切れた） | 同じ場所に、「Salesforce が処理した場合があるので、送り直していない」と案内する |
| `fetch` 自体の失敗（サーバーが止まっている） | 401 と同じ帯で案内する |
| `ORG_NOT_FOUND`（組織がない） | 組織の一覧を取り直し、組織の一覧を開いて選び直してもらう。知らない経路の 404 は `NOT_FOUND` で、組織の一覧は開かない |
| そのほか（`SF_CLI_ERROR`、`BAD_REQUEST`、`NOT_FOUND`、`INTERNAL_ERROR`、`details` のない `SALESFORCE_ERROR`） | 実行のエラーなら結果の位置に、それ以外なら通知に `message` を出す |
| API 以外の例外（画面のプログラムの誤り） | 「そのほか」と同じく、起きた流れの場所（結果の位置、組織の一覧の位置、AI の入力欄の下）か通知に、例外の文を出す |

エラーの「詳細」（`details`）は、どこに出すときも `ErrorDetails` の部品で、開いて見られる形にする。

組織が1つもない場合は、組織の一覧に「sf CLI でログインした組織がありません」と出し、`sf org login web -a <alias>` を案内する。

読み込み中は、操作した場所（オブジェクトの一覧、項目の一覧、結果、組織の一覧）ごとに読み込み中の表示を出す。

### 非同期の流れ

画面が API を呼んで結果を状態に反映する処理を、**流れ**と呼ぶ（クエリの実行、続きのページ、最近のクエリ、CSV の取得、AI の生成、接続の確認など）。
流れには、新しい要求による置き換え、利用者の中止、組織の切り替え、画面から消えること、遅れて届いた応答、二度押しが重なる。
区切り2と3では、これを流れごとに世代の番号、取得中の印、ref、組織の印で守ったため、守り方がばらばらになり、レビューのたびに穴が見つかった。
そこで、穴の原因になる出来事のうち、組織の切り替えと遅れて届いた応答は、画面の作りで起きないようにする。
残る置き換え、中止、二度押しは、小さな共通の部品 `useTask` だけで扱う。

#### 仕組み

次の3つで成り立つ。

- **組織を切り替えたら作業画面を作り直す**：作業画面（左の一覧、AI の入力欄と提案、エディタ、最近のクエリ、結果）は、利用者が選んだ組織のユーザー名（`OrgContext` の `selected`）を React の `key` にして描き、ユーザー名を props で渡す。表示する条件も `selected` である。組織の一覧を読み直して、選んでいる組織が一覧から消えても（`selectedOrg` が見つからなくても）、作業画面はそのまま残す。そのあいだ、本番の帯は「わからない組織は本番として扱う」（screens.md）に従う。組織を切り替えると作業画面全体が作り直され、古い作業画面の中の要求は `useTask` が中止する。組織の切り替えは「画面から消える」と同じ出来事になり、流れの側で組織を比べる必要がなくなる。実行中や生成中でも切り替えられ、そのときは実行や生成が止まって消える。同じ組織を選び直したときは作り直さない（`key` が変わらない）。組織の一覧を読み直して表示用の情報が変わっても、`selected` が同じなら作り直さない。組織を選ぶまでは、作業画面を表示しない。
- **API の呼び出し口で中止を優先する**：`apiClient` は、渡された `signal` が中止されていれば、応答が届いていても必ず `ABORTED` を投げる。
- **`useTask`**：流れごとに1つ持つ部品である（`src/web/state/useTask.ts`）。同時に走るのは1本だけで、走っている間に始めたときは、前の要求を中止して置き換えるか（`replace`）、無視するか（`ignore`）を選ぶ。画面から消えたら、走っている要求を中止する。1つの状態を書く流れが複数あるときは、1つの `useTask` を共有するか（組織の一覧の読み直しと待ち合わせと再確認）、書く側の流れを、古い要求が残りうる間は必ず作り直される部品の中に置く（続きのページは、実行ごとに作り直す結果の表の部品の中に置く）。どちらでも、「先にほかの流れを止める」という取り決めが要らない。

本体（`useTask` に渡す関数）と、呼んだ側の役割は次のように分ける。

- **本体は状態を書かない**：本体は、`signal` を API に渡して結果を返すだけにする。本体は、`useTask` から渡された `signal` 以外で要求を中止しない（タイムアウトや別の `signal` を組み合わせない）。待ち時間の上限が要る処理は、サーバーの側で数える（AI の応答の待ち時間など）。本体の中で読んでよいのは、引数と、呼んだ時点で渡された値だけである。API 使用量のように、ついでに得た値も戻り値で返す。
- **途中の表示は `useTask` が持つ**：CSV の取得件数や AI の段階は、本体が `progress(値)` で知らせ、`useTask` が自分の状態として持つ。要求が終わったとき、中止されたとき、無効になったときは、`useTask` が消す。呼んだ側は、この値を表示するだけで、後始末をしない。
- **反映は `done` を受けたときに、`await` を挟まずに行う**：呼んだ側は、`start` が返した結果が `done` なら、その場で状態に反映する（途中で別の `await` をしない）。`error` なら通知などの後始末をする。`stale` なら何もしない。作業画面の外への書き込み（通知、組織の状態、API 使用量）も、`done` か `error` を受けたときだけ行う。`done` か `error` を返したあとに作業画面が消えても、外への書き込みは行ってよい（その要求は終わっているため）。

組織を切り替えたときは、作業画面の状態をすべて初期化する（エディタの本文と取り消しの履歴、Tooling API と Query All の指定、API バージョン、AI の要望と提案、結果、絞り込みの文字を含む）。
パネルの開閉は localStorage にあり、作り直した作業画面が読み直すので残る。
エディタの本文は、同じ組織のまま再読み込みしたときだけ復元する。
本文は sessionStorage に組織と一緒に保存し、保存先には表示中の作業画面の本文だけがある、という形を保つ。
そのために、エディタは作られたときに `claimEditorText(org, initial)` で保存先を自分の組織のものにする。
起動時のクエリ（`initial`）があればそれを保存して返す。
なければ、保存先がその組織の本文ならそれを返し、ほかの組織の本文なら保存先を消して（`removeItem`）空を返す。
ここで組織を比べるのは、再読み込みで戻す本文がどの組織のものかを知るためである（遅れて届いた応答を捨てる比較ではない）。
以後は変更のたびに保存する。
前の組織の本文は、切り替えた先のエディタが作られた時点で消えるので、元の組織に戻っても出てこない。
別の組織から元の組織へ戻っても、本文は復元しない（「切り替えたら初期化する」を例外なく守るため。前の本文は最近のクエリから呼び出せる）。
最近のクエリはサーバーが組織ごとに保存しているので、元の組織に戻れば元の履歴が表示される。
通知（`AppContext`）は作業画面の外にあり、組織を切り替えても、利用者が閉じるまで残る。

#### `useTask` の形

```ts
type TaskOutcome<T> = { kind: 'done'; value: T } | { kind: 'error'; error: unknown } | { kind: 'stale' }

function useTask<P = never>(): {
  /** 置き換え、中止、画面から消えたことで無効になった要求は 'stale' を返す */
  start: <T>(
    body: (signal: AbortSignal, progress: (value: P) => void) => Promise<T>,
    whileRunning: 'replace' | 'ignore',
  ) => Promise<TaskOutcome<T>>
  cancel: () => void
  running: boolean
  /** いま走っている要求が知らせた途中の値。走っていなければ undefined */
  progress: P | undefined
}
```

`start` と `cancel` は、表示のたびに同じ関数を返す（effect の依存配列に入れてよい）。

#### `useTask` の状態と遷移

要求が有効かどうかは、`useTask` の中の「いま走っている要求」と比べる1か所だけで判定する。
「画面から消えたか」の印は、最初は下りていて、消えたとき（layout effect の後始末）に立て、layout effect で下ろす。
表示の前でも、表示の effect、layout effect、操作の処理のどこから `start` を呼んでも走る。
StrictMode の「表示、消える、もう一度表示」では、消えたときに要求を中止し、もう一度表示したときに印を下ろす。

| いまの状態 | 出来事 | 次の状態 | `start` の結果 |
| --- | --- | --- | --- |
| 待機 | `start` | 実行中 | |
| 実行中 | `start`（replace） | 実行中（新しい要求、途中の値は消す） | 前の要求は `stale`。前の要求は中止する |
| 実行中 | `start`（ignore） | 実行中（そのまま） | 新しい呼び出しは `stale`。描画を待たずに判定し、連打でも二重に始めない |
| 実行中 | 本体が成功 | 待機（途中の値を消す） | `done` |
| 実行中 | 本体が失敗（`useTask` が中止していない） | 待機（途中の値を消す） | `error` |
| 実行中 | `progress` | 実行中（途中の値を更新） | |
| 実行中 | `cancel` | 待機（途中の値を消す） | `stale`。要求を中止する。`cancel` は真を返す（待機中や、要求が終わった直後は偽を返し、何もしない） |
| 実行中 | 画面から消える | （なし） | `stale`。要求を中止する |
| 待機 | `cancel` | 待機（そのまま） | |
| 画面から消えたあと | `start` | （そのまま） | `stale`。本体を走らせない |
| 表示の前後 | 子の部品の表示の effect や layout effect から `start` | 実行中 | 印は消えたときにしか立たないので、本体を走らせる |
| 画面から隠れる（Suspense、Activity） | | | 作業画面では使わない。使うなら、隠れたときの見せ方を決めてから、この表に行を足す |
| どれでも | 無効になった要求の成功、失敗、`progress` | （そのまま） | 成功と失敗は `stale`。`progress` は捨てる |
| 待機 | 本体が `start` の中で同期的に例外を投げる | 待機 | `error`（`start` は例外を外へ投げない） |

中止された要求の本体が失敗しても（中止による失敗を含む）、結果は `stale` にする。

#### 失敗したとき

各流れが失敗したときに何を見せ、何を残すかは、次の「流れごとの指定」の表の「失敗したとき、ほか」の列に書く。
`stale` の結果は失敗ではないので、何も見せない。

#### 判定の置き場所

- 要求が有効かどうか：`useTask` の中の「いま走っている要求」と比べる1か所だけ。
- 中止されたかどうか：`apiClient`（`signal` が中止されていれば `ABORTED`）と `useTask`（無効になった要求は `stale`）の2か所。流れの側では判定しない。
- 実行中かどうか：その流れの `useTask` の `running` だけ。結果などの状態に「実行中」を持たない。
- 組織が切り替わったかどうか：作業画面の `key` だけ。流れの側で組織を比べない。

#### 流れごとの指定

| 流れ | 置き場所 | whileRunning | 失敗したとき、ほか |
| --- | --- | --- | --- |
| クエリの実行 | 作業画面 | ignore（AI の Replace & Run だけ replace） | 失敗は結果の位置にエラーを出す（「エラーの扱い」）。`SALESFORCE_ERROR` の結果に、実行した SOQL、Tooling API の指定、付けた要望を持たせる（「AI で直す」が使う。docs/ai.md「画面の状態と遷移」）。実行中は結果の位置に結果の表を出さないので、表の部品は消え、その中の続きのページと CSV の取得も止まる。結果の表の部品は、結果ごとの番号（`id`）を `key` にして作り直す（実行した時刻では、同じミリ秒に終わった実行を区別できない）。「実行中」は、この `useTask` の `running` だけで判定する（結果の状態に「実行中」を持たない）。実行中は、結果の位置に「実行しています」と「Cancel」を出す。Cancel は `cancel` で実行を止め、実際に止めたとき（`cancel` が真を返したとき）だけ結果を空にする。結果は空、`useTask` は待機になり、2つが食い違わない（Salesforce の側で始まった処理までは止まらない、と注記する）。完了と同時に Cancel を押しても、届いた結果は消えない。実行中は、ツールバーの実行ボタンを押せなくし、⌘↵ も何もしない（`ignore` なので、描画を待たずに二度目を始めない） |
| 続きのページ | 作業画面（結果の表の部品の中） | ignore | 結果の表の部品は実行ごとに作り直すので、新しい実行が始まれば、古い続きの取得は部品ごと止まって `stale` になり、別の結果へ行を足さない。結果（`SoqlContext`）は1ページ目だけを持ち、書き換えない。続きの状態（読み込んだ行、次の URL、列、失敗）は、結果の表の部品の reducer（`results/pages.ts`）が持つ（下の「続きのページの状態と遷移」）。CSV の取得も、この状態から始める。読み込み中は、この部品の `useTask` の `running` で、表の下に出す（結果全体を「実行中」にしない）。失敗は「続きを読み込めませんでした」と読み込みのボタンを出し、期限切れのクエリロケーターは再実行を案内する。自動では取り直さない |
| 最近のクエリ | 作業画面 | replace | 何も出さない（一覧が前のまま残る） |
| CSV の取得 | 作業画面（結果の表の部品の中） | ignore | 通知を出す。取得件数は `progress` で知らせ、結果のヘッダーに出す。新しく実行すると、実行中は結果の表を出さないので、結果の表の部品が消え、CSV の取得も止まる。続きの取得が期限切れ（クエリロケーターの失効）になった結果では、CSV のボタンを押せなくする。API 使用量は戻り値で返し、呼んだ側が反映する。`done` のときだけダウンロードする |
| AI の生成と修正（1つの `useTask` を共有） | 作業画面 | ignore | AI の入力欄の下にエラーを出す。段階は `progress` で知らせる。状態と遷移は docs/ai.md「画面の状態と遷移」を正とする |
| AI の接続の確認 | 設定画面 | replace | 欄の下にエラーを出す。入力を変えたら `cancel` する |
| 組織の一覧（読み直し、裏の確認の待ち合わせ、接続の再確認。1つの `useTask` を共有） | 作業画面の外（`OrgContext`） | replace | どれを走らせているかを `progress` で知らせ、読み込み中か確認中かをそこから導く（下の「組織の一覧の状態と遷移」）。新しく始めたものが前のものを止めるので、古い一覧が新しい一覧を上書きしない。待ち合わせは、一覧が完了し、裏の確認が終わっていない（`connectionCheck` が `pending`）ときに始め、待ち時間は `signal` で抜ける。読み直しと再確認の失敗は、一覧の位置か通知にエラーを出し、表示を戻す。待ち合わせの失敗は何も出さない（セッション切れと sf CLI がないことだけは、ほかの流れと同じく案内する）。確認中は「接続を確かめ直す」ボタンを隠し、確認中であることを出す。`ORG_NOT_FOUND` による読み直しも、この task で走らせる |
| 組織の要約 | 作業画面の外（`OrgContext`） | replace | 何も出さない（「組織の一覧と本番の判定」）。`done` のときに、組織ごとの表のその組織の欄へ書く |
| 組織を開く | 作業画面の外（ヘッダー） | ignore | 通知を出す。ボタンの部品を組織の `key` で作り直すので、切り替えたあとに届いた失敗は `stale` になる |
| 設定の読み込み（起動時）と保存 | 作業画面の外（`AppContext`。2つで1つの `useTask` を共有） | 読み込みは ignore、保存は replace | 読み込みの失敗は何も出さない（既定の設定で動く。セッション切れと sf CLI がないことだけは案内する）。保存の失敗は通知を出す。保存は、まだ走っている起動時の読み込みを置き換える。保存中かどうかは `progress` で知らせ、その間は保存のボタンを押せなくする。保存を設定画面の外に置くのは、保存中に設定画面を閉じても、サーバーが書いた設定を画面に反映するためである |
| 設定の読み込み（設定画面） | 設定画面 | ignore | 通知を出して設定画面を閉じる。読み込みが終わるまで、保存のボタンを押せなくする |
| REST API の送信 | 作業画面（REST API の画面） | ignore | 状態と遷移は [rest.md](rest.md)「送信の流れ」を正とする |
| REST API の実行履歴 | 作業画面（REST API の画面） | replace | 何も出さない（一覧が前のまま残る） |
| Apex の実行 | 作業画面（Apex の画面） | ignore | 状態と遷移は [apex.md](apex.md)「実行の流れ」を正とする |
| Apex の実行履歴 | 作業画面（Apex の画面） | replace | 何も出さない（一覧が前のまま残る） |
| 結果の表の保存と削除 | 作業画面（結果の表の部品の中。`useRecordEdits.ts`） | ignore | 状態と遷移は [edit.md](edit.md)「保存と削除」を正とする |
| REST API と Apex の AI | 作業画面（各画面。`useAiSession`） | ignore | SOQL の AI と同じ作り。中身は [ai-agent.md](ai-agent.md)「画面」を正とする |

`signal` を受け取るように直す API は、組織の要約、最近のクエリ、組織の一覧、接続の再確認、設定、組織を開く、である。
中止できない `await`（共有の describe のキャッシュ）は、本体の中で待ってよい。
待っている間に無効になっても、その要求の結果は `stale` として捨てられる。

describe の読み込み（`useLoadable`）は、キーで決まる読み込みと共有のキャッシュを扱う専用の部品として残す。
区切り2から穴が見つかっておらず、キーが変わったら結果を捨て、再読み込みの間は前の結果を残す動きが、すでに状態から導く形になっているからである。

`useLoadable` は、要求と結果から次の値を導き、パネルはそれを読むだけにする（判定をパネルごとに書かない）。

| いまの状態 | 出来事 | `data` | `error` | `loading` | `pending`（「読み込んでいます…」を出す） |
| --- | --- | --- | --- | --- | --- |
| 何もない | キーが決まる（最初の読み込み） | なし | なし | 真 | 真 |
| 読み込み中 | 成功 | あり | なし | 偽 | 偽 |
| 読み込み中 | 失敗 | なし | あり | 偽 | 偽（「読み込めませんでした」を出す） |
| 失敗 | 再読み込み | なし | なし | 真 | 真 |
| データあり | 再読み込み | 前のまま | なし | 真 | 偽（前のデータを出したまま、再読み込みのボタンだけが回る） |
| データあり | 再読み込みが失敗 | 前のまま | あり | 偽 | 偽 |
| どれでも | キーが変わる（Tooling API の切り替えなど） | なし | なし | 真 | 真 |

Tooling API を切り替えると、左の一覧は、新しい API のオブジェクトの一覧が届くまで「読み込んでいます…」を出し、届いてから FROM のオブジェクトの項目に戻る。
届く前に前のオブジェクトの項目を出し続けると、新しい API にそのオブジェクトがあるか確かめないまま describe を呼び、失敗の通知を出しうるので、そうしない。
補完は、要求の寿命を CodeMirror が持つので、`useTask` を使わない。

#### 組織の一覧の状態と遷移

組織の一覧を書く3つの要求（読み直し、裏の確認の待ち合わせ、接続の再確認）は、`OrgContext` の1つの `useTask` を共有する。
本体は、始めたときに `progress` でどの要求かを知らせる。
`useTask` が要求の終わりに途中の値を消すので、「どれを走らせているか」を別の状態に持たず、後始末も要らない。
画面が読む値は、次のように導く。

- **読み込み中**（`loading`）：走っているのが読み直しであるとき。最初の一覧か失敗が届くまでも、読み込み中とみなす（起動の effect が走る前の描画で「組織を選んでください」を出さないため）。
- **確認中**（`connectionCheck` が `pending`）：走っているのが再確認であるとき、または最後に届いた一覧の `connectionCheck` が `pending` のとき。

reducer（`orgState.ts`）は、届いた一覧、最後の読み直しの失敗、組織ごとの要約を持ち、「実行中」を持たない。

| いまの状態 | 出来事 | 次の状態 |
| --- | --- | --- |
| 起動 | 起動の effect | 読み直し（`refresh` なし）を始める。StrictMode では1回目が中止され、2回目が走る |
| どれでも | 組織の一覧を開く、`ORG_NOT_FOUND` | 読み直し（`refresh` あり）で、走っている要求を置き換える |
| どれでも | 「接続を確かめ直す」 | 再確認で、走っている要求を置き換える |
| 一覧あり、確認が `pending`、何も走っていない | （effect） | 待ち合わせを始める |
| 待ち合わせ中 | 届いた一覧の確認が `pending` | 2秒待ってから一覧を反映する。反映で上の行に戻り、もう一度待つ |
| 読み直し、待ち合わせ、再確認のいずれか | 成功 | 一覧と確認の状態を書き、失敗を消す |
| 読み直し中 | 失敗 | 失敗を書く。一覧は前のまま。組織の一覧の位置にエラーを出す |
| 待ち合わせ中 | 失敗 | 確認の状態を `failed` にする。エラーは出さず、「接続を確かめ直す」ボタンを出す（`pending` のままだと待ち合わせを始め直し続けるため） |
| 再確認中 | 失敗 | 通知を出す。確認の状態は前の値に戻る（導いた値なので、書き戻しは要らない） |
| どれでも | 置き換えられた要求の成功や失敗 | 何もしない（`stale`） |

設定の保存の置き場所では、次の案を比べた。

| 案 | 中身 | 弱点 |
| --- | --- | --- |
| 設定画面の `useTask` で保存し、保存中は閉じられなくする | 閉じるボタン、取消、Esc を保存中だけ止める | 閉じる経路を1つずつ塞ぐことになり、取りこぼす（Chrome は続けて押された Esc の取り消しを許さず、ブラウザが dialog を閉じる）。code-review でこの穴が出たので採らなかった |
| 機能を減らす：閉じたら保存の結果を捨て、次に設定画面を開いたときに読み直す | 何もしない | 作業画面の設定（名前空間を省くか）が、次に設定画面を開くまで古いまま残る |
| 採った案：`AppContext` の `useTask` で保存する | 上の表のとおり | 保存の通知と反映を `AppContext` が持つ |

組織の要約は、別の `useTask`（replace）で取得する。
組織を選ぶたびに置き換えるので、切り替える前の組織の要約や失敗は `stale` になり、認証エラーの通知も出さない。

#### 起動時のクエリ

起動時の `-o`、`--query`、`--run` は、`OrgContext` の状態に、**届いた指定**（`launch`）として入れる。
組織を選ぶ `select` の遷移が、届いた指定を、作業画面に渡す**初期値**（`seed`、クエリと実行するかどうか）に変える。
実行するかどうかは、この遷移の1か所だけで、「届いた指定に `run` があり、選んだ組織が `-o` の組織であるとき」と決める。
`-o` の組織かどうか（エイリアスかユーザー名が一致するか）は、自動の選択と同じ関数（`orgState.ts` の `isNamed`）で判定する。
この reducer は `orgState.ts` に置き、表の行をそのまま単体テストにする。
誰が選んだか（自動の選択か利用者か）は見ない。

| いまの状態 | 出来事 | 次の状態 |
| --- | --- | --- |
| 届いた指定あり | `-o` の組織を選ぶ（自動の選択でも、一覧の読み込みに失敗したあと利用者が選んでも） | 初期値は、クエリと、指定どおりの実行するかどうか。届いた指定は消す |
| 届いた指定あり | ほかの組織を選ぶ（`-o` の組織が一覧にないとき、`-o` がないときを含む） | 初期値は、クエリと「実行しない」。届いた指定は消す |
| 初期値あり | 別の組織を選ぶ | 初期値は消す（届いた指定はもうないので、新しい作業画面は何も受け取らない） |
| 初期値あり | 同じ組織を選び直す | そのまま（作業画面は作り直されない） |
| 届いた指定なし | 組織を選ぶ（再読み込み、2回目以降の選択） | 初期値なし |

初期値は、別の組織を選ぶまで `OrgContext` に残る。
作業画面は組織が変わったときにしか作り直されないので、残っていても、受け取るのは最初の作業画面だけである。
初期値は、作業画面に props で渡し、クエリはエディタまで props で渡す。
エディタは、初期値のクエリを最初の本文として作る（取り消しの履歴に入らないので、⌘Z で空にならない）。
実行すると決まっていれば、作業画面は描画の直後（`setTimeout` の 0 ms）に、初期値のクエリを実行する。
エディタの本文を読まないので、エディタが作られる順序に頼らない。
クエリの実行は起動時の指定を知らない。

描画の直後まで待つのは、StrictMode のためである。
StrictMode は作業画面の effect を「実行、後始末、再実行」と続けて動かし、後始末で実行中のクエリを中止する。
effect の中で直接実行すると、1回目の要求は送ってから中止されるので、サーバーに2回届きうる。
予約にすれば、1回目の予約は再実行より前に後始末で取り消されるので、2回目の予約で1回だけ実行される。

- **A→B→A と切り替えたとき**：B を選んだ時点で初期値が消え、A の作業画面は何も受け取らない。
- **クエリが空のとき**：実行しても何もしない（利用者が空のまま実行したときと同じ）。

起動時の指定は、起動用のコードを交換したとき（「起動から作業画面まで」の1）にしか受け取らない。
タブを再読み込みしたときは起動時の指定がないので、保存したエディタの本文を復元する。
実行の失敗は、利用者の実行と同じく結果の位置に出す。

既知の弱点：sfbench の開発中に Fast Refresh で部品が作り直されると、起動時のクエリがもう一度入ったり実行されたりする。
`OrgProvider` が作り直されると届いた指定が起動時の値に戻り、作業画面やエディタの部品が作り直されると初期値をもう一度受け取るからである。
起きるのは開発中だけで、SOQL は読むだけなので害はない。
防ぐには、受け取り終えたことを作業画面から `OrgContext` へ知らせる往復か、起動時の指定を React の外に置く仕組みが要り、開発中だけの事象に対して重いので、どこでも防がない。

起動時のクエリの持ち方では、次の案を比べた。
物差しは、規則が作りで守られるか、規則を知る場所の数、自前のコードの量、表のとおりにテストできるかである。

| 案 | 中身 | 規則を知る場所 | 利点 | 弱点 |
| --- | --- | --- | --- | --- |

#### 続きのページの状態と遷移

結果の表の部品が、`useReducer` で「読み込んだ行、次の URL、列、失敗」を持つ。
初期値は結果の1ページ目である。
届いたページを受け付けるかは、reducer だけが「届いたページの元の URL が、いまの次の URL と一致するか」で決める。
行は、写さずに参照の配列を作り直して足すので、reducer は純粋であり、StrictMode で2回呼ばれても結果は同じになる。

| いまの状態 | 出来事 | 次の状態 |
| --- | --- | --- |
| 次の URL が u、失敗なし | 表の末尾に近づく | u を読み始める（`useTask` の ignore。読み込み中の二度目は何もしない） |
| 次の URL が u | u のページが届く | 行を足し、次の URL を進め、失敗を消す |
| 次の URL が u | u 以外のページか、その失敗が届く（古い描画の値で取り直したもの） | 何もしない（行も失敗の通知も出さない） |
| 次の URL が u | u の取得が失敗する | 失敗を「読み直せる」か「期限切れ」にする。「読み直せる」なら通知を出す（reducer が残した失敗だけを通知する） |
| 失敗が「読み直せる」 | 表の末尾に近づく | 何もしない（自動では取り直さない） |
| 失敗が「読み直せる」 | 読み込みのボタン | u を読み直す |
| 失敗が「期限切れ」 | なし | ボタンを出さず、再実行を案内する |
| 読み込み中 | 読み込みが終わる（受け付けたか捨てたかによらない） | 表がもう一度、末尾に近いかを確かめる（読み込みの関数が作り直されるので、表の effect がもう一度走る） |
| どれでも | 再実行、Cancel、組織の切り替え | 部品が消え、取得中の要求は `stale` になり、状態ごと捨てる |

続きのページの持ち方は、code-review で二重に足される穴が続けて見つかったので、別のサブエージェントに案を出させて比べた。
物差しは、二重に足されないことが作りで決まるか、変更の範囲、reducer が純粋か、である。

| 案 | 中身 | 二重に足されないか | 変更の範囲 | 弱点 |
| --- | --- | --- | --- | --- |
| 採った案：結果の表の部品の reducer が、行も持ち、元の URL を照合して受け付ける | 上の表のとおり | 作りで決まる（照合が reducer の1か所。行と次の URL の持ち主も同じ） | 中（結果の表、CSV、`SoqlContext`） | 古い描画の値で同じページを取り直すと、API を1回余分に使う（足されはしない）。ページごとに参照の配列を作り直す |
| 既存のライブラリ（TanStack Query の `useInfiniteQuery`） | ページの取得と追加をライブラリに任せる | ライブラリが決める（次のページの取得中は二度目を始めない） | 大（取り込む大きさ約13 KB、既定の取り直しを止める設定、キャッシュのキーの設計） | 「非同期の流れ」の検討で採らなかった理由（取り込む大きさ、既定の動きを止める設定）がそのまま当てはまる。期限切れのクエリロケーターの扱いは自前で残る |
| 機能を減らす：自動の読み込みをやめ、ボタンだけにする | 末尾に近づいても読まず、「次の N 件」のボタンで読む | 押すたびの二度押しは ignore で防げるが、古い値で押されたボタンの取り直しは残るので、照合は要る | 小 | 大きな結果をスクロールで見る操作が重くなる（旧版と同じ使い勝手を区切り2dで決めている） |
| 行を結果の配列に足し、件数だけ部品が持つ（ひとつ前の実装） | 行は結果の配列へ push し、reducer は次の URL と件数を持つ | 照合が reducer と配列の長さの2か所に分かれる | 中 | 部品を作り直すと、件数と配列が食い違いうる |
| ページを塊のまま持つ | 行の配列の代わりにページの配列を持ち、書き換えずに足す | 作りで決まる。reducer も純粋 | 大（表、絞り込み、CSV、列幅の見本が、行の引き方ごと変わる） | 変更が広い |
| `useTask` に、終わるときと同じ処理の中で反映する口を足す | `start` に反映の関数を渡す | 決まらない（古い描画の値で呼ばれる経路が残る） | 小 | 「反映は呼んだ側で」という取り決めが変わる |
| 同じ描画の `running` と次の URL で決める（前の実装） | 読み込み中かを描画の値で見る | 決まらない（React が2つの更新を1回の描画にまとめることに頼る） | 小 | 前提がコードにない |

物差しには表れないが、採った案と B2、B3 では、仕組みの数も比べた。
採った案は、`useTask`（操作）、`useLoadable`（キーで決まる読み込み）、CodeMirror の補完の3つを使い分ける。
`useLoadable` と補完は区切り2からの仕組みで、役割が重ならないので、2系統の C' と同じ程度の重さと見た。

組織を切り替えたときにエディタを残すかは、利用者に確かめた。
引き継いでも、別の組織ではオブジェクトや項目がなく実行できるとは限らないので、初期化してよいと決めた。
実行中の切り替えを止める案は、正しさのためには要らないので、利用者と相談して採らなかった。

当初は「クエリロケーター（続きのページの URL）は二度呼べないので、取り直す既定の動きと衝突する」として案A を退けていたが、確かめると、期限内なら同じ URL を呼び直せた（検証用の組織で同じ続きのページを2回取得し、同じ2000件が返った）。
A、B3、C' は、案D を見せずに、別のサブエージェントに問題と制約だけを渡して出させた案をもとにしている。

## SOQL と項目の選択の同期

旧版と同じく、エディタの SOQL を正とし、項目の一覧の選択状態は SOQL から導く。

- **項目を押したとき**: 今の SOQL を `soql-parser-js` で解析し、SELECT 句に項目を足すか外して組み立て直し、整形してエディタに入れる。解析できなければエディタを書き換えず、「SOQL を解析できないので、項目の一覧から変更できません」と案内する。旧版は直前に解析できた内容でエディタを上書きしていたので、書きかけの内容が消えていた。
- **エディタを書き換えたとき**: 入力が止まってから 300 ミリ秒後に解析する。解析できたら、FROM のオブジェクトと SELECT 句の項目から選択状態を作る。FROM のオブジェクトがオブジェクトの一覧にあれば、左の一覧をそのオブジェクトに切り替える。一覧になければ（存在しない名前など）切り替えない。解析できなければ、選択状態は直前のまま変えない。エディタを空にしたら、オブジェクトの一覧に戻る。
- **オブジェクトを選んだとき**: エディタを `SELECT Id FROM <オブジェクト>` に置き換える（旧版と同じ）。
- **実行したとき**: 300 ミリ秒の待ち時間に関係なく、その場で解析して FROM のオブジェクトを決め、結果の表示と CSV のファイル名に使う。
- 親リレーションの項目は `Account.Name` のようにドットでつないだ名前で、子リレーションはサブクエリで表す。
- 項目名、オブジェクト名、リレーション名は、大文字と小文字を区別せずに照らし合わせる。旧版は区別していたので、小文字で書いた SOQL では一覧が追従しなかった。
- 名前空間を省く設定がオンなら、組み立てるときに組織の名前空間を除く。照らし合わせるときは、名前空間付きと名前空間なしを同じ名前とみなす。名前空間を補うのは、カスタムの接尾辞（`__c`、`__r` など）を持つ名前だけで、ドットで区切った各部分に別々に適用する（旧版の `fullApiName` と同じ）。

プログラムからエディタを書き換えるとき（項目の追加と削除、整形、最近のクエリの読み込み、オブジェクトの選択）は、CodeMirror のトランザクションで行い、Cmd+Z（Ctrl+Z）で元に戻せるようにする。

この処理は `soql/` にまとめ、旧版の振る舞い（parity.md の各項目）をテストで押さえる。

## Tooling API と Query All

- ツールバーの Tooling API と Query All は、どちらもチェックボックス（オンとオフの切り替え）にする。
- 一方をオンにすると、もう一方はオフになり押せなくなる。Tooling API には Query All に当たる呼び出しがないからである。
  画面がこれを守り、サーバーは両方がオンの要求を 400 で拒む。サーバーの側は、画面を通らない要求に備えた入力の検査で、画面と同じ判定を二重に持つことを承知で置いている。
- Tooling API を切り替えると、オブジェクトの一覧、describe、補完の候補を Tooling 側（`?tooling=1`）に切り替える。
- 最近のクエリを押したときは、そのクエリを実行したときの Tooling API と Query All の指定も戻す。

## API バージョン

SOQL の画面と Apex の画面のツールバーに、API バージョンの選択を置く。
既定は「最新（66.0）」で、組織が対応するバージョンを新しい順に並べる。
古いバージョンでの項目の見え方や Apex のふるまいを確かめるためである。

- 一覧は `GET /api/orgs/:user/versions`（組織の `/services/data/` の結果）から作り、タブの中で組織ごとに1回だけ取る。取れなければ「最新」だけを出す。
- 選んだバージョンは、画面ごとに別に持つ。エディタの本文と同じ規則で sessionStorage（`sfbench.soqlApiVersion`、`sfbench.apexApiVersion`）に保存し、同じ組織のまま再読み込みしたときだけ戻す。組織を切り替えたときと、`npx sfbench` で開き直したときは最新に戻る。作業画面を作るときに取るので、Apex の画面をまだ開いていなくても、ほかの組織の値は残らない。
- 「最新」を選んでいるときは、バージョンを送らない。サーバーが組織の最新を使う。
- 一覧にないバージョン（読み込み中、または最近のクエリに残したバージョンを Salesforce が廃止したとき）も選択肢に残し、選択の表示と実際に送るバージョンを食い違わせない。組織が対応しなければ、実行したときにサーバーが断る。
- AI の提案は、AI に一覧と項目を渡したときのバージョンを持ち、置き換えるとそのバージョンに切り替える。「AI で直す」は、失敗した実行のバージョンで項目を読み、そのバージョンで実行し直す。
- SOQL の画面では、クエリの実行、オブジェクトの一覧、describe、補完の候補、AI に渡す一覧と項目に効く。続きのページは、Salesforce が返した `nextRecordsUrl` にバージョンが入っているので、そのまま取る。describe はバージョンごとに別にキャッシュする。
- 最近のクエリは、最新でないバージョンで実行したときだけ、そのバージョンを残し、「API 55.0」の札を出す。押すと、そのバージョンに戻す（残していなければ最新に戻す）。同じクエリは、バージョンが違っても1件にまとめ、最後に実行したバージョンを残す。
- Apex の画面では、`sf apex run --api-version <バージョン>` で渡す。コマンドライン引数に画面からの値が載るのはこれだけで、サーバーは形（`66.0` の形）を確かめ、組織が対応するバージョンの中にあることを確かめてから渡す。Apex の実行履歴にはバージョンを残さない。
- 組織が対応しないバージョンは、サーバーが 400 で断り、何も送らない。

## 補完

補完は、旧版にあった候補（FROM のオブジェクトの項目、SOQL のキーワード）に加えて、カーソルの位置の文脈に応じた候補を出す。

### 文脈の判定

書きかけの SOQL は `soql-parser-js` では解析できないことが多い（`WHERE` で終わる文など）。
そのため、`soql/` に字句を区切る関数を置き、文字列リテラルを飛ばしながら、カーソルの位置がどの句（SELECT、FROM、WHERE、ORDER BY など）の中か、どのサブクエリの中かを判定する。
SELECT 句の時点では FROM がカーソルより後ろにあるので、文全体の字句から FROM のオブジェクトを探す。

| 位置 | 候補 |
| --- | --- |
| FROM のあと | オブジェクトの API 名とラベル |
| SELECT、WHERE、ORDER BY、GROUP BY などの句 | FROM のオブジェクトの項目 |
| `Account.` のようにドットのあと | その参照先のオブジェクトの項目（describe を取得してから出す）。ポリモーフィックな参照は最初の参照先（旧版と同じ） |
| サブクエリ `(SELECT … FROM Contacts)` の中 | 子リレーションの子オブジェクトの項目。サブクエリの FROM のあとでは、親オブジェクトの子リレーション名 |
| それ以外 | SOQL のキーワード（`SELECT`、`FROM`、`WHERE`、`ORDER BY`、`LIMIT`、日付リテラルなど） |

### CodeMirror での実現

- CodeMirror の既定の絞り込みは候補の表示名だけに効く。API 名とラベルの両方で絞り込むため、`CompletionResult` に `filter: false` を指定し、絞り込みは自前で行う。候補の `apply` には挿入する名前を入れる。
- 補完の起点を決める正規表現は、日本語のラベルでも探せるよう `\w` ではなく Unicode の文字クラス（`[\p{L}\p{N}_.]`）を使う。
- 候補の表示は「API 名 / ラベル」にする。
- 候補は、API 名が入力と前方一致するもの、ラベルが前方一致するもの、それ以外（部分一致）の順に並べる。同じ順位の中では describe の順を保つ。
- 挿入する名前は、名前空間を省く設定に従う。
- 補完は入力に合わせて開くほか、Ctrl+Space でも開く。↑↓、Enter、Esc、クリックで操作する（CodeMirror の標準）。

### 日本語入力

旧版には「変換を確定した Enter で補完を開く」振る舞いがあり、日本語のラベルで項目を探すのに使われていた。
これを引き継ぎ、変換の確定（`compositionend`）のあとに補完を開く。

ただし Safari では、変換を確定する Enter の keydown が `compositionend` の後に届くことがある。
そのまま補完を開くと、その Enter で最初の候補が確定してしまう。
そのため、`compositionend` から100ミリ秒以内の Enter と、`keyCode` が 229 の Enter は、補完の確定に使わない（補完の確定のキー割り当ての前に、これらを読み捨てるキー割り当てを置く）。
macOS の Chrome と Safari、Windows の Chrome と Edge で、日本語入力のまま手で確かめる。

## 結果の表

### 列

- 列は、SELECT 句ではなく、取得したレコードのキーを集めて作る（旧版と同じ）。親リレーションは `Account.Name` のように展開し、`attributes` は除く。子リレーション（`totalSize` と `records` を持つ値）は1つの列にし、セルには件数を出す。集計関数の `expr0` なども、キーのとおりに列にする。
- 続きのページで新しいキーが現れたら、列を足す。足した列は、同じ親リレーションの列の後ろに置く。旧版は1ページ目だけで列を決めていたので、1ページ目で親リレーションがすべて null だと、2ページ目以降のセルが `[object Object]` になっていた。
- 結果は生のレコードの配列だけを持ち、セルの値は描画のときに列の名前から求める。旧版は全セルについてオブジェクトを作っていたので、大きな結果でメモリを多く使っていた。ページを足すときは、行のオブジェクトは写さず、行への参照の配列だけを作り直す（5万行でも、参照の配列は数百 KB で、すぐに捨てられる）。配列を書き換えずに作り直すのは、続きの状態を1つの reducer にまとめ、受け付けるかの判定を1か所にするためである（「続きのページの状態と遷移」）。

### 描画

- 表は CSS grid で描き、行を TanStack Virtual で仮想化する（見えている行だけを描く）。
- 列幅は、最初のページの先頭200行の値の長さから決めて固定する。続きのページで足した列の幅は、その列を足したページの行の先頭200行から決める（それより前の行では、その列はすべて null だったため）。仮想化した行が入れ替わるたびに列幅が揺れないようにするためである。列幅は見出しの端をドラッグして変えられないが、セルの中身は省略記号で切り、全文はセルを選ぶと見られる。セルは押すか、表にフォーカスを置いて矢印キーで選ぶ。
- 列が多い場合（`FIELDS(ALL)` などで数百列）も横方向は仮想化しない。描く行の数を絞っているので、数百列でも描画は間に合う。
- 列の見出しは固定し、横にスクロールしても見出しと列がずれないよう、見出しと行を同じ grid の中に置く。

### 続きのページ

- スクロールが最後の行の近く（残り50行）に来たら、続きのページを `/query/next` で取得して足す。
- 行の絞り込み中は、続きのページを自動では取得しない。絞り込むと行が少なくなり、すぐに「最後の近く」とみなされて、続きのページを次々に取得してしまうからである。代わりに、絞り込みの結果の下に「次の N 件を読み込む」ボタンを出す。1回押すと1ページ分（最大2000件）を読み込む。
- 行の絞り込みは、読み込み済みの行の、全列のセルの文字列に対する部分一致（大文字と小文字を区別しない）にする。ページを足したときは、足した行だけを調べる。
- 続きのページの取得に失敗したら（クエリロケーターの期限切れ、通信の失敗など）、自動では取得し直さない。最後の行の近くにいる限り取得を繰り返し、API の呼び出しとエラーの通知が続いてしまうからである。代わりに、失敗した旨と読み込みのボタンを出す。クエリロケーターの期限切れ（`INVALID_QUERY_LOCATOR`）は、同じ要求を送り直しても成功しないので、ボタンを出さずにクエリの再実行を案内する。
- 1ページの件数は最大2000件だが、列の多いクエリやサブクエリを含むクエリでは Salesforce がもっと小さいページを返す。読み込みのボタンの件数と CSV の API 呼び出し回数の見込みは、最初のページの件数から求める。
- `COUNT()` のように `totalSize` があってレコードがない結果では、続きのページがないので、残りの件数は0とする。

### 子リレーションとレコード

- 子リレーションのセルを押すと、結果の下に子レコードの表を開く。新しく実行すると閉じる。子レコードの表には、そのサブクエリの1ページ目だけを出す（サブクエリの `nextRecordsUrl` は旧版と同じく扱わない）。
- 18桁のレコード ID は、`instanceUrl/<ID>` への通常のリンクにし、新しいタブで開く（旧版と同じ）。ブラウザが Salesforce にログインしていなければ、ログイン画面になる。ヘッダーの「組織を開く」ボタンでログイン済みの状態にできる（screens.md）。

### CSV

- 続きのページをすべて取得してから作る。
- 残りの件数が1万件を超えるときは、取得を始める前に、件数と API の呼び出し回数の見込み（最初のページの件数ごとに1回）をダイアログで出して確認を取る。取得中は、結果のヘッダーに進み具合と中止のボタンを出す。上限は設けない。
- BOM 付きで、カンマ、改行、二重引用符を含む値を二重引用符で囲む。子リレーションのセルは件数（`N rows`）を出力する。
- 値は手を加えずに出力する。`=` などで始まる値に `'` を付けて表計算ソフトの数式の実行を防ぐ方法もあるが、Excel で開くと `'` がそのまま値として見えてしまうので、付けない（旧版と同じ）。
- ファイル名は `<オブジェクト>.csv` にする。SOQL を解析できずオブジェクトがわからないときは `query.csv` にする。
- 子レコードの表を開いていても、出力するのは親の結果の表である。
- 行を絞り込んでいても、出力するのは全件である。絞り込みは表示のためだけのものとする。
- CSV のために取得したページは、結果の表には足さない。結果の表に数十万件を持たせないためである。中止したときは、取得したページを捨てる。同じページを結果の表の側でも取得することがあるが、許容する。

列の決め方、セルの値、CSV の作り方は `results/` の純粋な関数にし、テストする。

## 組織を開く

ヘッダーの組織の切り替えボタンの隣に、「組織を開く」ボタン（外部リンクのアイコン）を置く。
押すと `POST /api/orgs/:user/open` で、サーバーが `sf org open` を実行し、ログイン済みの状態で組織のホームを開く。
この API はボディを受け取らず、常に組織のホームを開く。
一度開けばブラウザが Salesforce にログインした状態になるので、以後はレコードの通常のリンクで開ける。
`sf org open` は数秒かかるので、押したあとは完了まで読み込み中の表示にする。
SSH の先や WSL では、サーバーのある環境のブラウザで開くので、手元のブラウザでは開かない。

## 組織の一覧と本番の判定

- 組織の一覧のポップオーバーを開くたびに、`/api/orgs?refresh=1` で取り直す。`sf org login web` で足したり、ログインし直したりした組織を反映するためである。取り直している間は、手元にある一覧を表示しておく。
- 本番の判定は `orgs/` の純粋な関数にする。一覧では `sf org list` の情報（`kind` と `edition`）で判定し、組織を選んだあとは summary（`OrganizationType` と `IsSandbox`）で判定し直す。
- 一覧の `kind` が `scratch` の組織は、summary の結果にかかわらず本番にしない。Enterprise Edition で作ったスクラッチ組織は、`OrganizationType` が Enterprise Edition、`IsSandbox` が false になり、summary だけでは本番と区別できないからである。

## サーバーに足すもの

区切り2で、サーバーに次を足す。

- 設定の「Salesforce の応答を待つ時間」（`Settings.requestTimeoutSeconds`、既定は120、10から600までの整数）。範囲外の値は 400 で拒む。`fetch` と `sf api request rest` のタイムアウトに使い、変更は次の要求から効く。`sf` のほかのコマンド（`org list`、`show-access-token`）のタイムアウトは変えない。Salesforce の処理時間ではなく、手元の sf CLI の起動時間に依存するからである。
- describe の応答（オブジェクトの一覧と各オブジェクト）の JSON の最上位に、サーバーが取得した時刻 `fetchedAt`（ISO 8601）を足す。項目の一覧に「読み込んだ時刻」を出すためである。型は `WithFetchedAt<T>`（`src/shared/api.ts`）である。
- `POST /api/orgs/:user/open` を、ボディを受け取らず常に組織のホームを開くように変える。

sfbench のバージョンは、ビルド時に Vite の `define` で画面に埋め込み、設定画面に出す。

## テスト

`useTask` は、「非同期の流れ」の状態と遷移の表の1行を1つのテストにする。
本体には、手で成功や失敗にできる偽の Promise を渡し、`renderHook` で確かめる。
StrictMode の行は `reactStrictMode: true` で確かめる。
組織の切り替えと流れごとの指定は、それを使う画面の単位のテストで確かめる。

- `soql/`、`results/`、`orgs/` の純粋な関数を、旧版の振る舞いを中心に単体テストする。
- 画面の部品は、主要な流れ（起動、組織の選択、オブジェクトの選択と項目の追加、実行、エラーの表示）だけを Testing Library でテストする。API はテストの中で差し替える。
- jsdom はレイアウトを計算しないので、TanStack Virtual は行を描かない。結果の表のテストでは、要素の大きさを差し替えるか、仮想化を止める設定を部品に用意する。
- CodeMirror は jsdom の上では Testing Library の入力操作で書き換えられないので、テストではエディタの `view.dispatch` で入力する。
- 実際の組織につないだ確認と、日本語入力の確認は、手で行う（`npm run dev`）。
