# sfbench 設計

sfbench は、Salesforce の SOQL、REST API、匿名 Apex を手元のブラウザで実行するツールである。
認証は sf CLI に任せ、ブラウザの画面とローカルの Node サーバーで動く。
この文書は、実装と保守の基準となる決定事項をまとめる。
画面の仕様は [screens.md](screens.md) に、lwc-soql-builder から引き継ぐ機能の一覧は [parity.md](parity.md) にある。

## 背景と前提

sfbench は lwc-soql-builder の後継として、ゼロから作り直したものである。
lwc-soql-builder は OAuth のユーザーエージェントフロー（implicit フロー）でログインしていたが、2026年7月末から Salesforce 側でエラーになり、使えなくなった（lwc-soql-builder #47）。
このフローは 2027-02-20 に正式にサポートも終わる（同 #49）。
加えて 2025年9月以降、組織にインストールされていない接続アプリケーションは一般ユーザーが自己承認できない。
そのため、プロジェクトの接続アプリケーションを全組織で使う方式そのものが成り立たない。

sfbench はこの二つを、OAuth を自前で行わないことで回避する。
認証は利用者の sf CLI に保存済みのものを借りる。
sf CLI 自身の接続アプリケーション（`PlatformCLI`）は各組織にもともと入っているので、上記の制限を受けない。

公開後に保守する人がいない前提で設計する。
そのため、運用するサーバーを持たず、利用者の実行時の npm 依存をゼロにし、外部の変化で壊れる箇所を sf CLI の出力に絞る。
この原則の例外は、「原則の例外」の節にまとめる。

対象の OS は macOS、Linux、Windows である。
動作環境は Node.js（22.21.0 以上の 22 系、または 24.5.0 以上）と sf CLI である。
Node の下限は、`fetch` がプロキシの環境変数を読む機能（後述の「プロキシ」）が入った版に合わせた。

## 全体構成

```
npx sfbench [-o <alias>] [--query "<SOQL>" --run] ...
  └ ローカルの Node サーバー（127.0.0.1、既定のポートは 7717）
      ├ 画面（ビルド済みの静的ファイル）を配信し、ブラウザで開く
      ├ アプリ専用の API（/api/*）
      └ Salesforce の呼び出し
          ├ sf CLI から instanceUrl とアクセストークンを取得する
          ├ 基本の経路: トークンを付けて fetch で REST API を呼ぶ
          └ 代わりの経路: sf api request rest に呼び出しを任せる
```

ブラウザは Salesforce を直接呼ばない。
Salesforce の REST API は、組織の CORS 許可リストにあるオリジンからしかブラウザで呼べず、`localhost` は既定で入っていないからである。
登録には組織ごとに管理者の設定が要る。
加えて、ブラウザから呼ぶにはトークンを画面に渡す必要がある。
サーバーはトークンを外に出さず、画面が必要とする操作だけを API として提供する。

## 認証と Salesforce の呼び出し

### sf CLI の呼び出し方

サーバーと CLI の入口は、sf CLI を子プロセスとして呼ぶ。
`@salesforce/core` や sf CLI のプラグイン機構には依存しない。
CLI の内部構造が変わっても、出力の形が保たれる限り動き続けるようにするためである。

| 用途 | コマンド | 呼ぶ側 |
| --- | --- | --- |
| 組織の一覧と instanceUrl | `sf org list --skip-connection-status --json` | サーバー |
| 既定の組織の解決 | `sf config get target-org --json` | CLI の入口 |
| アクセストークンの取得 | `sf org auth show-access-token --no-prompt --json` | サーバー |
| 代わりの経路での API 呼び出し | `sf api request rest --file <request.json> --include` | サーバー |
| 匿名 Apex の実行 | `sf apex run --file <code.apex> [--api-version <バージョン>] --json` | サーバー |
| 組織を開く | `sf org open` | サーバー |

呼び出しは次の規則に従う。

- 対象の組織は引数ではなく環境変数 `SF_TARGET_ORG` で渡す。値は `sf org list` に載っているユーザー名だけを受け付ける。
- 利用者の入力（SOQL、REST API のパスやボディ、Apex のコード）をコマンドライン引数に載せない。`sf api request rest` には、メソッド、URL、ヘッダー、ボディを書いた JSON ファイルを `--file` で渡す。`sf apex run` には、コードを書いたファイルを `--file` で渡す。ファイルは `~/.sfbench/tmp/` に作り、呼び出し後に消す。引数には英数字だけのファイル名を渡す。例外は `sf apex run` の `--api-version` で、画面が選んだ値を、形と組織が対応するバージョンの中にあることを確かめてから渡す（[web.md](web.md)「API バージョン」）。
- `sf org open` にはパスを渡さず、組織のホームを開く。
- `sf` は、起動前に PATH の各ディレクトリから絶対パスを解決し、その絶対パスで起動する（Windows では `sf.cmd` を探す）。作業ディレクトリは PATH の探索に含めない。Windows の cmd.exe はコマンドを PATH より先に作業ディレクトリから探すので、利用者が信頼できないリポジトリで `npx sfbench` を実行したときに、そこにある `sf.cmd` を起動しないようにするためである。
- サーバーが起動する子プロセスの作業ディレクトリは `~/.sfbench/tmp/` に固定する。例外は、CLI の入口が実行する `sf config get target-org` で、利用者の作業ディレクトリのまま実行する。プロジェクトごとの設定（`.sf/config.json`）を読むためである。この場合も `sf` は絶対パスで起動するので、作業ディレクトリにある実行ファイルは起動しない。
- 子プロセスにはタイムアウトを設ける（既定は60秒。`sf apex run` は「Salesforce の応答を待つ時間」に15秒を足した値）。タイムアウトしたプロセスは止め、エラーとして扱う。
- 環境変数 `SF_JSON_TO_STDOUT=true` と `SF_DISABLE_AUTOUPDATE=true` を付ける。エラーの JSON も標準出力から読むためと、自動更新の案内で出力が乱れないようにするためである。
- 終了コードが 0 でない場合も、標準出力の JSON の `name` と `message` を読んでエラーとして扱う。JSON を読めない場合は、標準エラーの内容をエラー文にする。
- `sf` が見つからない（`ENOENT` など）場合は、sf CLI のインストールを案内する。
- サーバーが同時に起動する sf のプロセスは4つまでにし、超えた分は待ち行列で順に実行する。sf の起動は重く、続けて呼ぶと手元の PC の負荷が上がるためである。
- 同じ組織のトークンの取り直しが同時に必要になったときは、`show-access-token` を1回だけ実行し、結果を共有する。

Windows では `sf` の実体が `sf.cmd` で、Node はシェルを通さないと `.cmd` を起動できない。
シェルを通すと引数の記号（`&`、`%`、`^` など）が解釈されるが、上の規則で引数を固定の文字列だけにしているので、解釈される記号は含まれない。

2026-10-16 に sf CLI 2.153.5（macOS）で次を確かめた。

- `sf org display --json` の `accessToken` は伏せられた値になっていて使えない。
- `sf org auth show-access-token` は `--no-prompt` を付ければ非対話で、Node の `execFile` からも呼べる。付けないと確認待ちで止まる。
- `show-access-token` の `result` には `accessToken` しかない。
- アクセストークンを失効させたあとで `show-access-token` を呼ぶと、CLI がリフレッシュした新しいトークンを返す。
- `sf api request rest` は REST API、Tooling API、describe のいずれも動き、`--include` で `Sforce-Limit-Info` ヘッダーも返す。1回の呼び出しに約3秒かかる。

区切り1の初めに、同じ環境で次を確かめた。

- `--skip-connection-status` を付けた `sf org list` は、`instanceUrl`、`isSandbox`、`isScratch`、`isDevHub` を含む。多くの組織では `orgEdition`（`Developer Edition`、`Enterprise Edition` など）も含むが、空の組織もある。組織が約90ある環境では、出力まで約9秒かかった。
- `sf config get target-org --json` は、既定の組織が未設定だと `result[0]` に `value` を含まない。
- `SF_TARGET_ORG` は `api request rest` と `show-access-token` に効く。
- `api request rest --file` の JSON は `{ "url", "method", "header": [{ "key", "value" }], "body": { "mode": "raw", "raw" } }` の形で書く。ヘッダーを `{ "名前": "値" }` の形で書くとエラーになる。`raw` は sf CLI が `JSON.stringify` して送るので、ボディは JSON として解析した値を入れる（文字列を入れると、引用符で囲まれた文字列として届く）。ボディのない要求では `raw` を入れない。
- `api request rest` は、HTTP のエラー（400 など）でも終了コード 1 で、標準出力にステータス行とボディを出す。
- リフレッシュトークンが失効した組織では、`api request rest` は `name` が `Error`、`message` が「Unable to refresh session due to: ... expired access/refresh token」のエラーを返す。`show-access-token` はエラーにならず、保存済みの古いトークンを返す。

次は未確認である。

- `SF_TARGET_ORG` が `org open` に効くこと。
- Windows で上の呼び出し方が動くこと。

### 組織を使えるかの確認

一覧は表示を速くするため、接続を確かめない `sf org list --skip-connection-status` で取得する。
そのうえでサーバーは、起動して一覧を取得したあとに、接続を確かめる `sf org list` を裏で1回だけ実行する。
組織が約50ある環境で約12秒かかり、組織ごとに API を呼ぶので、一覧を開くたびには実行しない。
利用者が「接続を確かめ直す」を押したときにも実行する。

`connectedStatus` から、各組織を次のように分ける。

| `connectedStatus` | 扱い |
| --- | --- |
| `Connected` | 使える |
| リフレッシュトークンの失効を示すエラー文 | 再ログインが必要。一覧の下に畳んで出す |
| 「HTTP response contains html content」か「HTTP status code: 420」を含む | 削除された組織かトライアル切れ。一覧に出さない |
| それ以外 | わからない。一覧に出す |

確認の時点でネットワークが落ちていた場合などに、すべての組織が隠れてしまわないよう、隠すのは削除やトライアル切れのはっきりした印があるときだけにする。
スクラッチ組織は、速い一覧にも含まれる `status` と `isExpired` で判定する。
sf CLI はスクラッチ組織の接続を確かめない（接続を確かめる `sf org list` でも `connectedStatus` がない）ので、Dev Hub に記録された状態で判断し、期限内で Active なら使える、期限切れか Active でなければ一覧に出さない。

`sf org list --json` の出力には各組織の `accessToken` が含まれる。
サーバーは画面に必要な項目だけを写し、トークンを画面に渡さない。

### 呼び出しの手順

サーバーは組織ごとに instanceUrl、アクセストークン、API バージョンを保持する。
組織の識別にはユーザー名を使う。
エイリアスは利用者が付け替えられるからである。

REST API はトークンを付けた `fetch` で呼ぶ。
401 が返ったら `show-access-token` でトークンを取り直し、1回だけ再試行する。
再試行しても 401 なら、認証エラーとして扱う。
API バージョンは、組織ごとに最初の呼び出しで `/services/data/` から最新のものを取得する。
レスポンスの `Sforce-Limit-Info` ヘッダーから API 使用量を読み、画面に返す。

### 代わりの経路への切り替え

次のいずれかに当てはまるとき、その組織の呼び出しを `sf api request rest` で試す。

- `show-access-token` が認証エラー以外の理由で失敗した（コマンドの仕様が変わったなど）。
- `fetch` がネットワークエラーで失敗した。ただし、データを変えうる要求は試さず、エラーにする。データを変えうる要求は、GET と HEAD 以外のメソッドの要求と、メソッドは GET でもデータを変えうると印（`changesData`）を付けた要求である（Tooling API の executeAnonymous は GET で Apex を実行する）。判定は `salesforce.ts` の `mayChangeData` の1か所で行う。応答を受け取る途中で接続が切れた場合、Salesforce はすでに処理を終えている可能性があり、送り直すと二重に実行されるからである。トークンを取得できなかった場合は、要求がまだ送られていないので、どの要求でも試す。

`fetch` にはタイムアウトを設ける（既定は120秒。設定の「Salesforce の応答を待つ時間」で変えられる）。
タイムアウトした場合は経路を切り替えず、エラーにする。

`sf api request rest` で成功した場合だけ、その組織の経路を切り替える。
失敗した場合は切り替えず、エラーを画面に出す（ネットワークそのものが落ちているときに、遅い経路に移っても結果は変わらないため）。
切り替えた組織は、10分経ったあとの最初の読み取りの要求（GET と HEAD）で、もう一度 `fetch` を試す。
データを変えうる要求で試さないのは、`fetch` がまだ失敗する場合に、その要求を送り直せないからである。
`fetch` で接続が途中で切れたデータを変えうる要求は、「Salesforce が処理した可能性があるので送り直していない」と伝えるエラー（`SALESFORCE_UNREACHABLE`）にする。
応答を待つ時間を過ぎたときは、`fetch` でも `sf api request rest` でも `SALESFORCE_TIMEOUT` にする。
どちらも、Salesforce がエラーを返した `SALESFORCE_ERROR` とは別のコードにする。画面が、Salesforce が断ったのか、処理されたかもしれないのかを見分けられるようにするためである。
サーバーは自動では止まらないので、一時的な失敗で遅い経路に移ったままにならないようにするためである。

次のいずれかを認証エラーとみなす。
エラーの `name` は汎用的な `Error` のことがあり、それだけでは判定できないからである。

- `fetch` の経路で、トークンを取り直して再試行しても 401 が返った。失効した組織でも `show-access-token` は古いトークンを返すので、取り直しても 401 が続く。
- `sf api request rest` が 401 を返した。
- sf CLI のエラー文が、リフレッシュトークンの失効を示している（「Unable to refresh session」「expired access/refresh token」「invalid_grant」を含む）。

認証エラーのときは経路を切り替えず、画面に再ログインのコマンド（`sf org login web -a <alias>`）を表示する。
`sf api request rest` に切り替えても同じ認証情報を使うので、結果は変わらないからである。

### プロキシ

会社のプロキシを通す環境では、Node の `fetch` は既定でプロキシの環境変数を読まない。
そのため、CLI の入口はサーバーを Node の `--use-env-proxy` オプション付きで起動する。
このオプションを付けると、`fetch` が `HTTPS_PROXY`、`HTTP_PROXY`、`NO_PROXY` を読む。
Salesforce の呼び出しも AI の API の呼び出しも、これでプロキシを通る。
このオプションは Node 22.21.0 と 24.5.0 で入った。

開発時は環境変数 `SFBENCH_TRANSPORT=cli` で、常に `sf api request rest` を使える。
トークンを扱えない環境（AI のエージェントから動かす場合など）で動作を確かめるためである。

## ローカルサーバー

### API

管理用の API は CLI の入口が呼び、画面用の API は画面が呼ぶ。

| メソッドとパス | 種類 | 内容 |
| --- | --- | --- |
| `GET /api/health` | 管理用 | 生存確認と sfbench のバージョン |
| `POST /api/launch` | 管理用 | 起動用の一回限りのコードを発行する |
| `POST /api/shutdown` | 管理用 | サーバーを止める |
| `POST /api/session` | 交換用 | 起動用のコードを、セッショントークンと起動時の指定に交換する |
| `GET /api/orgs` | 画面用 | 組織の一覧（トークンを除く）と、各組織を使えるか。`waitForCheck=1` を付けると、裏で動いている接続の確認が終わってから答える |
| `POST /api/orgs/check` | 画面用 | 一覧を取り直し、各組織への接続を確かめ直す |
| `GET /api/orgs/:user/versions` | 画面用 | 組織が対応する API バージョン（古い順） |
| `GET /api/orgs/:user/summary` | 画面用 | 組織の詳しい種別（`Organization` の `OrganizationType`、`IsSandbox`）と名前空間 |
| `GET /api/orgs/:user/sobjects` | 画面用 | describeGlobal。`version=` で API バージョンを選べる |
| `GET /api/orgs/:user/sobjects/:name` | 画面用 | describe。`version=` で API バージョンを選べる |
| `POST /api/orgs/:user/query` | 画面用 | SOQL の実行（`{ soql, tooling, queryAll, apiVersion? }`） |
| `POST /api/orgs/:user/query/next` | 画面用 | 続きのページ（`{ nextRecordsUrl }`） |
| `POST /api/orgs/:user/rest` | 画面用 | REST API の実行（`{ method, path, headers, body }`）。Salesforce が返したステータスによらず、200 で `{ id, status, headers, body, size, elapsedMs }` を返す（[rest.md](rest.md)） |
| `GET /api/orgs/:user/rest/history` | 画面用 | REST API の実行履歴 |
| `POST /api/orgs/:user/apex` | 画面用 | 匿名 Apex の実行（`{ code, apiVersion? }`）。コンパイルエラーと実行時の例外も 200 で返す（[apex.md](apex.md)「応答の形」） |
| `GET /api/orgs/:user/apex/history` | 画面用 | 匿名 Apex の実行履歴 |
| `POST /api/orgs/:user/open` | 画面用 | 組織のホームを、ログイン済みの状態でブラウザに開く |
| `GET /api/orgs/:user/history` | 画面用 | 最近のクエリ |
| `GET /api/settings`、`PUT /api/settings` | 画面用 | 設定 |
| `POST /api/ai/generate` | 画面用 | AI に生成させる |
| `POST /api/ai/test` | 画面用 | AI の接続を試す |

`:user` には組織のユーザー名が入る。
`sf org list` に載っていない値は 404 の `ORG_NOT_FOUND` にする。知らない経路の 404 は `NOT_FOUND` にし、画面が組織が消えたと取り違えないようにする。

describe の結果はサーバーのメモリに組織ごとに保持し、タブ間で共有する。
再読み込みを指示されたときだけ取り直す。

サーバーは `/` と `/launch/*` には画面の `index.html` を返す。
画面は、セッショントークンを持たずに `/` を開かれた場合（ブックマークから開いたなど）は、「`npx sfbench` を実行して開いてください」と表示する。

静的ファイルは起動時にメモリへ読み込む。
サーバーは npx のキャッシュ（`~/.npm/_npx/`）から動くので、動作中に別のバージョンが入るとファイルが消えることがあるからである。

### 認証

サーバーには二種類のトークンがある。

- **管理用トークン**：起動時に発行し、`~/.sfbench/server.json` に書く。CLI の入口は管理用の API を呼ぶときに `X-Sfbench-Admin` ヘッダーで送る。
- **セッショントークン**：画面のタブごとに発行する。画面は sessionStorage に置き、画面用の API を呼ぶときに `X-Sfbench-Session` ヘッダーで送る。

画面を開く手順は次のとおりである。

1. CLI の入口が `POST /api/launch` に、組織の名前（エイリアスかユーザー名。解決は画面が行う）と起動時の指定（`--query`、`--run` など）を送る。サーバーは一回限りのコードを返す。コードの有効期限は60秒、`--no-open` のときは10分である。
2. CLI の入口はブラウザで `http://127.0.0.1:<port>/launch/<code>` を開く。
3. 画面はコードを `POST /api/session` に送り、セッショントークンと起動時の指定を受け取る。コードはここで無効になる。
4. 画面は URL を `/` に置き換え、起動時の指定を一度だけ適用する。再読み込みしても、`--run` のクエリは再実行しない。

この方式は次の理由で選んだ。

- 起動時の指定は URL ではなくサーバーから受け取るので、外部の Web サイトが細工した URL を開かせても、クエリは実行されない。
- CLI の入口が表示する URL（`--json`、`--no-open`）には一回限りのコードしか含まれないので、AI のエージェントの会話ログに残っても再利用できない。
- 独自のヘッダーで送るので、別オリジンからの要求はブラウザのプリフライトで止まる。サーバーは CORS の許可を返さない。Cookie を使わないのは、Cookie はポートで分かれず、127.0.0.1 上で動くほかのサーバーにも送られるからである。

コードが期限切れか使用済みのときは、「この URL は使えません。`npx sfbench` を実行して開き直してください」と表示する。
サーバーが再起動するとセッショントークンは無効になる。
無効なトークンで呼ばれたとき、画面は作業中の内容を残したまま、上部の帯で「sfbench に接続できません。`npx sfbench` を実行して開き直してください」と案内する。
エディタの内容は sessionStorage にも保存し、帯が出ても失われないようにする。

### 要求の検証

- `127.0.0.1` だけで待ち受ける。
- `Host` ヘッダーが `127.0.0.1:<port>` か `localhost:<port>` でない要求を拒否する（DNS リバインディングの対策）。
- 管理用の API は、正しい管理用トークンを持ち、`Origin` ヘッダーがない要求だけを受け付ける。CLI の入口が使う Node の `fetch` は `Origin` を送らず、ブラウザは送るので、ブラウザからの要求を拒否できる。
- 画面用の API は、正しいセッショントークンを持つ要求だけを受け付ける。`Origin` ヘッダーがあれば自分のオリジンと一致すること、`Sec-Fetch-Site` ヘッダーがあれば `same-origin` であることも確かめる。ブラウザは同一オリジンの GET に `Origin` を付けないので、`Origin` がないことだけでは拒否しない。別オリジンからの要求は、独自ヘッダーを付けた時点でプリフライトになり、サーバーが許可を返さないので届かない。
- `/api/session` は、有効なコードを持つ要求だけを受け付け、`Origin` と `Sec-Fetch-Site` の確認は画面用の API と同じにする。
- 「自分のオリジン」は、検証済みの `Host` ヘッダーから組み立てた `http://<Host>` とする。
- 任意の URL を中継しない。`/rest` のパスと `/query/next` の `nextRecordsUrl` は、`new URL(path, instanceUrl)` で解決し、オリジンが instanceUrl と一致し、パスが `/services/` で始まる場合だけ通す。
- `GET /api/settings` は API キーを返さず、設定済みかどうかだけを返す。

### バージョンをまたいで変えない契約

新しいバージョンの CLI の入口は、古いバージョンのサーバーを見つけて止める必要がある。
そのため、次の形は 0.1.0 で決めたあと変えない。

- `~/.sfbench/server.json` の項目名: `port`、`adminToken`、`pid`、`version`
- `~/.sfbench/server.lock` の作り方と中身（排他的作成、PID と作成時刻）と、残骸の判定方法
- `X-Sfbench-Admin` ヘッダー
- `GET /api/health` の応答に `version` を含むこと
- `POST /api/shutdown` で止まること
- `POST /api/launch` に組織と起動時の指定を送るとコードが返ること（新しい CLI の入口が、より新しいサーバーを使う場合があるため）

### 開発時の設定

`npm run dev:server` は `--dev` を付けてサーバーを起動する。
`--dev` のときは次のように動く。

- 裏で動かさず、前面で動く。`node --watch` で、ソースを変えると再起動する。
- ポートは 17717 に固定し、使用中なら起動に失敗する。Vite の転送先を固定するためと、手元で使っている sfbench（7717）とぶつからないようにするためである。
- 状態（`server.json`、設定、最近のクエリ、ログなど、普段は `~/.sfbench/` に置くもの）を、リポジトリのルート直下の `.sfbench-dev/` に置く。開発中のサーバーが、手元で常駐している sfbench の `server.json` を上書きしたり、普段使いの設定や履歴を壊したりしないようにするためである。`.sfbench-dev/` は `.gitignore` に入れてある。置き場所は環境変数 `SFBENCH_HOME` で変えられる。
- `/api/session` は、コード `dev` を何度でも受け付け、毎回同じ開発用のセッショントークンを返す。開発用のセッショントークンはサーバーの起動のたびに変わらない値（`.sfbench-dev/` に保存）にする。再起動のたびにコードを取り直さずに済むようにするためである。
- `Host` と `Origin` に Vite の開発サーバー（`localhost:5173`）も許可する。Vite の転送は、ブラウザの `Origin` をそのまま渡す。Vite の転送先を文字列の省略形（`'/api': 'http://…'`）で書くと `changeOrigin` が有効になり、`Host` が転送先に書き換わる。そのためオブジェクトの形で書き、`changeOrigin: false` を明示する。

サーバーは起動時に `http://localhost:5173/launch/dev` を表示する。
Vite は `/launch/dev` には画面（`index.html`）を返し、`/api` だけをサーバー（`127.0.0.1:17717`）へ転送する。
画面のモジュールは `src/web/api/` に置かない。置くと `/api/` で始まる URL で配信され、サーバーへ転送されてしまう。
`npm run dev` は `npm run dev:server` と `npm run dev:web` を並べて起動し、Ctrl+C を押すか Vite が終わると両方を止める（`scripts/dev.mjs`）。
サーバーは `node --watch` の下で動くので、起動に失敗しても（ポート 17717 が使用中など）終了せず、エラーを表示してファイルの変更を待つ。このとき Vite は動き続ける。
画面のコードを保存すると Vite がその場で反映し、サーバーのコードを保存すると `node --watch` がサーバーを起動し直すので、`npm run build` は要らない。
Vite の開発サーバーは `localhost:5173` に固定し、使用中なら起動に失敗する。
`dev:server` は Node の型除去機能で TypeScript を直接実行する。
型除去は、動作環境の下限（22.21.0）で既定で有効になっている。

## 起動

### コマンドライン引数

| 引数 | 内容 |
| --- | --- |
| `-o, --target-org <alias>` | 開く組織。省略時は sf CLI の既定の組織（`target-org`） |
| `--query "<SOQL>"` | SOQL を入力した状態で開く |
| `--run` | `--query` の SOQL を実行した状態で開く |
| `--rest <path> [--method <method>] [--body <json> \| --body-file <file>]` | REST API の入力欄を埋めた状態で開く。送信はしない。メソッドの既定は GET。組織が決まらないときはエラーで終える |
| `--apex "<code>" \| --apex-file <file>` | Apex の入力欄を埋めた状態で開く。実行はしない。組織が決まらないときはエラーで終える |
| `--json` | 開いた URL などを JSON で出力する |
| `--no-open` | ブラウザを開かず、URL だけを出力する（WSL や SSH 先で使う） |
| `stop` | 起動中のサーバーを止める |

AI のエージェントから呼ばれることを想定して、コマンドは画面を開いたらすぐ終了する。
サーバーは切り離した子プロセスとして裏で動く。
自動で実行するのは読み取り専用の SOQL だけで、データを変更しうる REST API と Apex は入力欄を埋めるだけにする。

`-o` を省いたときは、CLI の入口が自分の作業ディレクトリで `sf config get target-org` を実行して既定の組織を得る。
sf CLI の既定の組織はプロジェクトのディレクトリごとの設定で変わるので、利用者が `npx sfbench` を実行した場所の設定に従うためである。
CLI の入口は、`-o` の値か既定の組織（エイリアスかユーザー名）をそのまま `/api/launch` に送り、すぐにブラウザを開く。
組織の名前は画面が組織の一覧（`/api/orgs`）と照らしてユーザー名に解決し、その間は読み込み中の表示を出す。
`sf org list` は組織が多いと数秒から十数秒かかるので、CLI の入口がそれを待ってからブラウザを開くと、利用者は何も表示されないまま待たされるからである。
一覧にない名前なら、画面は「sf CLI に `<名前>` という組織はありません」と表示し、組織の一覧を開いた状態にする。
`--run` の指定があっても、このときは実行しない。
既定の組織もない場合、`--run` を付けていればコマンドはエラーで終了する。
付けていなければ、組織の一覧を開いた状態で画面を開く。

`--rest` の詳しい規則は [rest.md](rest.md)「`--rest` の起動時の指定」に、`--apex` の規則は [apex.md](apex.md)「`--apex` の起動時の指定」にある。

ブラウザは、macOS では `open`、Linux では `xdg-open`、Windows では `%SystemRoot%\System32\rundll32.exe url.dll,FileProtocolHandler` で開く。
いずれもシェルを通さずに、絶対パスか PATH から起動する。
ブラウザを開けなかった場合は、URL を出力して終了する。

SSH のポート転送で使う場合は、手元と同じポート番号に転送する（`-L 7717:127.0.0.1:7717`）。
別の番号に転送すると、`Host` ヘッダーの検証で拒否される。

### 起動中のサーバーの使い回し

コマンドは次の順に動く。

1. `server.lock` を取る。
2. `server.json` を読み、そのポートの `/api/health` に問い合わせる。
3. 応答があり、バージョンも同じなら、そのサーバーを使う。
4. 応答があり、動いているサーバーのほうが古いなら、`/api/shutdown` で止め、そのポートが空くまで最大5秒待ってから新しく起動する。動いているサーバーのほうが新しいなら、そのサーバーを使う。
5. 応答がない、または記録がなければ、新しく起動する。
6. 新しく起動した場合は、子プロセスの PID と一致する `server.json` が書かれ、`/api/health` が応答するまで、最大15秒待つ。待てなければエラーで終了する。
7. `server.lock` を放す。
8. `/api/launch` でコードを受け取り、ブラウザで新しいタブを開く。

サーバーは、待ち受けを始めてから `server.json` を書く。
書き込みは一時ファイルに書いてから名前を変えて置き換え、書きかけの状態を読ませない。
起動時には `~/.sfbench/tmp/` に残ったファイルのうち、1時間以上前のものを消す。
新しいファイルは、止まらずに残っている古いサーバーが使っている可能性があるからである。

既存のタブには送り込まず、毎回新しいタブを開く。
人が書きかけのクエリを上書きしないためである。
タブが複数あるとどれに送るか決められず、外部のコマンドから特定のタブを前面に出すこともできない。

古いサーバーだけを止めるのは、新旧の sfbench を併用している利用者の環境で、互いにサーバーを止め合わないようにするためである。

PID を使ってプロセスを止めることはしない。
PID が別のプロセスに再利用されている可能性があるからである。
`/api/shutdown` に応答しないサーバーがポートを使い続けている場合は、次の空きポートで起動する。
この場合、古いサーバーは PC を再起動するまで残る。
`npx sfbench stop` が止めるのも、`server.json` に記録された1つだけである。

起動処理の待ち時間は、ポートが空くまでの5秒と起動完了までの15秒を合わせて最大20秒になる。
ロックの残骸とみなす時間（60秒）はこれより長くとる。

### 排他

AI のエージェントが続けて2回呼んでもサーバーが2つ立たないよう、起動処理の間は `~/.sfbench/server.lock` で排他する。
ロックは排他的作成（`O_EXCL`）で作り、PID と作成時刻を書く。
ロックがすでにあるときは最大20秒待ち、取れなければ「別の sfbench が起動中です」と出してエラーで終了する。
作成した PID が存在しない、または作成から60秒以上経ったロックは、残骸とみなす。
残骸を消すときは、一意な名前に変えてから消す。
二つの CLI の入口が同時に同じ残骸を消そうとしても、名前の変更に成功するのは一方だけなので、もう一方が新しく作られたロックを消すことはない。

### ポート

既定のポートは 7717 である。
使用中なら 7718、7719 と、7736 まで順に空きを探す。
ポートを固定するのは、ブラウザに保存した表示の好み（localStorage はポートを含むオリジンごとに分かれる）を保つためである。
7717 は、開発でよく使われる番号と、sf CLI が OAuth の受け口に使う 1717 を避けて選んだ。

### 停止

サーバーは自動では止まらない。
`npx sfbench stop` を実行するか、PC を再起動するまで動き続ける。
画面を閉じたまま動いていても、待ち受けているだけで負荷はほとんどない。
自動で止めると、PC のスリープやブラウザによるタブの凍結の間に止まり、作業中の画面が使えなくなるからである。

### ログ

サーバーは `~/.sfbench/server.log` に自分でログを書く。
書き込みのたびにファイルを開いて追記し、閉じる。
書き込む前に 1MB を超えていたら、`server.log.1` に移してから書く。
ファイルを開いたままにしないので、Windows でも動作中に名前を変えられる。
アクセストークン、管理用トークン、セッショントークン、API キー、`sf org open` の URL（セッションを含む）、SOQL、リクエストのボディ、Apex のコードと例外のメッセージは書かない。
Windows では、子プロセスのコンソール画面を出さない（`windowsHide`）。

## データの保存

sfbench の状態はサーバー側の `~/.sfbench/` に置く。

| ファイル | 内容 |
| --- | --- |
| `server.json` | 起動中のサーバーの情報 |
| `server.lock` | 起動処理の排他 |
| `server.log` | サーバーのログ |
| `settings.json` | 設定。AI の API キーも含む。画面から編集し、利用者が手で書く必要はない |
| `history/<ユーザー名>.json` | 組織ごとの最近のクエリ |
| `rest-history/<ユーザー名>.json` | 組織ごとの REST API の実行履歴（[rest.md](rest.md)「実行履歴」） |
| `apex-history/<ユーザー名>.json` | 組織ごとの匿名 Apex の実行履歴（[apex.md](apex.md)「実行履歴」） |
| `tmp/` | `sf api request rest` と `sf apex run` に渡す一時ファイル。子プロセスの作業ディレクトリでもある |

`~/.sfbench/` はディレクトリを 700、ファイルを 600 の権限で作る。
Windows ではこの権限の指定が効かないので、ユーザーのプロファイルのアクセス権に頼る。

履歴のファイル名は、ユーザー名のうち英数字と `@`、`.`、`-`、`_` 以外の文字を `_` に置き換えて作る。

ブラウザの localStorage には、パネルの開閉のような、消えても困らない表示の好みだけを保存する。

### 最近のクエリ

- 実行に成功したクエリだけを残す。`--run` で実行したものも含む。
- 同じクエリは、新しく残さずに先頭へ移す。
- 組織ごとに100件まで残し、古いものから消す。お気に入りの保存は作らない。
- クエリと一緒に、Tooling API と Query All の指定、実行時刻、AI に頼んだ文（区切り3）を残す。
- 書き込むのは `/query` の処理で、成功した場合だけである。

### 設定

| 項目 | 既定 | 内容 |
| --- | --- | --- |
| 名前空間を省く | オン | 組織の名前空間を省いて SOQL を書けるようにする。全組織で共通 |
| Salesforce の応答を待つ時間 | 120秒 | `fetch` と `sf api request rest` のタイムアウト。長いクエリや大きな describe で足りないときに延ばす（区切り2で実装） |
| AI | オフ | 使う AI の API と、その接続情報 |

名前空間を省く設定がオンのとき、サーバーは `/query` と `/query/next` の呼び出しに `Sforce-Call-Options: defaultNamespace=<名前空間>` ヘッダーを付け、画面は SOQL の生成と補完で名前空間を省く。
オフのときはヘッダーを付けず、名前空間付きのまま扱う。
旧版もヘッダーをクエリにだけ付けていた。

`PUT /api/settings` では、API キーの項目を省けば保存済みのキーを維持し、空を明示すれば消す。
ただし、AI の提供元を変えたときは、保存済みのキーを消し、入れ直してもらう。
保存済みのキーが、利用者の意図しない宛先に送られないようにするためである。

## 画面

画面の仕様は [screens.md](screens.md) に書く。
決まっている方針は次のとおりである。

- 起動するとすぐ作業画面を開く。ログイン画面もトップページもない。
- 表示言語は英語と日本語で、ブラウザの言語設定で切り替える。
- 見た目は素の CSS で作る。スコープは CSS Modules で区切り、色や余白は `src/web/styles/tokens.css` の CSS 変数にまとめる。ダークモードは `prefers-color-scheme` で切り替える。
- フォントはダウンロードせず、システムフォントと等幅フォントを使う。
- UI キットは使わず、`<dialog>`、Popover API、`<details>` などブラウザ標準の部品で作る。
- パネルの開閉は、React の状態と CSS の切り替えで作る。ドラッグによる大きさの変更は作らない。

## SOQL

旧版の機能を引き継ぐ。
一覧と実装の状況は [parity.md](parity.md) で管理する。
旧版から変える点は次のとおりである。

- 名前空間は、旧版の SOAP（`metadata.describe`）ではなく `SELECT NamespacePrefix FROM Organization` で取得する。名前空間を省く仕組みは引き継ぎ、設定でオフにできるようにする。
- Tooling API でのクエリを選べるようにする。Tooling API を選んだときは Query All を使えない（Tooling API に対応する呼び出しがない）。
- 最近のクエリは組織ごとに分け、100件まで残す。

## AI で組む機能

利用者が書いた要望から、AI に SOQL、REST API のリクエスト、匿名 Apex を組ませる。
詳細は区切り3で詰める。
ここでは決まっている方針だけを書く。

- 既定は無効である。設定画面で選ぶまで、AI を一切呼ばない。
- 未設定のときは、AI の入力欄の位置に設定への案内を出す。設定画面で Off を選んだ場合は、AI に関する表示をすべて隠す。
- AI は API で呼ぶ。対応するのは Anthropic の Messages API と OpenAI の Chat Completions API の2つである。どちらもサーバーが `fetch` で呼ぶ。OpenAI 互換の API（Gemini、OpenRouter、手元で動かすモデルなど）には対応しない（理由は [ai.md](ai.md)）。
- モデル ID と API キーを、設定画面で入れる。モデル ID は sfbench に埋め込まない。モデルが廃止されたときに、利用者が書き換えるだけで済むようにするためである。
- API キーは `~/.sfbench/settings.json` に保存し、画面には返さない。
- AI を呼ぶのは、利用者が Generate か Fix with AI を押したときだけである。
- AI には組織を触らせない。Salesforce への問い合わせは sfbench が行い、AI にはテキストだけを渡す。渡すのはオブジェクトと項目の名前、型、選択リストの値、エディタの内容、エラー文で、クエリの結果とレコードは渡さない。
- AI の出力は JSON の形で受け取る。Anthropic では `output_config.format`、OpenAI では `response_format` の JSON Schema で形を縛り、受け取った出力は sfbench の側でも検査する（[ai.md](ai.md)）。
- 出力はいったん提案カードで見せ、利用者が反映を選んでからエディタを書き換える。SOQL に限り「反映して実行」を選べる。

AI の CLI（Claude Code、Codex など）を呼ぶ案は採らなかった。
CLI はツールや MCP サーバーを使えるので、渡した文章に指示が埋め込まれていた場合（プロンプトインジェクション）に組織を操作されないよう隔離する必要がある。
その方法は CLI ごとに違い、オプションも頻繁に変わる。
起動にも数秒かかる。
API なら、テキストを送ってテキストを受け取るだけなので、この問題が起きない。

## REST API と Apex

REST API の画面は、メソッド、パス、ボディ、レスポンス、実行履歴だけの簡素なものにする。
複雑なリクエストは AI に組ませる。

Apex の画面は、`sf apex run` で匿名 Apex を実行し、結果とデバッグログを表示する。
デバッグログを同じ呼び出しで受け取れるのが sf CLI だけだからである。
詳細は [apex.md](apex.md) にある。

## 原則の例外

外部の変化で壊れる箇所を sf CLI の出力に絞る、という原則には次の例外がある。
いずれも、壊れたときの影響を一つのファイルに閉じ込め、失敗したときに原因を画面に出す。

- **`sf api request rest` の出力**：`--include` を付けた出力は JSON ではなく、ステータス行、ヘッダー、ボディの生テキストである。解析処理は1ファイルにまとめ、実際の出力を記録したものでテストする。
- **AI の API**：Anthropic と OpenAI の API の仕様が変わると、AI の機能が動かなくなる。呼び出しは提供元ごとに1ファイルにまとめ、失敗したときは API が返したエラー文を画面に出す。

## 技術構成

- 画面は React と TypeScript で書き、Vite でビルドする。
- サーバーは TypeScript で書き、公開前に JavaScript にコンパイルする。Node 標準の API だけを使う。
- 利用者の実行時の npm 依存はゼロにする。画面のライブラリはビルド時に取り込み、npm にはビルド済みのファイルだけを公開する。
- 画面で使う予定のライブラリは、`soql-parser-js`（SOQL の解析と整形）、CodeMirror 6（エディタと補完）、TanStack Virtual（結果の表の仮想スクロール）である。画面の技術設計は [web.md](web.md) にある。
- テストは Vitest で書く。sf CLI の出力は、実際の出力を記録したものを使う。
- CI は、Ubuntu と Windows のそれぞれで、Node 22 と 24 の最新版を使って回す。下限の Node 22.21.0 は Ubuntu でだけ確かめる。

ディレクトリは次のとおりである。

```
src/
  server/   ローカルサーバーと CLI の入口
  web/      画面
  shared/   サーバーと画面で共有する型
docs/       設計文書
```

## 旧版から変わるロジック

| 項目 | 旧版 | sfbench |
| --- | --- | --- |
| 認証 | OAuth。トークンは localStorage | sf CLI に任せる。ログアウトはない |
| 最近のクエリ | localStorage。全組織で共通、20件 | `~/.sfbench/` に組織ごとに100件 |
| API バージョン | sessionStorage | サーバーのメモリに組織ごとに保持 |
| describe の結果 | 画面のメモリ（タブごと） | サーバーのメモリに組織ごとに保持し、再読み込みできる |
| 名前空間の取得 | SOAP | REST のクエリ |
| 名前空間を省く | 常にオン | 設定でオフにできる |
| API 使用量 | jsforce の `limitInfo` | サーバーが `Sforce-Limit-Info` を読む |
| レコードを開く | `instanceUrl` へのリンク | 同じ。加えて、ヘッダーの「組織を開く」ボタンで、`sf org open` によりログイン済みの状態にできる |
| GitHub へのリンク | ヘッダーのアイコン | ヘッダーの「?」と設定画面の下部のリンク。0.1.0 では GitHub の README を開き、説明サイトができたら差し替える |
| PWA | あり | なし |
| Google Analytics | あり | なし |

## 区切り2のあとに作る機能

- **結果の表での編集と削除**：結果のヘッダーの「Edit」の切り替えをオンにしたときだけ、行の選択列が出る。行を選ぶと「Delete N」、セルをダブルクリックして値を変えると「Save N changes」が出る。編集できるのは FROM のオブジェクト自身の、describe で更新可能な項目だけである。保存と削除は REST API の sObject Collections で行い、本番の組織では確認のダイアログを出す。区切り4（REST API の画面）のあとの PR で作る。本番の確認の判定と `/rest` の経路を、REST API の画面と共有する。
